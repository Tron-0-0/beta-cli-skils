# Соглашение: Governance физической модели данных (опционально)

**Когда читать:** в регулируемых доменах (финансы, персональные данные и т.п.), где схема БД должна соответствовать утверждённой физической модели данных вне репозитория, или при подключении инструмента автоматической валидации схемы.

**Что описывает:** синхронизацию Liquibase/Flyway-миграций с утверждённой моделью данных, разметку схемы, точки контроля.

> Этот файл — опциональная надстройка, а не базовое правило: применяй его, только если в организации действительно есть процесс согласования физической модели данных отдельно от кода. Если такого процесса нет — файл не нужен, схема управляется правилами `03_migrations.md`/`08_database.md`.

---

## 1. Правило

- **Источник истины о модели данных** — либо сам код миграций (schema-as-code, самодостаточный вариант), либо внешний утверждённый документ/реестр атрибутов (например, для регулируемых доменов, где схему согласовывает архитектор/DBA до внедрения). Выбранный вариант — один на организацию, не смешивается по сервисам.
- **Самодокументируемость схемы** — комментарии на таблицах/колонках уже обязательны по `03_migrations.md` вне зависимости от этого файла; здесь это отправная точка, а не отдельное требование — governance в регулируемых доменах идёт дальше, к явной маркировке чувствительных данных и (если есть) сверке с внешним реестром.
- **Маркировка PII/регулируемых данных** — колонка, содержащая персональные данные или иную регулируемую категорию (платёжные реквизиты, данные с ограничением доступа), помечается явно в комментарии или в поле классификации внешнего реестра (например, `COMMENT ON COLUMN ... IS 'PII: ...'`) — не полагаться на то, что имя колонки самоочевидно выдаёт её чувствительность. Эта маркировка — источник для смежных решений в других соглашениях: какие поля маскировать в логах (`09_logging.md`), какие не выставлять в DTO без отдельного решения (`07_api_contract.md`).
- **Автоматизированная валидация** (если есть инструмент/плагин сборки, сверяющий миграции с утверждённым реестром атрибутов) — встраивается в фазу сборки, ломает сборку при расхождении имени/типа/описания колонки с реестром, а не оставляется на ручное ревью.
- **Без автоматизации** — контроль соответствия модели данных выполняется ручным ревью изменений схемы архитектором/DBA перед мержем; это не эквивалентно автоматической проверке и должно быть явно зафиксировано как временное или осознанное решение.

## 2. Соглашения для агента

- Не выдумывай наличие инструмента автоматической валидации модели данных, если он не подключён в сборке репозитория — если такого плагина/файла реестра в проекте нет, считать, что контроль ручной, и не описывать автоматизацию как факт.
- При подключении инструмента валидации — конфигурация встраивается в фазу сборки (например, `verify`), реестр атрибутов — единый источник правды, изменения в реестр — только через PR с ревью.
- Каждая новая таблица/колонка — комментарий с описанием, независимо от того, есть ли внешняя валидация.
- Новую колонку с PII/регулируемыми данными — помечай явно в комментарии/реестре при создании, не задним числом; при добавлении такой колонки проверяй, не нужно ли синхронно обновить маскирование в `09_logging.md`/экспозицию в DTO по `07_api_contract.md`.
- Типы и описания в миграции согласовывай с entity (см. `08_database.md`) вручную, если автоматической проверки нет.

## 3. Чек-лист

- [ ] Известно, есть ли в организации процесс согласования физической модели данных — если нет, этот файл не применяется
- [ ] Каждая новая таблица/колонка имеет комментарий с описанием назначения
- [ ] Колонки с PII/регулируемыми данными помечены явно (комментарий/реестр), не только по смыслу имени
- [ ] Если есть инструмент автоматической валидации — он подключён к фазе сборки и не даёт смержить расхождение
- [ ] Если автоматизации нет — расхождения ловятся ручным ревью архитектора/DBA перед мержем
- [ ] Типы колонок в миграции совпадают с типами полей entity

## 4. Пример: комментарии как минимальный уровень governance

```sql
CREATE TABLE orders (
    id UUID PRIMARY KEY,
    customer_email VARCHAR(255) NOT NULL,
    total_amount NUMERIC(18, 2) NOT NULL
);
COMMENT ON TABLE orders IS 'Заказы клиентов';
COMMENT ON COLUMN orders.customer_email IS 'PII: email клиента для уведомлений о заказе';
COMMENT ON COLUMN orders.total_amount IS 'Итоговая сумма заказа, включая налоги';
```

## 5. Когда пересматривать

При появлении/отключении инструмента автоматической валидации модели данных, изменении процесса согласования схемы с архитектором/DBA, либо при изменении политики классификации чувствительных данных.
