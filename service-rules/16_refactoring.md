# Соглашение: Рефакторинг кода

**Когда читать:** при рефакторинге, code review, добавлении новых сервисов, устранении дублирования.

**Что описывает:** лимиты длины/сложности, устранение дублирования, когда абстракция оправдана.

---

## 1. Правило

- **Методы** — не длиннее ~30 строк. Длиннее — сигнал выделить приватные методы по смысловым блокам.
- **Классы** — не длиннее ~200 строк для сервисов/контроллеров; DTO с вложенными структурами и Swagger-документация могут быть длиннее (до ~400), но выносить JSON-примеры/константы в ресурсы, а не раздувать класс текстом.
- **Цикломатическая сложность** метода — не больше 5; больше — разбить на части с выделением условий в отдельные методы/предикаты.
- **Вложенность** — не больше 3 уровней; глубже — early return/guard clauses вместо вложенных `if`.
- **Параметры метода** — не больше 5 (см. также `01_coding.md` про форматирование вызовов); больше — параметр-объект или признак, что метод делает слишком много.
- **Правило трёх (rule of three):** абстракцию/обобщение вводи после третьего повторения похожего кода, не после второго и тем более не заранее "на будущее" — преждевременная абстракция под гипотетические будущие варианты обычно дороже, чем директное дублирование двух похожих блоков.
- **Дублирование между похожими сущностями одного домена** (два сервиса с идентичной структурой `create → map → save → response`, набор идентичных методов, отличающихся только типом) — кандидат на template-паттерн/generics, но только когда реальное дублирование подтверждено (одинаковая логика, не просто похожая структура).
- **Рефакторинг не меняет наблюдаемое поведение.** Это структурное изменение, а не функциональное; если по ходу обнаружен баг или нужна дополнительная логика — это отдельное изменение, не смешанное с рефакторингом в одном коммите/PR. Смешанный diff лишает ревьюера возможности отличить безопасное переименование/выделение метода от изменения, которое нужно проверять внимательнее.
- **Без тестового покрытия — сначала тест, потом структура.** Если код, который предстоит менять, не покрыт тестами (типичный случай для унаследованного кода) — сначала добавляется тест, фиксирующий текущее поведение (см. `06_unit_tests_with_spring_context.md`), и только потом меняется структура; иначе нет объективного способа отличить "рефакторинг ничего не сломал" от "рефакторинг случайно поменял поведение, просто это не с чем сравнить".

## 2. Соглашения для агента

### Устранение дублирования

1. **Template-паттерн для похожих сервисов** — если два+ сервиса имеют идентичную последовательность шагов, вынеси общий код в абстрактный базовый класс/шаблонный метод, оставь специфику в переопределяемых точках. Реализацию паттерна размещай по правилу `01_coding.md` §1.11 — в отдельном пакете по паттерну, не инлайном в `service.impl`.
2. **Generic-методы вместо повторяющихся однотипных методов** — если несколько методов идентичны кроме типа параметра, замени параметризованным generic-методом.
3. **Единые DTO** — если два DTO имеют идентичную структуру полей для разных сценариев (создание/ответ), рассмотри один DTO как источник истины с маппингом, а не поддержку двух копий.
4. **DRY в мапперах** — один маппер с несколькими целевыми методами вместо двух мапперов с идентичной логикой на разные target-типы.

### Когда НЕ обобщать

- Два метода выглядят похоже, но их изменения обычно происходят по разным причинам (разная скорость эволюции бизнес-правил) — предпочти дублирование общей абстракции, которая начнёт обрастать условными ветками "if type == X".
- Абстракция вводится для одного текущего случая "на будущее" — не делай этого, пока не появится второй/третий реальный случай.

### Рефакторинг контроллеров

- Контроллер — только валидация + делегирование; логика длиннее ~15 строк в теле метода контроллера — вынеси в сервис.

### Дисциплина рефакторинга

- Не смешивай структурное изменение с изменением поведения в одном коммите/PR — если по ходу рефакторинга обнаружен баг, фиксируй его отдельным изменением, а не попутно.
- Перед рефакторингом кода без тестов — сначала добавь тест на текущее поведение (см. `06_unit_tests_with_spring_context.md`), не полагайся на то, что "код и так простой, ничего не сломается".

## 3. Чек-лист

- [ ] Метод ≤30 строк, класс ≤200 строк (для DTO/документации — до 400 с обоснованием)
- [ ] Цикломатическая сложность метода ≤5, вложенность ≤3 уровня
- [ ] Параметров метода ≤5
- [ ] Нет дублирующегося кода между похожими сервисами/сущностями (реальное дублирование, не мнимое сходство)
- [ ] Абстракция введена после третьего повторения, не после первого/второго и не "про запас"
- [ ] Изменение поведения (багфикс/новая логика) не смешано со структурным рефакторингом в одном коммите/PR
- [ ] Код без тестового покрытия перед рефакторингом сначала получил тест на текущее поведение
- [ ] Рефакторинг не сломал существующие тесты

## 4. Примеры кода

Дублирование двух сервисов с идентичной структурой:

```java
// До: PhysicalAssetServiceImpl и RentalAssetServiceImpl отличаются только типом
public ServiceResponse createPhysicalAsset(PhysicalAssetRequest request) {
    var org = organisationService.resolve(request.organisationId());
    var entity = mapper.toEntity(request, org);
    repository.save(entity);
    return responseMapper.toResponse(entity);
}
// createRentalAsset — тот же код с другими типами
```

```java
// После: общий шаблон в абстрактном классе, специфика — в переопределении
public abstract class AbstractAssetCreationService<TRequest, TEntity, TResponse> {

    public TResponse createAsset(TRequest request) {
        var org = organisationService.resolve(resolveOrganisationId(request));
        TEntity entity = toEntity(request, org);
        repository().save(entity);
        return toResponse(entity);
    }

    protected abstract UUID resolveOrganisationId(TRequest request);
    protected abstract TEntity toEntity(TRequest request, Organisation org);
    protected abstract TResponse toResponse(TEntity entity);
    protected abstract JpaRepository<TEntity, UUID> repository();
}
```

Generic-метод вместо набора одинаковых `addXxx()`:

```java
// До: addRentalLine/addAssetLine/addServiceLine — идентичны кроме типа
public <T> void addLine(List<T> lines, T line, BiConsumer<T, Order> backReference) {
    lines.add(line);
    backReference.accept(line, this);
}
```

## 5. Когда пересматривать

При появлении третьего похожего сервиса/сущности (проверить, не пора ли обобщать), росте класса сверх лимита, когда введённая ранее абстракция начинает обрастать условными ветками под конкретные типы (сигнал, что абстракция была преждевременной), либо при систематических случаях, когда "безобидный" рефакторинг в PR незаметно менял поведение.
