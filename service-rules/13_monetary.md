# Соглашение: Денежные суммы и точность

**Когда читать:** при работе с денежными суммами, ставками, числовой точностью в финансовых расчётах.

**Что описывает:** `BigDecimal`, масштаб/точность, SQL `NUMERIC`/`DECIMAL`, округление, валюту.

---

## 1. Правило

- **Только `BigDecimal`** для денег — не `double`/`float` (двоичная плавающая точка не может точно представить десятичные дроби — ошибки накапливаются в расчётах) и не `String`/`int`-центы без явного документирования такого решения.
- **`BigDecimal` создавай из `String`, не из `double`** (`new BigDecimal("10.50")`, не `new BigDecimal(10.50)`) — конструктор от `double` наследует погрешность двоичного представления.
- **Масштаб (scale) явный и согласован** между Java-типом, SQL-колонкой (`NUMERIC(precision, scale)`, не "голый" `NUMERIC` без точности, см. `08_database.md`) и DTO контракта. Разные категории сумм (курсы/ставки vs итоговые суммы) могут иметь разный scale — это нормально, если задокументировано.
- **Округление — только явным `RoundingMode`** при любой операции, меняющей масштаб (`setScale(2, RoundingMode.HALF_UP)`); не полагаться на неявное поведение JDBC/Jackson при сериализации.
- **Сериализация в JSON — явное решение, не дефолт.** По умолчанию `BigDecimal` в JSON — число; клиент на JS (числа — IEEE754 double) может потерять точность суммы при разборе. Если контракт должен быть безопасен для таких клиентов — сериализовать сумму как строку (`@JsonFormat(shape = Shape.STRING)` на поле/DTO); решение — зафиксировать явно, а не полагаться на то, что сработает "как есть".
- **Валюта — явное поле**, если сервис работает более чем с одной валютой (`Currency`/ISO-код рядом с суммой); арифметика между суммами разных валют без конвертации — запрещена и должна быть невозможна на уровне типов/валидации, а не только по соглашению.
- **Сравнение `BigDecimal`** — через `compareTo`, не `equals` (`equals` учитывает scale: `10.0` и `10.00` не равны по `equals`, но равны по `compareTo`).
- **Валидация суммы на входе — Bean Validation** (`@DecimalMin`/`@Positive` и т.п. на DTO, см. `07_api_contract.md`), не ручная проверка в сервисе — кроме случаев, где отрицательное значение представляет валидный домен (возврат/сторно), это фиксируется явно в комментарии/названии поля.

## 2. Соглашения для агента

- Новое денежное/ставочное поле — `BigDecimal` и в entity, и в DTO; в SQL-миграции — `NUMERIC(precision, scale)` с явной точностью.
- Любая арифметика над суммами — с явным `RoundingMode` на каждом `setScale`/делении; деление `BigDecimal` без указания scale/rounding кидает исключение при неточном результате — это осознанная защита, не убирать её через `doubleValue()`.
- Не приводи `BigDecimal` к `double`/`float` для расчётов и обратно — только для отображения (и то с осторожностью).
- Сравнивай суммы через `compareTo`, не `equals`, если возможна разница в scale между сторонами сравнения.
- Если появляется работа с несколькими валютами — не пиши курсы/конвертацию "на глаз"; уточняй источник курса и правило округления, фиксируй как отдельное решение.
- Для нового денежного поля в response DTO — уточняй/фиксируй формат сериализации (число или строка); не оставляй это дефолту Jackson без осознанного решения, особенно если контракт потребляет JS/TS-клиент.
- Денежное поле в request DTO — снабжай Bean Validation аннотацией диапазона (`@DecimalMin`/`@Positive`), если отрицательное значение не является ожидаемым доменным случаем.

## 3. Чек-лист

- [ ] Денежные суммы — `BigDecimal`, не `double`/`float`
- [ ] `BigDecimal` создаётся из `String`, не из `double`
- [ ] SQL-колонка — `NUMERIC(precision, scale)` с явной точностью, согласована с Java-типом
- [ ] Округление — явный `RoundingMode` на каждой операции, меняющей масштаб
- [ ] Формат JSON-сериализации суммы (число/строка) — осознанное решение, не дефолт Jackson без проверки
- [ ] Сравнение сумм — через `compareTo`, не `equals`
- [ ] Мультивалютные суммы — с явным полем валюты, конвертация не выполняется "по умолчанию"
- [ ] Денежное поле во входном DTO — с Bean Validation диапазона, если отрицательное значение не является ожидаемым доменным случаем

## 4. Примеры кода

```java
@Column(name = "total_amount", precision = 18, scale = 2)
private BigDecimal totalAmount;

BigDecimal price = new BigDecimal("19.99");                 // из String, не из double
BigDecimal withTax = price.multiply(new BigDecimal("1.20"))
        .setScale(2, RoundingMode.HALF_UP);                  // явный rounding

if (amount.compareTo(BigDecimal.ZERO) > 0) { ... }           // compareTo, не equals
```

```java
public record OrderCreateRequest(
        @NotNull @Positive BigDecimal amount,               // Bean Validation вместо ручной проверки в сервисе

        @JsonFormat(shape = JsonFormat.Shape.STRING)         // явный формат — не дефолт-число, риск потери точности на JS-клиенте
        BigDecimal totalAmount
) {}
```

## 5. Когда пересматривать

При добавлении работы с новой валютой, изменении бизнес-правила округления, либо при обнаружении расхождений точности между слоями (Java/SQL/DTO), включая потерю точности сумм на стороне клиента при разборе JSON.
