# Соглашение: Самопроверка перед сдачей

**Когда читать:** перед push/PR — финальная самопроверка.

**Что описывает:** сводный чек-лист, объединяющий требования остальных файлов набора перед сдачей изменений.

---

## 1. Правило

Перед PR изменения проходят через самопроверку по всем смежным темам, а не только через зелёную сборку. Зелёный `verify`/`check` — необходимое, но не достаточное условие: он не ловит забытые миграции, утечки секретов или неактуальную документацию.

## 2. Чек-лист перед PR

**Сборка и качество кода**
- [ ] Локальная сборка через wrapper (`./mvnw clean verify`/`./gradlew check`) — зелёная (`04_compilation.md`)
- [ ] Новая зависимость не вносит уязвимость выше порога (`04_compilation.md`)
- [ ] Новый/изменённый код покрыт тестами (`06_unit_tests_with_spring_context.md`)
- [ ] Лимиты длины/сложности соблюдены, дублирование — реальное (не мнимое), абстракции не введены "про запас" (`16_refactoring.md`)
- [ ] Слои, DI через конструктор, null-safety, `enum` вместо констант, SOLID, паттерны в отдельном пакете, именование, Javadoc/комментарии, импорты — по конвенции (`01_coding.md`)
- [ ] Нет закомментированного кода и TODO без ссылки на задачу

**Секреты и безопасность**
- [ ] Секреты, пароли, ключи не попали в коммит (проверь diff, не только новые файлы)
- [ ] Логи/метрики не содержат персональных данных и секретов (`09_logging.md`, `02_monitors.md`)
- [ ] Файлы с локальными credentials (`*.env`, `*.local.properties`) — в `.gitignore`, не в индексе
- [ ] Новые/изменённые параметры конфигурации — через env с дефолтом, без хардкода секретов в `application.yml` (`12_configuration.md`)

**Контракт и данные**
- [ ] API-контракт актуален: сигнатуры, OpenAPI-документация соответствуют коду (`07_api_contract.md`)
- [ ] Изменение схемы БД сопровождается миграцией с `--rollback` и комментариями (`03_migrations.md`)
- [ ] Новые/изменённые JPA-связи — `LAZY` по умолчанию, каскады и `@Version` обоснованы, N+1 проверен (`08_database.md`)
- [ ] Денежные поля — `BigDecimal`, с явной точностью в БД (`13_monetary.md`, если применимо)
- [ ] Новый мутирующий REST-эндпоинт (`POST`/`PATCH` с побочным эффектом) поддерживает `Idempotency-Key` (`14_idempotency_rest.md`, если применимо)
- [ ] Разрушающее изменение схемы/контракта разбито на обратно-совместимые шаги
- [ ] Новая таблица/колонка задокументирована согласно governance модели данных, если он принят в организации (`15_data_model_governance.md`, опционально)

**Асинхронность и интеграции**
- [ ] Kafka producer/consumer идемпотентны, ошибки уходят в DLT, десериализация безопасна (`11_kafka.md`, если затронуто)

**Наблюдаемость и эксплуатация**
- [ ] Новые внешние зависимости отражены в readiness-проверке или health-индикаторе (`02_monitors.md`)
- [ ] Ключевые бизнес-события залогированы на уровне INFO с параметризацией, ошибки — со стеком (`09_logging.md`)
- [ ] Изменения graceful shutdown/probes согласованы с `10_cloud_native.md`, если затронуто

**Документация**
- [ ] `README.md`/внутренняя спецификация обновлены, если менялся публичный контракт или конфигурация

## 3. Когда пересматривать

При появлении нового обязательного этапа проверки (например, security-сканера зависимостей), изменении состава смежных правил или добавлении нового файла в набор `service-rules`, чек-лист которого стоит включить в этот сводный список.
