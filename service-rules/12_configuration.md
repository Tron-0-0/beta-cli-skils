# Соглашение: Конфигурация и properties

**Когда читать:** при добавлении конфигурационных параметров, настройке профилей, работе с properties.

**Что описывает:** externalized config, `@ConfigurationProperties`, профили, секреты.

---

## 1. Правило

- **12-factor:** конфигурация — через переменные окружения с дефолтом (`${VAR:default}`), не хардкод в коде и не файлы, специфичные для конкретной машины.
- **Типизированная конфигурация — `@ConfigurationProperties`**, не россыпь `@Value("${...}")` по разным классам: группа связанных параметров валидируется как один объект (`@Validated` + Bean Validation аннотации), ошибка конфигурации падает при старте приложения (fail-fast), а не в рантайме на первом обращении к параметру.
- **`@Value`** — приемлем точечно для одиночного параметра без структуры; как только параметров у одной темы становится 3+, они переезжают в `@ConfigurationProperties`-класс.
- **Профили** (`application-{profile}.yml`) — для различий между окружениями (local/test/prod), не для веток бизнес-логики; логика приложения не должна зависеть от активного профиля напрямую в коде (`if (env.acceptsProfiles("prod"))` — анти-паттерн, кроме бинов инфраструктуры).
- **Секреты** — не в `application.yml`/репозитории, даже с плейсхолдером-дефолтом для чувствительных значений; источник — секрет-менеджер/Vault/переменные окружения CI, инжектируемые в рантайме. Файлы с реальными секретами для локального запуска (`*.env`) — только локально, в `.gitignore`.
- **Имя секретного параметра — распознаваемое** (содержит `password`/`secret`/`token`/`key`/`credential`), не нейтральное произвольное название. От этого зависит не только читаемость: по такому же имени поля/заголовка автоматически срабатывает маскирование в логах (см. `09_logging.md`) и встроенный санитайзер Actuator на `/env`/`/configprops` (см. `02_monitors.md`) — секрет с нестандартным именем оба механизма молча пропускают в открытом виде.
- **Immutable properties-классы** — `record`/`@ConstructorBinding` предпочтительнее мутабельных классов с сеттерами: конфигурация не должна меняться после старта контекста.
- **Профили переопределяют только различия.** Значение, одинаковое во всех окружениях, задаётся один раз в базовом `application.yml`; в `application-{profile}.yml` — только то, что реально отличается. Дублирование неизменного значения по всем профилям создаёт риск: правка в одном файле не применяется, потому что значение переопределено (и забыто) в профиле, который реально активен.

## 2. Соглашения для агента

- Новый связанный набор параметров (3+ штук) — заводи `@ConfigurationProperties(prefix = "...")` record-классом с валидацией, а не отдельными `@Value`.
- Значения без дефолта в коде — только для по-настоящему обязательных параметров (иначе приложение должно падать при старте с понятной ошибкой, а не NPE в рантайме).
- URL/ключи заголовков/лимиты, переиспользуемые в нескольких местах, держи в одном константном классе или properties-объекте, не дублируй строкой в местах использования.
- Секреты никогда не подставляй в код/properties репозитория даже "временно для теста" — используй локальный `.env`, исключённый из индекса.
- Имя нового секретного параметра — с одним из распознаваемых слов (`password`/`secret`/`token`/`key`/`credential`), чтобы маскирование в логах и Actuator-санитайзер сработали без отдельной настройки под каждое новое имя.
- Настройки внешней интеграции (таймауты, URL, resilience-параметры) группируй в отдельный properties-неймспейс на каждую интеграцию — тот же подход применим к настройкам Kafka-топиков/групп (см. `11_kafka.md`), а не только к HTTP-клиентам.
- Новый профиль или правку существующего — проверяй, не дублирует ли он значение, уже заданное в базовом `application.yml` без реальных отличий; такое значение — в базовый файл, а не в профиль.

## 3. Чек-лист

- [ ] Новый параметр — через `${ENV:default}`, без хардкода в коде
- [ ] Связанная группа параметров (3+) — `@ConfigurationProperties` с валидацией, не россыпь `@Value`
- [ ] Обязательные параметры без дефолта вызывают явную ошибку при старте, а не позже
- [ ] Секретов нет в `application.yml`/репозитории; источник — env/секрет-менеджер
- [ ] Имя секретного параметра содержит распознаваемое слово (`password`/`secret`/`token`/`key`/`credential`)
- [ ] Профили используются только для окруженческих различий, не для веток бизнес-логики
- [ ] Значения, одинаковые во всех профилях, заданы один раз в базовом `application.yml`, не задублированы
- [ ] Properties-классы неизменяемы

## 4. Примеры кода

```java
@ConfigurationProperties(prefix = "orders.mdm-client")
@Validated
public record MdmClientProperties(
        @NotBlank String url,
        @NotNull Duration timeout
) {}
```

```java
@Configuration
@EnableConfigurationProperties(MdmClientProperties.class)
public class MdmClientConfig {
}
```

```properties
server.port=${APP_PORT:8080}
orders.mdm-client.url=${MDM_URL}
orders.mdm-client.timeout=${MDM_TIMEOUT:5s}
```

```yaml
# application.yml — общее для всех окружений
orders:
  mdm-client:
    timeout: 5s

---
# application-prod.yml — только реальное отличие prod от остальных
orders:
  mdm-client:
    url: https://mdm.prod.internal
```

## 5. Когда пересматривать

При переезде на другой источник конфигурации (Spring Cloud Config, Vault-агент), появлении новой крупной интеграции с собственным набором параметров.
