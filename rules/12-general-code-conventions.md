# Соглашение: Общепринятые правила написания кода

**Когда читать:** при написании любого нового кода — как общий фон поверх остальных, более специфичных правил этого набора.

**Что описывает:** стандартные практики чистого кода на Java: размер и ответственность класса/метода, управляющие конструкции, именование и константы, неизменяемость, форматирование.

---

## 1. Правило

### 1.1 Размер и ответственность

- Один класс — одна ответственность (SRP). Если у класса появляется несколько независимых причин для изменения — разделить.
- Метод делает одну вещь и называется по тому, что он делает. Размер метода (не больше 40 непустых строк) формализован в `checkstyle.xml` (`MethodLength`), здесь не дублируется.
- Если для читаемости метод разбивается на несколько более мелких — и таких мелких вспомогательных методов набирается много — не копить их приватными методами в том же классе, а выносить в отдельный класс-помощник, у которого будет своя, более узкая ответственность.
- Число параметров метода/конструктора (не больше 4) формализовано в `checkstyle.xml` (`ParameterNumber`). Если параметров больше — сгруппировать в DTO/объект-параметр, а не подавлять проверку.

### 1.2 Управляющие конструкции

- Early return вместо глубокой вложенности `if/else`: сначала проверки и выход из метода, основная логика — без лишнего уровня вложенности.
- Глубина вложенности условий/циклов/`try` формализована в `checkstyle.xml` (`NestedIfDepth`, `NestedForDepth`, `NestedTryDepth`), здесь не дублируется.
- Не использовать пустые `catch`-блоки — либо обработать исключение, либо пробросить дальше (формализовано в `pmd.xml`, правило `EmptyCatchBlock`, сборка падает при нарушении; см. также `07-logging-and-errors.md`).
- Блок `if` (в том числе guard-clause с early return) отделяется пустой строкой от кода до него и после него — если он не является первой или последней строкой окружающего блока (тела метода, цикла, другого `if`/`else`). Пустая строка не нужна, если до/после `if` идёт ещё один `if`/`else if`, продолжающий ту же цепочку условий.
- Блок цикла (`for`, `while`, `do-while`) отделяется пустой строкой от кода до него и после него по тому же принципу, что и `if`: пустая строка не нужна, только если цикл является первой или последней строкой окружающего блока (тела метода, другого цикла, `if`/`else`).
- Фигурные скобки (опускаются только у однострочного тела из одного оператора) формализованы в `checkstyle.xml` (`NeedBraces`), `else if` вместо `else { if (...) }` — `checkstyle.xml` (`MatchXpath`, id `ElseIf`). Здесь не дублируются.

### 1.3 Именование и константы

- Никаких «магических» чисел и строк в коде — выносить в именованные константы (`private static final`). Числа формализованы в `checkstyle.xml` (модуль `MagicNumber`, сборка падает при нарушении). Повторяющиеся строковые литералы — `pmd.xml` (`AvoidDuplicateLiterals`).
- Имена — по смыслу, без сокращений ради экономии символов (`front_word`, а не `fw`), без венгерской нотации.
- Булевы переменные/методы называются как вопрос: `isValid`, `hasNext`.

### 1.4 Неизменяемость и null-safety

- Локальные переменные — `final`, где это не мешает читаемости. Для полей, которые не меняются после инициализации, `final` формализован в `pmd.xml` (`ImmutableField`).
- Не возвращать `null` из публичных методов, где по смыслу может не быть значения, — использовать `Optional<T>` (кроме `default`-методов репозитория, где `Optional` разворачивается, см. `11-repository.md`).
- Не изменять коллекции/объекты, переданные извне, без явной необходимости; при возврате внутренней коллекции наружу — отдавать неизменяемую копию/обёртку, если вызывающий код не должен её мутировать.

### 1.5 Форматирование

- Поля класса по умолчанию идут слитно, без пустых строк между ними (`blank_lines_before_field=0` в `spotless-format.xml`). Исключения — расставляются вручную, Spotless их не проверяет и не исправляет (движок Eclipse JDT formatter не умеет ставить пустую строку перед полем условно, только одинаково для всех полей):
  - `static`-поля отделяются пустой строкой от остальных (нестатических) полей.
  - Поле с аннотацией (`@Value`, `@Mock` и т.п.) отделяется пустой строкой сверху от предыдущего поля; после него, если следующее поле без аннотации, пустая строка не нужна.
- Не оставлять закомментированный (мёртвый) код и `TODO` без конкретики — либо доделать, либо завести задачу и явно описать, что доделать.

## 2. Соглашения для агента

- Прежде чем добавить ещё один параметр в метод с уже 3 параметрами — оценить, не пора ли группировать параметры в объект.
- Не оставлять пустой `catch` даже временно «для отладки» — минимум залогировать через `log` (см. `07-logging-and-errors.md`).
- Добавляя `if` или цикл не первой/последней строкой окружающего блока — отделять его пустой строкой сверху и снизу, а не только там, где "само так получилось".
- Магическое число/строку, встреченные при правке существующего кода рядом с задачей, — выносить в константу попутно, если это не выходит за рамки текущей правки.

## 3. Чек-лист

- [ ] Класс отвечает за одну зону ответственности (SRP)
- [ ] Метод — одна вещь
- [ ] Early return вместо глубокой вложенности
- [ ] Нет пустых `catch`-блоков
- [ ] `if` не в начале/конце окружающего блока отделён пустой строкой сверху и снизу (кроме цепочки `if`/`else if`)
- [ ] Цикл (`for`/`while`/`do-while`) не в начале/конце окружающего блока отделён пустой строкой сверху и снизу
- [ ] Нет магических чисел/строк — вынесены в `private static final`
- [ ] Локальные переменные — `final`, где это не мешает читаемости
- [ ] Публичный метод не возвращает `null` там, где по смыслу может не быть значения — `Optional<T>`
- [ ] Поля слитны, кроме: `static`-поля отделены пустой строкой от остальных, поле с аннотацией отделено пустой строкой сверху
- [ ] Нет закомментированного кода и TODO без привязанной задачи

## 5. Когда пересматривать

Эти практики — общий фон, не специфичный для стека проекта, и пересматриваются редко: только при явном решении команды изменить численные пороги (длина строки, число параметров, уровни вложенности) под конкретный инструмент форматирования/линтер.
