# Соглашение: Repository

**Когда читать:** при создании нового репозитория или нового метода в существующем.

**Что описывает:** структуру интерфейса репозитория, выбор между производным query-методом и `@Query`, что можно и что нельзя делать в `default`-методах.

---

## 1. Правило

- Репозитории — интерфейсы `extends JpaRepository<Entity, UUID>` в пакете `repository/`, с Javadoc на класс (см. `04-comments-and-javadoc.md`). Наличие `@Repository` формализовано в `checkstyle.xml` (`MatchXpath`, id `RepositoryAnnotation`), здесь не дублируется.
- Javadoc на методы репозитория (производные query-методы, `@Query`-методы, `default`-методы) не нужен — исключение из общего правила Javadoc для публичных методов (см. `04-comments-and-javadoc.md`, `MissingJavadocMethod` отключён для `repository/` в `checkstyle-suppressions.xml`): имя метода репозитория должно быть само по себе достаточно описательным.

### 1.1 Производные query-методы vs `@Query`

- Простые производные запросы (`findByX`, `existsByX` и т.п.) объявляются как обычные абстрактные методы интерфейса — реализацию генерирует Spring Data, тело не пишется.
- Если производный метод перерастает простой запрос (много условий через `And`/`Or`) — не наращивать имя метода дальше, а переходить на `@Query` (JPQL) с явным телом запроса и понятным, коротким именем метода. Пороги формализованы в `checkstyle.xml`: имя производного метода не длиннее 40 символов (`MatchXpath`, id `RepositoryDerivedName`), не больше 4 параметров (`ParameterNumber`).

### 1.2 `default`-методы

- В репозитории можно и нужно добавлять `default`-методы, если это:
  - вызов одного/нескольких методов самого репозитория (в том числе производных query-методов или методов с `@Query`), и
  - простая обработка полученного результата: разворачивание `Optional` (`.orElseThrow(...)`), тривиальная проверка (`existsBy...`).
- Выборка/фильтрация коллекции делается запросом (производным методом или `@Query`), а не постобработкой в Java-коде `default`-метода. Запрет циклов и `.stream()` в `default`-методах формализован в `checkstyle.xml` (`MatchXpath`, id `RepositoryDefaultLoop`).
- `default`-методы репозитория не должны содержать бизнес-логику (условия предметной области, оркестрацию нескольких сущностей, вызовы других сервисов/репозиториев) — это остаётся в `service.impl` (см. `01-layers-and-dependencies.md`). Граница простая: если метод отвечает на вопрос «как достать/развернуть данные» — это `default`-метод репозитория; если «что с этими данными сделать по бизнес-правилам» — это сервис.

## 2. Соглашения для агента

- Перед добавлением производного метода со сложным условием — сразу писать `@Query`, а не наращивать имя до предела, который пропустит линтер.
- Не переносить в `default`-метод репозитория обработку, которая по сути является бизнес-правилом (например, решение, что делать при отсутствии записи, кроме тривиального `orElseThrow`) — это `service.impl`.
- Не добавлять Javadoc на методы репозитория — только на класс (линтер лишний Javadoc не ловит).

## 3. Чек-лист

- [ ] Репозиторий — `interface extends JpaRepository<Entity, UUID>`, Javadoc на класс
- [ ] Методы репозитория — без Javadoc
- [ ] Простой запрос — производный метод; сложное условие — `@Query`
- [ ] `default`-метод — только вызов методов репозитория + тривиальная обработка результата (`orElseThrow`, `existsBy...`)
- [ ] В `default`-методе нет бизнес-логики — только «как достать данные», не «что с ними сделать»

## 4. Примеры кода

```java
public interface FrontWordRepository extends JpaRepository<FrontWord, UUID> {

    default FrontWord getByIdOrThrow(UUID id) {
        return findById(id).orElseThrow(() -> new EntityNotFoundException("FrontWord не найден: id=" + id));
        // EntityNotFoundException — кастомное исключение проекта из пакета exception/, см. 07-logging-and-errors.md
    }
}
```

## 5. Когда пересматривать

При переходе части запросов на Criteria API/Specification (для действительно динамических фильтров, которые не выражаются производным методом или простым `@Query`) — тогда правило дополняется разделом про `Specification`, текущие два способа (производный метод / `@Query`) при этом остаются основными для простых случаев.
