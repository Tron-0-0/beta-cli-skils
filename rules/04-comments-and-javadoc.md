# Соглашение: Комментарии и Javadoc

**Когда читать:** при написании нового публичного класса/метода, при добавлении комментария в код.

**Что описывает:** когда обязателен Javadoc, в каком объёме, язык документации и комментариев, когда нужен обычный комментарий.

---

## 1. Правило

### 1.1 Javadoc

- Наличие Javadoc у публичных классов/интерфейсов и публичных методов/конструкторов формализовано в `checkstyle.xml` (`MissingJavadocType`, `MissingJavadocMethod`; методы репозиториев и тестов исключены в `checkstyle-suppressions.xml`), здесь не дублируется. Содержание — на русском: у класса — назначение, у метода — краткое описание + `@param`/`@return`, ссылки на связанные сущности через `{@link ...}`.
- Приватные методы Javadoc не требуют, **кроме** случая, когда приватный метод содержит сложную логику (нетривиальный алгоритм, несколько условий/веток, неочевидная последовательность действий) — тогда Javadoc обязателен и для него.
- Сущности (`model.entity`) — Javadoc в самой простой форме: одна строка с назначением сущности, без `@param`/`@return` (полей это не касается).
- Если метод бросает бизнес-специфичное unchecked-исключение (например, `DuplicateEntityException`) — тег `@throws` с описанием, при каком условии исключение возникает. Для исключений из `throws`-сигнатуры наличие `@throws` проверяет `checkstyle.xml` (`JavadocMethod`, `validateThrows`); для unchecked-исключений, брошенных в теле метода, — только смысловое ревью.

### 1.2 Комментарии

- Комментарии в коде и сообщения в логах — на русском. Идентификаторы кода — на английском (см. `03-naming.md`).
- Не комментировать очевидное.
- Обычный комментарий (не Javadoc) нужен там, где конкретная строка/блок кода делает неочевидную вещь: скрытое поведение Spring/Hibernate под капотом (ленивая загрузка, порядок flush/commit, побочный эффект аннотации), либо бизнес-условие, которое не следует напрямую из кода.

## 2. Соглашения для агента

- Не добавлять Javadoc к приватному методу без нетривиальной логики — лишний Javadoc такого же рода шум, как отсутствующий там, где он нужен.
- Не переводить существующий русскоязычный Javadoc/комментарий на английский и не писать новый на английском — язык документации в проекте единый.
- Не оставлять закомментированный (мёртвый) код.

## 3. Чек-лист

- [ ] Javadoc — на русском (класс — назначение, метод — описание + `@param`/`@return`)
- [ ] Метод, бросающий бизнес-исключение из тела, — с тегом `@throws` и условием возникновения
- [ ] Приватный метод без нетривиальной логики — без Javadoc; с нетривиальной логикой — с Javadoc
- [ ] Сущность (`model.entity`) — однострочный Javadoc без `@param`/`@return`
- [ ] Обычный комментарий стоит только там, где код делает неочевидную вещь, не дублирует то, что и так понятно из кода

## 4. Примеры кода

```java
/**
 * Интерфейс предоставляет методы для работы и управления
 * сущностью {@link FrontWord}.
 */
public interface FrontWordService {

    /**
     * Метод для создания сущности {@link FrontWord}.
     *
     * @param word слово, на основе которого будет создана сущность
     * @return созданная сущность
     */
    FrontWord createAndSaveFrontWord(String word);
}
```

```java
/**
 * Сущность слова, которое изучает студент.
 */
@Entity
@Table(name = "front_word")
public class FrontWord {
    ...
}
```

## 5. Когда пересматривать

Если проект перейдёт на англоязычную документацию (например, при открытии кода внешним контрибьюторам) — язык Javadoc/комментариев меняется здесь одним решением, а не постепенным смешением языков по файлам.
