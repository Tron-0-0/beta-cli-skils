# Соглашение: Логирование и ошибки

**Когда читать:** при добавлении логирования в новый метод, при обработке исключительной ситуации, при создании нового исключения.

**Что описывает:** уровни логирования и что на них логировать, иерархию кастомных исключений, где и как исключения обрабатываются централизованно.

---

## 1. Правило

### 1.1 Логирование

- Логирование только через `@Slf4j` (`log.info`/`log.warn`/`log.error`). Запрет `System.out`/`System.err` и `printStackTrace` формализован в `pmd.xml` (`SystemPrintln`, `AvoidPrintStackTrace`), здесь не дублируется.
- Уровни:
  - `log.info` — начало и конец бизнес-операции в `service.impl` (например: "Создание слова: word={}" в начале метода, "Слово создано: id={}" в конце), а также значимые изменения состояния по ходу операции (сущность сохранена/обновлена/удалена — с указанием её id и ключевых полей).
  - `log.warn` — восстановимые проблемы: невалидные входные данные, ситуация, которую код обработал сам (fallback, повторная попытка, пропуск некорректной строки при импорте).
  - `log.error` — непредвиденные ошибки, исключения, которые пробрасываются дальше и требуют внимания.
- При перехвате исключения — логировать с контекстом (какая операция, какой id/файл/параметр), не проглатывать молча.
- Исключения не используются для управления обычным потоком выполнения — формализовано в `pmd.xml` (`ExceptionAsFlowControl`).

### 1.2 Кастомные исключения

- Для доменных ошибок — свои исключения в пакете `exception/`, а не исключения фреймворка. Импорт `jakarta.persistence.EntityNotFoundException` запрещён `checkstyle.xml` (`IllegalImport`); наследование прямо от `RuntimeException`/`Exception` мимо базового `FlashCardException` — `checkstyle.xml` (`MatchXpath`, id `ExceptionBase`). Здесь не дублируется.
- Кастомные исключения обрабатываются централизованно, не через `try-catch` в каждом вызывающем месте:
  - для REST-слоя — через `@RestControllerAdvice`/`@ExceptionHandler` (см. `09-controllers.md`);
  - для `consoleui` — через единый централизованный механизм показа ошибок UI-слоя (`ConsoleErrorPresenter`, см. `15-console-ui.md`), а не try-catch в каждом экране.
- Исключение бросается на границе, где обнаружена проблема (например, в `default`-методе репозитория при `orElseThrow`, см. `11-repository.md`), и не оборачивается повторно без необходимости выше по стеку.

## 2. Соглашения для агента

- В новом методе `service.impl` — `log.info` на вход и результат операции, а не только на ошибку.
- Не заводить новое исключение вне `exception/` — расширять существующую иерархию, а не начинать параллельную.
- В `consoleui` не оборачивать вызов сервиса в собственный `try-catch` — ошибки уходят в `ConsoleErrorPresenter` централизованно.
- Логируя перехваченное исключение — включать в сообщение id/параметр операции, а не только текст `e.getMessage()`.

## 3. Чек-лист

- [ ] `log.info` — на начало/конец бизнес-операции и значимые изменения состояния
- [ ] `log.warn` — на восстановимые проблемы, `log.error` — на непредвиденные ошибки
- [ ] Перехваченное исключение логируется с контекстом операции, не проглатывается молча
- [ ] Новое доменное исключение — в `exception/`
- [ ] Обработка исключений — централизованная (`@RestControllerAdvice` для REST, `ConsoleErrorPresenter` для `consoleui`), не `try-catch` в каждом месте вызова

## 4. Примеры кода

```java
@Override
public FrontWord createAndSaveFrontWord(String word) {
    log.info("Создание слова: word={}", word);

    FrontWord frontWord = new FrontWord();
    frontWord.setWord(word);
    FrontWord saved = frontWordRepository.save(frontWord);

    log.info("Слово создано: id={}", saved.getFrontWordId());
    return saved;
}
```

```java
public class FlashCardException extends RuntimeException {
    public FlashCardException(String message) {
        super(message);
    }
}

public class DuplicateEntityException extends FlashCardException {
    public DuplicateEntityException(String message) {
        super(message);
    }
}
```

## 5. Когда пересматривать

При появлении REST-слоя — правило дополняется конкретной схемой `@RestControllerAdvice` (см. `09-controllers.md`); при появлении Kafka-слоя — схемой обработки ошибок консьюмера/продюсера (см. `14-kafka.md`). Уровни логирования и базовая иерархия исключений при этом не меняются.

## 6. Известные отклонения

- Экраны, реализующие retry-цикл повторного запроса пользовательского ввода при ошибке (например, `LoginPage.run`, `AddWordManually.tryAddWordWithAutoTranslation`/`tryAddWordWithManualTranslation`, `CreateCollectionScreen.run`), ловят доменное исключение локальным `try-catch` вместо полностью централизованной обработки — это осознанное отклонение от §1.2/§2, а не упущение. Причина: без локального перехвата у экрана нет возможности решить «показать ошибку и повторить запрос ввода» — исключение, поднятое до централизованного обработчика, закрывает весь экран вместо повтора. Показ ошибки при этом всё равно остаётся централизованным — экран передаёт исключение в `ConsoleErrorPresenter.showError(gui, exception)`, не рисует диалог сам (см. `15-console-ui.md` §6).
- `ChangePasswordScreen.run` расширяет этот же паттерн до multi-catch сразу на 4 типа доменных исключений в одной ветке (`InvalidCredentialsException`, `PasswordConfirmationMismatchException`, `PasswordUnchangedException`, `PasswordTooShortException`) — операция смены пароля проверяет несколько независимых условий, каждое со своим исключением, а повторный запрос ввода при любом из них нужен один и тот же. Принцип и причина отклонения те же, что и выше: multi-catch здесь не о накоплении разнородных перехватов, а о том, что все 4 исключения ведут к одному и тому же действию — показать ошибку и повторить форму.
