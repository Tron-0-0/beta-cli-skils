# Соглашение: Liquibase / изменения схемы БД

**Когда читать:** при добавлении новой таблицы, колонки, constraint'а — любом изменении схемы БД.

**Что описывает:** структуру директорий миграций, формат имени файла, формат Liquibase formatted SQL, именование колонок/ключей.

---

## 1. Правило

### 1.1 Структура директорий

```
db/changelog/
├── db.changelog-master.xml           ← корневой changelog, подключает changelog'и версий
└── v1.0.0/                           ← папка релизной версии
    ├── change_log_version_1.xml      ← changelog версии, подключает миграции этой версии
    ├── front_word/                   ← подпапка на таблицу — только если таблица менялась в этой версии
    │   └── ...sql
    ├── card/
    │   └── ...sql
    └── student/
        └── ...sql
```

- Корневой `db.changelog-master.xml` не содержит миграций напрямую — только `<include>` на changelog каждой релизной версии.
- Каждая релизная версия — своя папка (`v1.0.0`, `v1.1.0`, ...) со своим changelog-файлом версии, который подключает через `<include>` миграции этой версии.
- Внутри папки версии — подпапка на каждую таблицу, которая менялась **в этой версии**. Если в рамках версии таблица не менялась — подпапки для неё в этой версии нет (она просто не создаётся, а не остаётся пустой).
- Новый changeset подключается через `<include file="..." relativeToChangelogFile="true"/>` в changelog нужной версии, в конец списка `<include>`.
- Существующие changeset'ы и файлы changelog'ов версий никогда не редактируются и не удаляются — только добавление нового файла миграции и нового `<include>`.

### 1.2 Имя файла миграции

- Формат `DD-MM-YYYY_NN_описание-через-дефис.sql` (например, `23-04-2025_01_add-field-and-constrain-for-user.sql`) формализован в `checkstyle.xml` (`RegexpOnFilename`, id `SqlName`), здесь не дублируется. Файлы, созданные раньше в формате `YYYY-MM-DD_NN_...`, не переименовываются задним числом — они перечислены поимённо в `checkstyle-suppressions.xml`, новые файлы в старом формате сборку не пройдут.
- `NN` — порядковый номер за день (`01`, `02`, ...), на случай нескольких changeset'ов одной таблицы в один день.
- Описание — на английском, кратко отражает суть изменения (`init-migration`, `add-field-<field>`, `add-field-and-constrain-for-user`).

### 1.3 Формат файла (Liquibase formatted SQL)

- Первые две строки (`--liquibase formatted sql` и `--changeset id:...`) и наличие хотя бы одной строки `--rollback` формализованы в `checkstyle.xml` (`RegexpHeader`, `RegexpMultiline` id `SqlRollback`), здесь не дублируются.
- Значение `id` — `<имя-файла-без-расширения>_<table>`: совпадает с именем файла миграции (без `.sql`) с припиской имени таблицы, для которой написан changeset. Это делает id уникальным глобально, а не только в рамках файла changelog'а. Линтер проверяет только наличие `id`, соответствие имени файла — смысловое ревью.
- Тело — обычный SQL (`CREATE TABLE`, `ALTER TABLE` и т.д.), с отступами и выровненными именами колонок для читаемости в `CREATE TABLE`.
- Блок `--rollback` — в конце файла, одна инструкция на строку, откатывает именно то, что делает changeset, в обратном порядке (например: сначала `DROP CONSTRAINT`, потом `DROP COLUMN`).

### 1.4 Именование колонок и ключей

- PK-колонка: `<table>_id`, тип `UUID` (см. `03-naming.md`).
- FK-колонка в БД: `<referenced_table>_id` (в Java-коде сущности при этом поле называется без `id`, см. `03-naming.md`).
- Имя constraint для FK: `fk_<referenced_table>_id` (или `fk_<referenced_table>`, если однозначно понятно из контекста таблицы).

### 1.5 Прочее

- Один changeset — одно логическое изменение (одна новая таблица, или одно добавление колонки/constraint), не смешивать несвязанные правки в одном файле.
- `IF EXISTS`/`IF NOT EXISTS` в `--rollback`-инструкциях (чтобы повторный откат не падал на уже отсутствующем объекте) формализовано в `checkstyle.xml` (`RegexpSingleline`, id `SqlRollbackIfExists`).

## 2. Соглашения для агента

- Перед созданием новой миграции — определить актуальную папку версии (последнюю существующую `vX.Y.Z`, если версия ещё не зафиксирована как выпущенная, иначе — завести новую) и подпапку таблицы (создать, если для этой таблицы в этой версии её ещё нет).
- Никогда не редактировать уже существующий файл миграции или существующий `<include>` — только добавлять новый файл и новую строку `<include>` в конец списка.
- Rollback каждого нового changeset'а откатывает именно его изменения, в обратном порядке.
- `changeset id` формировать по шаблону из §1.3 (имя файла + таблица), не по свободной схеме.

## 3. Чек-лист

- [ ] Файл лежит в `db/changelog/vX.Y.Z/<table>/`, папка таблицы создана только если таблица менялась в этой версии
- [ ] `changeset id` — `<имя-файла>_<table>`
- [ ] Блок `--rollback` в конце файла откатывает изменения в обратном порядке
- [ ] Changeset подключён через `<include relativeToChangelogFile="true"/>` в конец списка соответствующего changelog версии
- [ ] Ни один существующий файл миграции/`<include>` не отредактирован
- [ ] PK/FK-колонки и имя FK-constraint именованы по `03-naming.md`

## 4. Примеры кода

```sql
--liquibase formatted sql
--changeset id:23-04-2025_01_add-field-and-constrain-for-user_front_word

ALTER TABLE front_word ADD COLUMN student_id uuid;
ALTER TABLE front_word ADD CONSTRAINT fk_student FOREIGN KEY (student_id) REFERENCES student(student_id);

--rollback ALTER TABLE front_word DROP CONSTRAINT IF EXISTS fk_student;
--rollback ALTER TABLE front_word DROP COLUMN IF EXISTS student_id;
```

## 5. Когда пересматривать

При переходе на новую релизную версию со сменой схемы версионирования (например, отказ от подпапок per-таблица в пользу подпапок per-фича), либо при переходе с Liquibase на другой инструмент миграций — тогда правило полностью переписывается под новый инструмент, а не патчится точечно.
