# Правила написания кода — flash_card

Каноничный источник правил для проекта `flash_card` (Spring Boot, Lanterna, Java 23, PostgreSQL, Liquibase, Lombok). Читать перед тем, как писать или менять код. Одно правило — один файл: описание, обоснование, конкретные соглашения для агента, чек-лист самопроверки и примеры кода на реальных классах проекта (`FrontWord`, `Student`, `Card`, `BackWord`).

## Приоритет

1. **Это файл и файлы, на которые он ссылается** — обязательны для любого нового или изменяемого кода в проекте.
2. **`CLAUDE.md` в корне проекта** — задаёт общий контекст (архитектура, домен, пайплайн задач); там, где `CLAUDE.md` касается стиля кода, он ссылается сюда, а не дублирует правило. Если формулировки расходятся — актуальны файлы из этой директории, `CLAUDE.md` следует поправить под них, а не наоборот.
3. **Локальные исключения** — если код осознанно отклоняется от правила (унаследованный код, временное решение), это фиксируется в самом файле правила отдельным разделом «Известные отклонения» (см. `align-with-rules`), а не молчаливым расхождением.

## Что проверяется линтером

Механически проверяемые правила вынесены в конфигурацию сборки (`./mvnw clean verify`, шаг `run-quality-gate`) и в тексте файлов этой директории не дублируются — на их месте стоит короткая заметка-указатель на модуль:

- `spotless-format.xml` + `spotless-maven-plugin` в `pom.xml` — форматирование, порядок и удаление неиспользуемых импортов;
- `checkstyle.xml` — именование, Javadoc, размеры и вложенность, импорты, `MatchXpath`-проверки аннотаций, формат миграций Liquibase;
- `import-control.xml` — направление зависимостей между слоями (модуль `ImportControl`);
- `checkstyle-suppressions.xml` — осознанные исключения из проверок Checkstyle (legacy-миграции, методы репозиториев, `WindowPresenter`);
- `pmd.xml` — статический анализ (PMD) по delombok-исходникам.

## Как применять

- При написании нового кода — сначала найди файл по теме в таблице выше, затем — похожий существующий класс в проекте (см. `10-general-principles.md`) и следуй обоим.
- Автоматическая сверка уже написанного кода с этими правилами — через скилл [`align-with-rules`](../skills/align-with-rules/SKILL.md), шестой шаг пайплайна разработки.
- У каждого файла этой директории (включая этот индекс) есть frontmatter `paths`: Claude Code подгружает файл в контекст автоматически, только когда читает файл из его зоны (например, `11-repository.md` — при чтении класса из `repository/`), а не в каждую сессию. Файлов без `paths` здесь быть не должно — такой файл грузился бы безусловно. Обоснование — в `CLAUDE.md`.
- Автозагрузка — страховка, а не замена явного чтения: при создании нового файла без чтения соседних правило не подтянется, поэтому скиллы пайплайна (`code-writer`, `execute-plan`, `align-with-rules`) по-прежнему читают нужные файлы явно.

## Как обновлять

- Правило меняется вместе с кодом: если решение в PR осознанно расходится с текущей формулировкой — сначала поправь файл правила (или зафиксируй отклонение), потом пиши код по нему, а не наоборот.
- Файлы-«заготовки» переводятся из планового состояния в проверяемое по факту появления первого класса в соответствующем слое (первый `@RestController` → `09-controllers.md` начинает применяться в `align-with-rules` наравне с остальными).
- При появлении новой темы, не покрытой существующими файлами (новый внешний интеграционный слой, новая технология хранения) — новый файл по той же структуре, с frontmatter `paths` под зону применения и с добавлением строки в таблицу выше.
- Если пункт правила удаётся формализовать в линтере — правило переносится в конфигурацию сборки, а в тексте остаётся заметка-указатель; файл, формализованный полностью, удаляется.
