# /spec-increment-review — Ревью инкремента без правок кода

Полностью локальное ревью текущей ветки относительно базовой: загрузка всех артефактов инкремента,
сверка diff с чек-листом реализации, сборка, тесты/lint, проверка ФМД-атрибутов
и ручной разбор diff на предмет багов. Код не меняется — единственный результат работы с файловой
системой это отчёт в `specification/increment/{release}/{KEY}/review-report.md`.

Артефакты инкремента хранятся по пути `specification/increment/<release>/<ticket>/`:
- `increment.md` — план инкремента (генерируется spec-increment-from-task)
- `implementation-plan.md` — технический план реализации (генерируется spec-increment-plan)
- `implementation-report.md` — отчёт о реализации (генерируется spec-increment-implement)
- `review-report.md` — отчёт ревью (генерируется spec-increment-review)

Service-rules — локальные конвенции проекта, лежащие в `.gigacode/service-rules/`.
Список правил и их маппинг на тип файлов — в `00_index.md` (единственный источник правды).

**Использование:** `/spec-increment-review master` | `/spec-increment-review develop`

Аргумент — имя **уже существующей локально** ветки (или другого ref), с которой сравнивается
текущая ветка.

## Важно

- **Gate-check:** не выполняй шаги, если не выполнен предыдущий шаг pipeline. Проверка gate-артефактов — Шаг 0.5.
- **Пропуск шагов** запрещён, кроме `--skip-gate-checks` (только для отладки).
- **Не исправляй код, не коммить, не пуш.** Даже очевидные однострочные баги — этот скилл только читает код и пишет отчёт.
- **Не переключай ветки.** Ни `git checkout`, ни `git switch`, ни `git worktree add`. Скилл работает в том состоянии рабочей копии, в котором был запущен, включая незакоммиченные изменения.
- **Не обращайся к удалённому репозиторию.** Ни `git fetch`, ни `git pull`, ни `git push`, ни запросы к API Gitverse. Если базовая ветка отсутствует локально — останови выполнение и сообщи пользователю.
- **Артефакты инкремента** (increment.md, implementation-plan.md, implementation-report.md) загружаются на шаге 1.5 и используются как основной источник критериев приёмки для ручного ревью (Шаг 5).
- Если `implementation-plan.md` не найден — ревью проводится по коду и `increment.md`.
- Если `implementation-report.md` не найден — gate-check не пройден (Шаг 0.5).
- **Релевантные service-rules** определяются автоматически на шаге 1.6 по типу содержимого изменённых файлов. Используются описания правил из `.gigacode/service-rules/00_index.md` — единственного источника правды.
- Результаты проверки конвенций добавляются в раздел "Соответствие service-rules" отчёта (Шаг 6).
- Известные отклонения проекта (GAP/deviation из 00_index.md) не блокируют вердикт, но фиксируются.
- Генерирует `review-report.md` после шага 6.
- После успешной проверки ФМД — удаляет `fdm_check.json`.
- Если сборка/lint не запускались из-за отсутствия изменений — это не находка и не блокирует итоговый вердикт.

## Шаг 0. Проверить окружение

1. `git rev-parse --abbrev-ref HEAD` — определить текущую ветку. Если HEAD в состоянии detached —
   сообщи пользователю и уточни контекст, прежде чем продолжать.
2. `git rev-parse --verify --quiet refs/heads/<аргумент>` — убедиться, что базовая ветка есть
   локально (если это не ветка, а тег/коммит — проверь соответствующим способом). Нет — стоп,
   попроси пользователя получить её вручную (`git fetch`/`git branch`); сам этого не делай.
3. `git status --short` — зафиксировать, есть ли незакоммиченные изменения. Они входят в объём
   ревью наравне с закоммиченными.

## Шаг 0.5. Gate-check: проверить implementation-report.md

> ⛔ **НЕ выполняй шаги 1–5, если gate-check не пройден.**

1. Определить `{release}` и `{ticket}`:
    - Сначала проверить аргументы вызова
    - Если аргументы не переданы — извлечь из имени текущей ветки: `feature/{KEY}` или `bugfix/{KEY}` → `{KEY}`
    - `{release}` — определить из названия папки `specification/increment/{release}/`

2. Найти `implementation-report.md`:
    - `Glob specification/increment/{release}/{ticket}/implementation-report.md`
    - Если файл **не найден** → **стоп**:
      ```
      ⛔ Пропущен(ы) шаг(и) pipeline-конвейера.
 
      Не выполнен Шаг 3 (spec-increment-implement): файл implementation-report.md не найден.
      Требует выполнения: `/spec-increment-implement <тикет>`
 
      Выполните пропущенный шаг, затем повторите запуск.
      ```
    - Если файл **найден** — прочитать раздел `**Статус выполнения**` в `implementation-report.md`:
        - **"✅ Выполнен"** → продолжить к шагу 3
        - **"❌ Провал"** → **стоп**:
          ```
          ⛔ Пропущен(ы) шаг(и) pipeline-конвейера.
   
          Шаг 3 (spec-increment-implement) завершён со статусом "Провал".
          Найдены критичные проблемы при реализации. Сначала исправьте найденные проблемы.
          ```

3. Проверить, что код в текущей ветке изменён:
    - `git diff --name-only <базовая_ветка>` — список изменённых файлов
    - Если список **пустой** → **стоп**:
      ```
      ⛔ Пропущен(ы) шаг(и) pipeline-конвейера.
 
      В текущей ветке нет изменённых файлов. Код должен быть реализован.
      Сначала выполните: `/spec-increment-implement <тикет>`
      ```

5. Если gate-check пройден → продолжить к шагу 1

## Шаг 1. Определить инкремент и подготовить diff

1. `BASE=$(git merge-base <аргумент> HEAD)`
2. Список изменённых файлов: `git diff --name-only $BASE` (сравнение с рабочим деревом — включает
   незакоммиченные изменения поверх HEAD)
3. Полный diff для чтения: `git diff $BASE` (при большом объёме — читай по файлам/группам файлов)
4. Извлеки ключ задачи из имени текущей ветки: `feature/{KEY}` или `bugfix/{KEY}` → `{KEY}`. Если
   ветка не соответствует этому шаблону — спроси у пользователя номер и название инкремента
   напрямую.
5. Найди файл(ы) плана инкремента: `Glob specification/increment/*/{KEY}/increment.md`
   (и `specification/increment/*/{KEY}.md` на случай старого формата без релиза).
    - **0 совпадений** — спроси у пользователя название инкремента для имени файла отчёта; сверяться
      с планом будет не с чем, ревью в шаге 5 опирается только на код.
    - **1 совпадение** — используй его как план для сверки.
    - **2+ совпадений** — выбери файл, чья секция "Затронутые файлы" сильнее всего пересекается со
      списком изменённых файлов из шага 1.2. При равном пересечении — уточни у пользователя через
      `AskUserQuestion`.
6. "Номер инкремента" = `{KEY}`. "Название инкремента" = слаг из имени выбранного файла (часть
   после `{KEY}-` и до `.md`).

## Шаг 1.5. Загрузить все артефакты инкремента

> Загрузить и проанализировать все три файла инкремента для использования в ревью (Шаг 5).

### 1.5.1. increment.md

Найти `specification/increment/{release}/{ticket}/increment.md` (тот же файл, что найден на шаге 1.5).

Прочитать и извлечь:

- **"## Изменения в коде"** — какие точки изменений заявлены (БД-миграция, Entity, Repository,
  Service, Controller, MapStruct, DTO). Сверить с фактическим diff из шага 1.2: все ли точки
  отражены в изменённых файлах.
- **"## Цель"** — конкретное проверяемое описание результата. Использовать как критерий для
  проверки достижения цели в отчёте.
- **"## Совместимость"** — поведение для существующих данных. Что нельзя сломать при реализации.
- **"## Затронутые файлы"** — заполненный список файлов (уже проверен в gate-check);
  сверить с `git diff --name-only` на предмет расхождений.

**Результат:**
- Если секции пусты или не найдены — зафиксировать: "increment.md: секция 'X' отсутствует".
- Расхождения между заявленным и фактическим diff — вынести в отчёт.

### 1.5.2. implementation-plan.md

Найти `specification/increment/{release}/{ticket}/implementation-plan.md`:
- `Glob specification/increment/{release}/{ticket}/implementation-plan.md`

**Если файл не найден** — зафиксировать в отчёте:
```
implementation-plan.md не найден. Ревью проводится по коду и increment.md.
```
И продолжить к пункту 1.5.3.

**Если файл найден** — прочитать и извлечь:

- **"## Чек-лист реализации"** — каждый пункт чек-листа проверить в diff. Если пункт не найден
  в коде — зафиксировать как "пункт чек-листа не реализован".
- **"## Детальные изменения по слоям"** — по каждому подуровню (БД-миграция, Entity, Repository,
  Service/impl, Controller, MapStruct-мапперы, DTO, Enum-ы):
    - Проверить что соответствующие файлы изменены/созданы в diff.
    - Проверить что реализация соответствует заявленным именам классов, методов, полей.
    - Если расхождение — зафиксировать в отчёте как "Расхождение по слою {слой}: заявлено — {X}, фактически — {Y}".
- **"## Целевое состояние"** — конкретное описание "after" с именами классов и методов.
  Сверить что реализовано.
- **"## Расхождения с increment.md"** — если в плане уже зафиксированы расхождения с
  increment.md — зафиксировать их в отчёте.

### 1.5.3. implementation-report.md

Найти `specification/increment/{release}/{ticket}/implementation-report.md`
(тот же файл, что проверен в gate-check).

Прочитать и извлечь:

- **"Изменённые файлы"** — сверить список файлов из отчёта с `git diff --name-only` из шага 1.2.
  Если есть расхождения (файлы в отчёте нет в diff или наоборот) — зафиксировать.
- **"Компиляция"** — результат из отчёта. Если компиляция была успешна — в шаге 2 можно
  пропустить запуск `mvn compile` (но при желании запустить для уверенности).
- **"Проблемы"** — если в отчёте есть описание ошибок/предупреждений — зафиксировать в отчёте
  ревью и проанализировать в шаге 5.

## Шаг 1.6. Определить релевантные service-rules

Прочитать `.gigacode/service-rules/00_index.md` — он содержит таблицу всех доступных правил.
Правила могут быть добавлены или изменены, поэтому индекс — единственный источник правды.

По списку изменённых файлов (шаг 1.2) определить релевантные правила **по типу содержимого**,
а не по путям:

| Что затронуто в diff | Релевантные правила (определяются по заголовку/кратко из 00_index.md) |
|----------------------|---------------------------------------------------------------------|
| SQL / DDL / Liquibase (чейнджлоги, migration-файлы) | `03_migrations.md` |
| Java-код сервисов, контроллеров, репозиториев | `01_coding.md` |
| Денежные/числовые поля (в Java-коде, DTO, DDL) | `13_monetary.md` |
| Логирование (`@Slf4j`, log-вызовы, logback-конфиг) | `09_logging.md` |
| Java-классы (enum, константы) | `17_enums_over_constants.md` |
| Entity, JPA-аннотации, маппинги | `08_database.md` |
| Конфиг-файлы (`application.*`, `feign.*`, `logback.*`) | `12_configuration.md` |
| `pom.xml`, `build.gradle` | `04_compilation.md` |
| Тесты (`*Test.java`) | `06_unit_tests_with_spring_context.md` |
| REST-контроллеры, swagger-документация | `07_api_contract.md` |
| Refactoring-паттерны (дублирование, длина методов/классов) | `16_refactoring.md` |
| Metrics, monitors, actuator | `02_monitors.md` |
| Dockerfile, K8s-манифесты, helm | `10_cloud_native.md` |
| Kafka-классы, `KafkaTemplate`, `@KafkaListener` | `11_kafka.md` |
| REST-идемпотентность, `@Idempotency` | `14_idempotency_rest.md` |

**Как определить тип файла:**
- По расширению: `.sql`, `.xml` (liquibase), `.properties`, `.yaml`
- По имени класса в Java-файлах: ищутся `@Entity`, `@Service`, `@Controller`, `enum`, `Slf4j`
- По содержимому: `pom.xml` → билд-файл; `logback*` → конфиг логирования; `*Test.java` → тесты
- Если файл не подходит ни под один тип — он игнорируется

**Результат:**
- Список релевантных правил в формате `{filename}: {краткое_описание_из_00_index}`.
- Для каждого правила отметить статус из 00_index.md: `✅ compliant` / `⚠️ deviation` / `❌ GAP` / `N/A`.
- Deviations и GAP — не блокировать, но помнить что это известное отклонение проекта.

Отдай список пользователю правил, которые будешь использовать при ревью кода. Спроси, устраивают они его или нет.

## Шаг 2. Компиляция backend

Если среди изменённых файлов (шаг 1.2) есть пути в `objects/` или `objects-rest-client/`, переходим к шагу 2.0. Если нету, то пропускаем этот шаг.

### Шаг 2.0. Запустить сборщик ошибок

> ⚠️ **ВАЖНО:** Всегда запускай **скрипт** `batch_fix_compilation.py` — он корректно парсит ошибки Java + Checkstyle и работает на Windows. **НЕ запускай `mvn compile` напрямую.**

1. **Всегда в первую очередь запускать скрипт:**
   ```
   python .gigacode\skills\spec-increment-review\scripts\batch_fix_compilation.py
   ```
   Скрипт запускает `mvn compile -am`, парсит все ошибки (javac + checkstyle), выдаёт структурированный отчёт.

2. Если `SUM: 0 errors` → переходить к **Шагу 5 (ручное ревью)**.

3. Если `SUM: N errors` → читать отчёт, исправлять ошибки, повторять запуск скрипта.

### Шаг 2.1. Исправление ошибок

По ошибкам из отчёта скрипта:

1. **Импорты** (`package ... does not exist`, `cannot find symbol: class X`) → добавить/исправить import.
2. **Синтаксис** (`mismatched input`, `';' expected`) → исправить синтаксическую ошибку.
3. **Сигнатуры** (`incompatible types`, `cannot find symbol: method X(...)`) → исправить типы/сигнатуры.
4. **Тесты** → править **только для восстановления компиляции** (сигнатуры, импорты, удалённые методы). Писать новые тесты — зона `spec-increment-test`.
5. **Если исправление меняет бизнес-логику** → показать пользователю diff, ждать одобрения.

### Шаг 2.2. Цикл исправления

```
run_shell_command("python .gigacode\skills\spec-increment-review\scripts\batch_fix_compilation.py")
→ прочитать stdout
→ исправить ошибки
→ run_shell_command(...) снова
→ пока SUM: 0 errors
```

Если компиляция не проходит и контекст почти заполнен (~90%):
- Сгенерировать `implementation-review.md` с результатом.
- Отметить статус: **❌ Требует доработки**.
- Указать: "Следующий шаг не запускать до исправления компиляции".
- **Не менять `Статус` файла инкремента** — остаётся `К выполнению`.
- Остановить выполнение.

### Если реальность разошлась с планом
- Точечно поправь разделы "Изменения в коде"/"Совместимость" файла инкремента.
- Если расхождение существенное (меняет объём или подход) — остановись и уточни у пользователя.

## Шаг 4. Сгенерировать `implementation-report.md`

> ⚠️ `implementation-report.md` — **gate-артефакт** для последующих шагов pipeline:
> spec-increment-review (Шаг 5) и spec-increment-test (Шаг 6). Если файл отсутствует или пуст — следующие шаги не выполняются.

Создать файл `specification/increment/{release}/{ticket}/implementation-report.md` со следующими разделами:

| Раздел | Описание |
|--------|----------|
| **Общая информация** | Номер/путь инкремента, {release}, {ticket}, дата/время выполнения |
| **Статус выполнения** | ✅ Выполнен / ❌ Провал |
| **Изменённые файлы** | Список созданных/изменённых файлов (код, миграции, заполненный раздел "Затронутые файлы" в `increment.md`) |
| **Компиляция** | Результат `mvn compile` (или `mvn -pl objects compile`) |
| **Проблемы** | Описание ошибок компиляции, предупреждений, блокирующих факторов |

## Шаг 3. Проверка ФМД-атрибутов

Если среди изменённых файлов есть пути, относящиеся к миграциям БД — `db/changelog/**`,
`**/db/changelog/**`, `**/migrations/**` или корневой `pom.xml` (может затрагивать плагин),
выполни проверку ФМД-атрибутов через `core-fdm-plugin`.

### 3.1. Определить версию плагина

Использовать версию `1.5.0`:
```
ru.sbrf.sbererp.core.plugin:core-fdm-plugin:1.5.0:validate@fdm-validate
```

Если проверка **не проходит** (код != 0) — спросить у пользователя, использовать ли
другую версию. Если пользователь ввёл новую версию — использовать её для текущего запуска
и сохранить для будущих (заменить `1.5.0` на новую).

### 3.2. Запустить команду проверки

**Важно:** `core-fdm-plugin` подключён в профиле `migration`. Обязательный флаг: `-Pmigration`.

```bash
mvn ru.sbrf.sbererp.core.plugin:core-fdm-plugin:1.5.0:validate@fdm-validate \
    -DattributesFile=/home/jenkins/agent/workspace/ofitcontr_PR-build-objects_PR-43/service/fdm-attributes.json \
    -Pmigration -Pnexus \
    -DoutputFile=fdm_check.json \
    -DfailOnError=true \
    -DgitBranch=<текущая_ветка> \
    -Dmaven.wagon.http.ssl.insecure=true \
    -Dmaven.wagon.http.ssl.allowall=true \
    -Dmaven.wagon.http.ssl.ignore.validity.dates=true \
    -Dmaven.resolver.transport=wagon
```

**Параметры:**
- `-Pmigration` — **обязательно**, плагин определён в профиле `migration`
- `-Pnexus` — репозиторий Nexus (если требуется для загрузки плагина)
- `fdm-attributes.json` — файл атрибутов ФМД (из шага 3.1)

### 3.3. Проанализировать результат

    - **Удалить** `fdm_check.json` (очистка после успешной проверки)
    - Зафиксировать в отчёте: "✅ ФМД-атрибуты валидны".
- **Провал** — команда завершилась с кодом != 0 или `fdm_check.json` содержит ошибки:
    - **НЕ удалять** `fdm_check.json` — нужен для анализа
    - Прочитать `fdm_check.json` целиком.
    - Извлечь список обнаруженных проблем (несоответствия атрибутов, отсутствующие таблицы,
      неверные типы и т.п.).
    - Зафиксировать в отчёте: "❌ Найдены проблемы ФМД-атрибутов", перечислить каждую проблему
      с файлом, атрибутом и описанием расхождения.

## Шаг 5. Ручное ревью diff

Прочитай каждый изменённый файл **целиком**, а не только hunks из diff — контекст вокруг
изменений часто скрывает баг, не видимый в самом diff. Сверяйся с планом инкремента из шага 1.5,
если он найден. Ищи корректностные баги — то, что реально ломается на конкретных входных
данных/состояниях, а не стилистические предпочтения:

### Файлы, игнорируемые при ревью

Следующие файлы игнорируются — не анализируются на предмет багов и не учитываются в
результате ревью (включая секцию «Изменённые файлы» в отчёте):

- `.run/*.xml` — конфигурации IDEA для запуска (локальные настройки разработчика, не влияют
  на корректность кода)
- `objects/src/main/resources/feign.properties` — настройки SSL для локального запуска через
  `spring.config.activate.on-profile=local`, не влияют на production-корректность

### Что искать

- Логические ошибки, гонки состояний, неверные условия
- Расхождения с планом инкремента (заявленное поведение не реализовано или реализовано иначе)
- Мёртвый код / ветки, которые никогда не выполняются (например, эффект или callback, который
  фактически не срабатывает)
- Крайние случаи, допустимые по типам, но ломающие логику (пустые списки, null, повторный клик,
  первый рендер до загрузки данных и т.п.)

### Семантика методов

- Сигнатуры методов согласованы между вызовом и реализацией (нет рассинхрона параметров).
- Если метод возвращает `Optional`/`List`/коллекцию — проверь, что вызывающий обрабатывает
  пустой случай (null, empty).
- Публичные API-контракты (контроллер → сервис) не ломаются без обновления спецификации.

Каждую находку подтверждай чтением реального кода — не сообщай о баге, в которой не уверен на
100% после перепроверки. Второстепенные замечания (упрощение, переиспользование, эффективность,
конвенции, которые не блокируют работу) выноси отдельным списком с пометкой "не блокирует".

**Куда добавлять:**
- **Блокирующие** (ломается работоспособность) → раздел "Находки"
- **Второстепенные** (конвенция/стиль, не блокирует) → раздел "Второстепенные замечания"

## Шаг 5.5. Проверка соответствия service-rules

Для каждого релевантного правила из шага 1.6 проверить изменённый код. Использовать правила как правила из папки /rules. Это конвенция проекта, написанный код, ОБЯЗАТЕЛЬНО должен им следовать.

**Общий подход к проверке:**
- Если файл изменён — проверить на соответствие правилам.
- Если файл НЕ был изменён — правило к нему неприменимо (пропускать).
- Если правило имеет статус `deviation`/`GAP` в 00_index.md — это **известное отклонение проекта**:
    - Если новый код следует тому же паттерну, что и существующий — ✅ (соответствует конвенции проекта)
    - Если новый код ломает и существующий паттерн — ⚠️ (необходимо зафиксировать, но не блокировать)
- Если правило имеет статус `✅ compliant` — это **действующая конвенция**:
    - Нарушение → ❌ (блокирующая находка)

**ПРИМЕРЫ проверок по ключевым правилам:**

- **03_migrations.md:** версионирование = версия из pom.xml? formatted SQL + `--changeset id:` +
  `COMMENT ON` + `--rollback`?
- **01_coding.md:** DI через `@RequiredArgsConstructor` + `private final`? MapStruct со
  `StrictMapperConfiguration`? Форматирование вызовов?
- **13_monetary.md:** все денежные поля — `BigDecimal` (нет `double`/`float`)?
- **09_logging.md:** используется `@Slf4j`? Строки форматирования через `{}`?
- **16_refactoring.md:** нет дублирования кода между сервисами? методы ≤30 строк?
- **17_enums_over_constants.md:** типы/статусы/коды ошибок — через `enum`?

**Результат:**
- Каждая проверка: ✅ пройдено / ⚠️ deviation (известное) / ❌ нарушение.
- ❌ Нарушения → блокирующие находки (раздел "Находки").
- ⚠️ Deviations → второстепенные замечания (в отчёте отметить "известное отклонение проекта").
