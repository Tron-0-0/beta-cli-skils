# Формирование плана реализации (intent + system-intent → plan)

Третий этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → `form-plan` → [`execute-plan`](../execute-plan/SKILL.md) → [`run-quality-gate`](../run-quality-gate/SKILL.md) → [`align-with-rules`](../align-with-rules/SKILL.md) → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → [`finish-task`](../finish-task/SKILL.md).

Этот скилл только планирует. Не создавай и не редактируй файлы кода на этом шаге — соблазн "заодно уже и написать" ломает пайплайн: план должен быть чем-то, что пользователь может прочитать и одобрить до того, как начнётся реализация (как Plan Mode).

`intent.md` от `form-intent` и `system-intent.md` от `form-system-intent` намеренно написаны на уровне бизнеса и системы — описывают цель/скоуп/критерии готовности, процесс/алгоритм и связь с `specification/`, но не называют классы, пакеты или слои. Именно этот скилл впервые переводит намерение в термины кода: какие слои проекта (определи по факту `src/main/java` — например `controller`/`service`/`repository`/`entity` для backend-сервиса, либо другая слоистая структура, если проект устроен иначе) и какие конкретные/новые классы участвуют, опираясь на раздел "Процесс / алгоритм" из `system-intent.md` и на архитектуру проекта.

## Порядок действий

1. Определи директорию задачи (та же логика, что в `form-intent`):
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```

2. Прочитай `$TASK_DIR/intent.md`. Если файла нет — прежде чем считать, что `form-intent` не выполнялся, проверь, не осталась ли задача в другой ветке: поищи `intent.md` в `specification/increment/$VERSION/*/`. Если нашёлся в другой ветке — скажи пользователю, что задача велась в ветке `<найденная>`, и предложи переключиться (`git checkout <найденная>`) вместо продолжения в текущей — весь пайплайн одной задачи должен идти в одной ветке. Если нигде не нашёлся — скажи пользователю, что сначала нужно прогнать `form-intent`, и спроси, хочет ли он это сделать сейчас или дать намерение прямо в чате (для мелкой задачи это ок, но тогда зафиксируй его коротко в начале `plan.md`).

   Затем прочитай `$TASK_DIR/system-intent.md`. Если файла нет — сначала проверь, не старая ли это задача, начатая до появления шага `form-system-intent` в пайплайне (например, `plan.md` для неё уже существует — тогда системный анализ отдельным файлом ей не требуется задним числом, план и так уже был составлен). Если это новая задача без `plan.md` — скажи пользователю, что сначала нужно прогнать `form-system-intent`, и спроси, хочет ли он это сделать сейчас или дать процесс/алгоритм прямо в чате (для мелкой задачи это ок, но тогда зафиксируй его коротко в начале `plan.md`).

3. Прочитай контекст проекта, необходимый для реалистичного плана:
   - `CLAUDE.md` в корне проекта (если есть) — архитектура, слои, что уже реализовано/заготовка.
   - `.claude/rules/README.md` (индекс правил) и только те файлы правил, что реально касаются задачи — какие именно, определяй по названиям/описаниям в индексе, а не по памяти о конкретных номерах.
   - Найди в коде 1-2 похожих существующих класса того же слоя/назначения, что и то, что предстоит написать, план должен ссылаться на них как на образец.

4. Определи, какие слои и сущности затрагивает задача (слои — по факту структуры `src/main/java` этого проекта, новые миграции БД — если есть Liquibase/Flyway) — отталкиваясь от раздела "Процесс / алгоритм" в `system-intent.md`: каждый шаг описанного там процесса должен лечь на конкретный слой/класс. Это первое место в пайплайне, где идея переводится в термины кода — ни в `intent.md`, ни в `system-intent.md` этого решения ещё нет.

   Если задача проходит через 3+ слоя или содержит нетривиальную логику принятия решений — набросай короткую цепочку вызовов (точка входа → метод → метод → результат), это дешёвый способ поймать пропущенный шаг ещё на плане, а не в середине `execute-plan`. Для однослойной правки цепочка не нужна.

   Если по ходу чтения кода обнаружилось расхождение между тем, что предполагают `intent.md`/`system-intent.md` (или уже описано в `specification/`), и тем, что реально есть в коде — зафиксируй это явно в `plan.md` (раздел "Расхождения с intent.md" в шаблоне ниже), не подгоняй план под ошибочное предположение молча.

5. Составь план: упорядоченный список конкретных шагов. Каждый шаг — это либо файл (новый/изменяемый) с кратким описанием, что в нём делается, либо миграция, либо тест. План должен явно закрывать каждый критерий готовности из `intent.md` — если какой-то критерий не покрывается ни одним шагом, это сигнал, что план неполный.

6. Если задача меняет схему БД — шаг с миграцией должен соответствовать правилу проекта для миграций из `.claude/rules/` (найди его по индексу `README.md` — обычно про Liquibase/Flyway: новый changeset, не редактирование существующих, формат имени файла и `--rollback`).

7. Запиши план в `$TASK_DIR/plan.md` по шаблону ниже.

8. Покажи план пользователю и явно спроси подтверждение — совмещённое с вопросом о завершении шага (например: «План устраивает, коммитим `plan.md`?»). Это та же точка, где дешевле всего поймать неверный подход, и точка коммита одновременно. При отрицательном ответе — не коммитить, доработать план по замечаниям и спросить снова. При положительном — обнови `$TASK_DIR/pipeline-state.md` (`form-plan` → `завершён`, `Текущий шаг` → `execute-plan`) и закоммить его вместе с `plan.md` отдельным коммитом, по аналогии с `intent.md` ([`form-intent/SKILL.md`](../form-intent/SKILL.md), шаг 6):
   ```bash
   git add "$TASK_DIR/plan.md" "$TASK_DIR/pipeline-state.md"
   git commit -m "$(cat <<'EOF'
   Add plan: <короткое имя задачи>

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```
   Затем скажи пользователю, что следующий шаг — `execute-plan`.

## Шаблон `plan.md`

```markdown
# План реализации: <короткое имя задачи>

- Ветка: <branch> / Версия: <version>
- Основано на: intent.md, system-intent.md

## Затрагиваемые слои/сущности
<слои проекта по факту структуры (например controller / service / repository / entity), миграции БД / ... — со ссылкой на существующие похожие классы, если есть>

## Цепочка вызовов
<для задач, затрагивающих 3+ слоя: команда/точка входа → метод → метод → результат. Пропустить пункт для однослойных правок>

## Расхождения с intent.md
<где код разошёлся с предположением из intent.md/system-intent.md или specification/ — или "нет">

## Шаги реализации
1. <файл/действие> — <что делается и зачем>
2. ...

## Затронутые файлы
- Новые: ...
- Изменяемые: ...

## Миграции БД
<путь к новому changeset'у/миграции, таблица, суть изменения — или "не требуется">

## Тесты
<какие unit-тесты добавляются/обновляются, по какому классу>

## Риски и открытые вопросы
- ...

## Соответствие критериям готовности (из intent.md)
- [ ] <критерий> — закрывается шагом N
- ...
```
