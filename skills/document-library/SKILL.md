# Обзор Java-библиотеки

Превращает "чёрный ящик" зависимости в файл-справочник: не пересказ javadoc, а осмысление — зачем библиотека
нужна, как она устроена внутри и как ей реально пользуются в этом проекте. Итоговый файл должен закрывать
вопрос "как эта штука работает и как её использовать", не отправляя читателя обратно в исходники библиотеки.

## Когда НЕ использовать

Если вопрос — про код самого проекта (не внешнюю зависимость), это `specification/absolut/architecture.md`/`structure.md`,
актуализируемые через `update-spec`. Если вопрос — про язык/JDK без конкретного стороннего артефакта, обычного
объяснения в диалоге достаточно, отдельный файл не нужен.

## Порядок действий

1. **Определи Maven-координату библиотеки.**
   - Если пользователь назвал библиотеку по имени (например, "Lanterna") — найди её в `pom.xml` проекта
     (`groupId`, `artifactId`, версия — либо явная, либо унаследованная через `dependencyManagement`/parent BOM,
     тогда версию нужно выяснить через `mvn dependency:tree` или `mvn help:evaluate`).
   - Если пользователь сразу дал путь к исходникам/jar-файлу или полную координату — используй её напрямую,
     шаг 2 (получение исходников через Maven) не нужен.
   - Если библиотеки нет в `pom.xml` и пользователь не уточнил версию — спроси, какую версию имеет в виду.

2. **Получи материалы для анализа** с помощью `scripts/resolve_library_sources.sh <groupId:artifactId:version> <output_dir>`
   (запусти из scratchpad-директории сессии, не внутри проекта). Скрипт сам перебирает уровни детализации от
   лучшего к худшему и печатает `TIER=` — от него зависит, что делать дальше:
   - `TIER=sources` — читай реальный исходный код, этого достаточно для раздела "Внутренняя механика".
   - `TIER=javadoc` — есть описания API, но не тела методов; для механики "под капотом" дополни через
     WebSearch/WebFetch по официальному репозиторию/документации библиотеки — не выдумывай механику
     из одних сигнатур.
   - `TIER=bytecode` — есть только сигнатуры без какой-либо документации (см. `api-summary.txt`); в этом
     случае веб-поиск обязателен, иначе раздел "Внутренняя механика" выйдет пустым или гадательным.
   - `TIER=none` — сборка через Maven не нашла артефакт вовсе (например, он в приватном репозитории). Скажи
     об этом пользователю и предложи анализ по официальной документации/GitHub-репозиторию через WebSearch.

3. **Проверь, как библиотека реально используется в проекте** — `grep`/поиск по `src/main/java` на импорты
   этого пакета. Это важно даже когда используешь только `bytecode`/`javadoc`-уровень: реальные вызовы в коде
   проекта — самый надёжный источник примеров для раздела "Как использовать", надёжнее сгенерированных с нуля.
   Если библиотека подключена, но нигде не импортируется (как, например, `docker-java` в этом проекте на момент
   написания этого скилла) — зафиксируй это как факт, а не пытайся притянуть несуществующее использование.

4. **Заполни `specification/libraries/<artifact-id>.md`** по шаблону из `references/library-doc-template.md`.
   Раздел "Внутренняя механика" — не список методов, а объяснение, почему API спроектирован так, а не иначе:
   что происходит между вызовом метода и результатом, какие есть жизненный цикл/состояние/потоки выполнения.

5. **Обнови `specification/libraries/index.md`** (создай, если это первая задокументированная библиотека) —
   прочитай текущее содержимое файла и допиши/обнови в нём строку своей библиотеки, не перезаписывая
   остальные строки: если параллельно (например, в соседней сессии) уже добавили другую библиотеку, обе
   строки должны остаться.

6. Спроси пользователя, доволен ли он результатом, прежде чем предлагать закоммитить — как и остальные
   шаги, работающие с `specification/`, зафиксируй файлы только по его явному подтверждению.

## Файлы и их назначение

- **`specification/libraries/<artifact-id>.md`** — один файл на библиотеку: назначение, внутренняя механика,
  как использовать, нюансы. Имя файла — `artifactId` из Maven-координаты (не человекочитаемое имя), чтобы
  оно однозначно соответствовало зависимости в `pom.xml`.
- **`specification/libraries/index.md`** — таблица всех задокументированных библиотек с датами анализа.

Каждый файл начинается со строки `> Актуально на: <дата>, ветка <branch>` — при повторном запуске скилла
на той же библиотеке (например, после обновления версии) перезаписывай файл целиком, а не дописывай в конец.
