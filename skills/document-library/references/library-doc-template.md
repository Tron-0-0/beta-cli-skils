Копировать структуру, не текст-заполнитель в скобках — он объясняет, что должно оказаться в разделе,
а не то, как это должно быть сформулировано.

```markdown
> Актуально на: <дата>, ветка <branch>

# <Человекочитаемое имя библиотеки>

- **Maven-координата:** `<groupId>:<artifactId>:<version>`
- **Глубина анализа:** sources | javadoc | bytecode + веб-документация (указать, что реально было доступно)
- **Официальные источники:** ссылки на репозиторий/документацию, если использовались

## Назначение

Зачем библиотека вообще существует (проблема, которую она решает) и зачем она используется
именно в этом проекте — с указанием конкретных классов/пакетов проекта, которые её применяют.
Если библиотека подключена в pom.xml, но в коде не используется (заготовка на будущее) — сказать
это прямо, а не выдумывать применение.

## Внутренняя механика

Как библиотека устроена и работает "под капотом": ключевые абстракции, жизненный цикл объектов,
поток управления между её основными классами/интерфейсами. Это то, ради чего читались исходники,
а не просто список публичных методов — объяснить, ПОЧЕМУ API спроектирован так, а не иначе,
если это следует из механики.

## Как использовать

Типичные сценарии использования с примерами кода. Там, где библиотека уже используется в проекте —
основой примеров должен быть реальный код проекта (с указанием файла), а не выдуманный из документации.
Для сценариев, которых в проекте пока нет, но которые релевантны — общие примеры с пометкой,
что это не текущее использование.

## Нюансы и грабли

Специфичное поведение, которое легко понять неправильно: неочевидные значения по умолчанию,
требования к порядку вызовов, потокобезопасность, версионные различия API, известные ограничения.
Пустой раздел лучше, чем выдуманные "грабли" — если ничего существенного не нашлось, написать это явно.
```
