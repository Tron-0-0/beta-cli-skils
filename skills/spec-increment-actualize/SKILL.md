# /spec-increment-actualize — Актуализировать абсолютную спецификацию по инкременту

## Важно

- **Gate-check:** не выполняй шаги 1–7, если не выполнен предыдущий шаг pipeline. Проверка gate-артефактов — Шаги 0.5–0.7.
- **Пропуск шагов pipeline запрещён**, кроме `--skip-gate-checks` (только для отладки).

Финальный шаг жизненного цикла инкремента: код уже реализован и прошёл ревью — эта команда
приводит `specification/absolut/` (описание системы "как есть") в соответствие с тем, что реально
изменилось, и закрывает сам файл инкремента (`Статус: Выполнено`).

**Использование:**
```
/spec-increment-actualize specification/increment/01.023.00/AO-12/increment.md
/spec-increment-actualize AO-12
/spec-increment-actualize 01.023.00/AO-12
```

## Правила структуры `specification/absolut/` (не зависят от конкретного проекта)

- `specification/absolut/index.md` — только заголовок и список ссылок на `index.md` каждого
  раздела. Никакого обзорного текста, никаких деталей — просто навигация.
- Каждый раздел — отдельная папка `specification/absolut/{N}-{слаг}/`. Внутри — `index.md`
  (только заголовок раздела и список ссылок на файлы внутри этой папки — без описания/обзора) и
  файлы с содержанием: как правило `db.md` (схема БД), `business.md` (бизнес-логика, роли, правила,
  статусы), `api.md` (эндпоинты, DTO, коды ошибок) — но если часть материала не укладывается ни в
  одну из этих трёх тем (инфраструктура, деплой, интеграция с внешним сервисом, конфигурация CI и
  т.п.), для неё создаётся отдельный файл с содержательным именем, а не искажаются db/business/api.
- Каждый файл раздела (кроме index.md) начинается с `[← Назад](index.md)`.
- Номера разделов не переиспользуются и не сдвигаются — новый раздел получает
  `максимальный существующий номер + 1`.

## Шаг 0. Найти файл инкремента

Инкременты хранятся по пути `specification/increment/<release>/<ticket>/increment.md`.

Если `$ARGUMENTS` — существующий путь (заканчивающийся на `increment.md`), используй его
напрямую. Иначе воспринимай аргумент как:
- **номер тикета** (например `AO-12`) — ищи через `Glob specification/increment/*/{ticket}/increment.md`
- **релиз/тикет** (например `01.023.00/AO-12`) — ищи через `Glob specification/increment/{release}/{ticket}/increment.md`

Несколько кандидатов или ни одного — покажи список и уточни у пользователя.

## Шаг 0.5. Gate-check: определить режим и проверить артефакты

> ⛔ **НЕ выполняй шаги 1–7, если gate-check не пройден.**

Скилл работает в двух режимах:
- **Pipeline-режим** — все 6 артефактов pipeline присутствуют → автоматический запуск без вопросов.
- **Standalone-режим** — некоторые артефакты отсутствуют → легитимный сценарий (догоняющая актуализация
  документации для исторических инкрементов или "старый" подход без полного пайплайна). Пользователь
  подтверждает запуск.

**Важно:** Все 6 файлов являются артефактами pipeline, генерируемыми предыдущими шагами.
`increment.md` одновременно выступает артефактом (от `spec-increment-from-task`) и входным файлом
для `spec-increment-actualize`. В Шаге 0.5 проверяются все 6 артефактов. В Шаге 0.7
`increment.md` дополнительно валидируется (проверка существования + статуса).

1. `{release}` и `{ticket}` уже известны из пути файла, найденного в Шаге 0
   (`specification/increment/{release}/{ticket}/increment.md`) — переиспользовать их напрямую, не
   определять заново по аргументам вызова или имени ветки.

2. Найти все 6 артефактов в `specification/increment/{release}/{ticket}/`:
   ```
   intent.md
   increment.md
   implementation-plan.md
   implementation-report.md
   review-report.md
   test-report.md
   ```
   Для каждого выполнить `Glob specification/increment/{release}/{ticket}/{filename}`.

3. Подсчитать количество найденных артефактов (N из 6).

   **Pipeline-режим** (N == 6):
    1. Все 6 артефактов найдены
    2. Все шаги пайплайна выполнены корректно
    3. Перейти к Шагу 0.6 (проверка качества артефактов).

   **Standalone-режим** (N < 6):
    1. Вывести список найденных и пропущенных артефактов:
       ```
       ⚠️ Standalone-запуск: пропущены шаги pipeline-конвейера.
 
       Найдено артефактов: {N} из 6
 
       ✅ Найдены:
         - intent.md
         - review-report.md
 
       ❌ Пропущены:
         - implementation-plan.md
         - implementation-report.md
         - test-report.md
 
       Это легитимный сценарий (догоняющая актуализация документации для исторического
       инкремента или "старый" подход без полного пайплайна).
       Рекомендуется использовать полный pipeline для будущих инкрементов.
 
       Продолжить с актуализацией документации?
       ```
    2. Запросить подтверждение у пользователя через `AskUserQuestion`:
       ```
       Статус: ⚠️ Standalone-запуск, N из 6 артефактов найдено
       Вопрос: Продолжить актуализацию документации несмотря на пропущенные шаги pipeline?
       Варианты: [Да, продолжить] / [Нет, отменить]
       ```
    3. Если пользователь отказался → **стоп**:
       ```
       Запуск отменён пользователем.
       ```
    4. Если пользователь подтвердил:
       a. Сообщить: "✓ Подтверждено. Начинаю актуализацию документации для {release}/{ticket}."
       b. **Standalone-режим (N < 6):** Предупредить: "⚠️ В Standalone-режиме проверка качества
       артефактов (Шаг 0.6) **пропускается** — файлы могут быть неактуальными или содержать провалы.
       Рекомендуется выполнить полный pipeline."
       Затем перейти к Шагу 0.7 (валидация increment.md).
       c. **Pipeline-режим (N == 6):** Перейти к Шагу 0.6.

## Шаг 0.6. Gate-check: проверить качество артефактов (только Pipeline-режим, N == 6)

> ⛔ **НЕ выполняй шаги 1–7, если качество артефактов не подтверждено.**
> ⚠️ **Флаг `--skip-gate-checks`:** если он есть в `$ARGUMENTS` — при любом **стоп** ниже вместо
> остановки выведи `⚠️ Gate-check пропущен флагом --skip-gate-checks: {текст, который был бы в
> стопе}` и продолжай к следующей проверке/Шагу 0.7.

Этот шаг проверяет, что предыдущие шаги pipeline действительно **успешно завершены**, а не просто
создали файлы. **Применяется только в Pipeline-режиме (N == 6).** В Standalone-режиме этот шаг
пропускается (см. Шаг 0.5, пункт 4b).

1. Проверить `implementation-report.md`:
    - `read_file` → `specification/increment/{release}/{ticket}/implementation-report.md`
    - Найти раздел `**Статус выполнения**`:
        - Если **"✅ Выполнен"** → продолжить к проверке review-report.md (это единственный статус,
          который генерирует `spec-increment-implement` — сам факт наличия файла уже означает,
          что Шаг 4 завершён)
        - Любое другое значение (файл повреждён или отредактирован вручную) → **стоп**:
          ```
          ⛔ implementation-report.md содержит неожиданный статус выполнения: "{значение}".
          Ожидается "✅ Выполнен". Проверьте файл вручную или перезапустите
          `/spec-increment-implement {ticket}`.
          ```

2. Проверить `review-report.md`:
    - `read_file` → `specification/increment/{release}/{ticket}/review-report.md`
    - Найти раздел `## Итог`:
        - Если **"Требует доработки"** → **стоп**:
          ```
          ⛔ Ревью выявило проблемы.
   
          review-report.md содержит итог "Требует доработки".
          Найдены критичные баги или несоответствия.
   
          Требуется: запустить `/spec-increment-review {базовая_ветка}`
          после исправления найденных проблем.
          ```
        - Если **"Готово к мержу"** → продолжить к проверке test-report.md

3. Проверить `test-report.md`:
    - `read_file` → `specification/increment/{release}/{ticket}/test-report.md`
    - Найти раздел `## Итог`:
        - Если **"Требуют доработки"** → **стоп**:
          ```
          ⛔ Тесты провалены.
   
          test-report.md содержит итог "Требуют доработки".
          Найдены упавшие тесты или проблемы компиляции тестов.
   
          Требуется: запустить `/spec-increment-test {ticket}`
          после исправления проблем.
          ```
        - Если **"Все прошли"** → продолжить к Шагу 0.7.

## Шаг 0.7. Проверить статус инкремента в `increment.md`

> ⚠️ **Флаг `--skip-gate-checks`:** если он есть в `$ARGUMENTS` — при стопе п. 4 (инкремент уже
> завершён) вместо остановки выведи `⚠️ Gate-check пропущен флагом --skip-gate-checks: инкремент
> уже завершён (Статус: Выполнено)` и продолжай к Шагу 1. Стоп п. 2 (файл не найден) флаг
> **не отменяет** — без файла инкремента актуализировать нечего в принципе.

1. `Glob specification/increment/{release}/{ticket}/increment.md`
2. Если файл **не найден** → **стоп**:
   ```
   ⛔ Файл инкремента не найден.
   Убедитесь, что {release}/{ticket} указаны корректно.
   ```
3. Если файл **найден** — прочитать его:
   `read_file` → `specification/increment/{release}/{ticket}/increment.md`
4. Найти секцию `## Статус`:
    - Если статус = **"Выполнено"** → **стоп**:
      ```
      ⛔ Инкремент уже завершён. Статус: Выполнено.
      Актуализировать нечего.
      ```
    - Если статус ≠ "Выполнено" → продолжить к Шагу 1.

## Шаг 1. Понять, что изменилось

1. Прочитай файл инкремента целиком — разделы "Изменения в коде" и "Затронутые файлы" описывают,
   что сделано
2. Если в файле есть раздел "Обоснование решений по результатам разработки" — прочитай и его: там
   причины конкретных решений (отступления от плана, выбор между альтернативами, обход
   неочевидного поведения), которых нет ни в самом плане, ни в дифе кода. Раздела нет — это
   нормально, значит на разработке не было решений, которые стоило объяснять отдельно
3. Если "Затронутые файлы" пуст, неполон или расходится с реальностью — проверь фактическое
   состояние кода/репозитория (например, `git diff`/`git log` для этого инкремента, если история
   это позволяет), не доверяй плану вслепую
4. Разложи изменения по природе: схема БД (миграции/таблицы) — одно, HTTP/WS API (контроллеры,
   DTO) — другое, бизнес-правила/поведение/роли/статусы — третье, всё остальное (инфраструктура,
   конфиги, скиллы автоматизации, интеграции) — отдельно

## Шаг 2. Определить раздел(ы) `specification/absolut/`

1. Прочитай `specification/absolut/index.md` — список существующих разделов
2. Для каждого раздела, который может быть релевантен, прочитай его `index.md` (список файлов) и,
   при необходимости, `business.md`/`api.md`/`db.md` — пойми предметную область раздела по
   содержанию, а не по названию папки
3. Сопоставь затронутый инкрементом код с предметной областью разделов. Один инкремент может
   затрагивать несколько разделов одновременно (например, БД-миграцию в одном разделе и API в
   другом) — актуализируй каждый затронутый раздел
4. Если ни один существующий раздел не подходит по смыслу — создай новый:
    - номер = максимальный существующий номер папки `specification/absolut/*/` + 1
    - слаг и название раздела — по смыслу предметной области, в стиле уже существующих разделов
      этого проекта (посмотри их названия и папки, чтобы выдержать стиль)

Не переходи к шагу 3, если не уверен, к какому разделу отнести изменения, — лучше уточни у
пользователя, чем угадай и создай дублирующий/неверный раздел.

## Шаг 3. Обновить/создать файлы раздела

Для каждого целевого раздела:

1. Точечно обнови только то, что реально изменил инкремент — не переписывай файл целиком и не
   удаляй факты, не относящиеся к этому инкременту
2. `db.md` — таблицы/колонки/индексы/миграции; `api.md` — эндпоинты, роли доступа, DTO, коды
   ошибок; `business.md` — бизнес-правила, роли и права, статусы, доменная логика и её причины
3. Если часть изменений не укладывается ни в одну из этих тем — создай/обнови отдельный файл с
   содержательным именем (не `misc.md` — конкретное имя темы, например `deploy.md`)
4. Пиши только факты из кода/файла инкремента — не придумывай и не обобщай сверх того, что видишь
5. Причины из раздела "Обоснование решений по результатам разработки" (Шаг 1, под-пункт 2), если он был —
   вплетай рядом с фактом, который они объясняют (обычно в `business.md`), а не отдельным блоком
   и не как есть. Переноси только то, что объясняет неочевидное текущее поведение или устройство —
   не историю обсуждения и не то, что и так понятно из кода

## Шаг 4. Актуализировать `index.md` раздела

Для каждого затронутого (или только что созданного) раздела `specification/absolut/{раздел}/index.md`
должен содержать **только**:

```markdown
# Название раздела

[← Назад](../index.md)

## Содержание

- [База данных](db.md)
- [Бизнес-логика](business.md)
- [API](api.md)
```

Список — ссылки на файлы, которые **реально существуют** в этой папке сейчас (включая любые
дополнительные файлы из шага 3, не только эти три). Если в файле уже была секция вида "Обзор" с
описательным текстом — удали её: разрешено только название раздела и список ссылок.

## Шаг 5. Актуализировать `specification/absolut/index.md`

Тот же принцип — **только** заголовок и список ссылок на `index.md` всех разделов:

```markdown
# [Название проекта/спецификации]

## Содержание

1. [Название раздела 1](01-slug/index.md)
2. [Название раздела 2](02-slug/index.md)
```

Если создан новый раздел — добавь для него строку в конец списка. Не переписывай формулировки
существующих строк, если их раздел не менялся в этом инкременте.

## Шаг 6. Завершить инкремент

Если `Статус` файла инкремента ещё не `Выполнено`:
1. `Статус` → `Выполнено`
2. Дополни/уточни "Затронутые файлы" фактическим списком — код и документация вместе

## Шаг 7. Сообщить результат

Сообщи пользователю: какие разделы актуализированы (существующие — какие именно файлы; новый —
номер, название, состав файлов), и что статус инкремента закрыт.

## Ограничения

- Пиши только факты из кода/инкремента — не придумывай
- Не удаляй в файлах раздела факты, не относящиеся к текущему инкременту — актуализируй точечно
- Абсолютная спецификация фиксирует фактическое состояние системы, а не историю правок — не пиши
  в формате "было/стало" ("до этого было X, теперь Y", "раньше здесь использовался...", "до
  инкремента N делалось иначе"). Описывай только то, как это работает сейчас. Ссылка на конкретный
  файл `specification/increment/...` уместна и полезна, если она добавляет контекст, важный для
  агента при чтении абсолютной документации (например, объясняет неочевидную причину решения) — но
  сама по себе она не повод пересказывать историю изменений
- Не переименовывай и не перенумеровывай существующие разделы
- В БД-описаниях приоритет у реальных имён колонок (snake_case или аналог), а не у имён полей в
  коде приложения
- Не привязывайся к конкретным названиям разделов/технологиям — определяй структуру по
  фактическому состоянию `specification/absolut/`, а не по памяти о конкретном проекте
- Раздел "Обоснование решений по результатам разработки" в файле инкремента (если есть) — не
  переноси в абсолютную документацию дословно и отдельным блоком, а вплетай по факту рядом с
  соответствующим поведением (шаг 3.5); его отсутствие в файле инкремента — не пропуск, а сигнал,
  что объяснять было нечего
