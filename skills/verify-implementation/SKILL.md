# Проверка реализации (execution → verification report)

Седьмой этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → [`form-plan`](../form-plan/SKILL.md) → [`execute-plan`](../execute-plan/SKILL.md) → [`run-quality-gate`](../run-quality-gate/SKILL.md) → [`align-with-rules`](../align-with-rules/SKILL.md) → `verify-implementation` → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → [`finish-task`](../finish-task/SKILL.md).

Роль этого шага — независимая проверка, а не продолжение реализации. Не исправляй найденные проблемы по ходу — фиксируй их в отчёте. Смешивание проверки и исправления путает диагностику с исправлением и скрывает от пользователя реальный масштаб проблем до того, как он решит, чинить сейчас или отложить.

Полное чтение изменённых файлов и вывод от ручного запуска приложения объёмны и не должны занимать контекст основной сессии — эта часть выполняется в изолированном subagent-контексте, по аналогии с [`run-quality-gate`](../run-quality-gate/SKILL.md).

## Порядок действий

1. Определи директорию задачи:
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```

2. Прочитай `$TASK_DIR/intent.md`, `plan.md`, `execution-report.md`. Если чего-то из них нет — прежде чем считать шаг пропущенным, поищи недостающие файлы в `specification/increment/$VERSION/*/`. Если нашлись в другой ветке — скажи пользователю, что задача велась в ветке `<найденная>`, и предложи переключиться (`git checkout <найденная>`) вместо продолжения в текущей. Если файлов действительно нигде нет — скажи пользователю, каких файлов не хватает, и проверяй по тому, что есть (например, если `intent.md` не создавали для мелкой задачи — просто отметь в отчёте, что критерии готовности не формализованы).

3. Проверь, можно ли переиспользовать уже готовый результат сборки, не гоняя `./mvnw` заново — в пайплайне её уже прогонял `run-quality-gate`, а если `align-with-rules` применял правки — ещё раз он сам, на своём шаге 7. Тестов на этом шаге переиспользовать нечего — их ещё нет, они появятся только на `write-tests`. Эта проверка дешёвая и инлайновая — субагент ей не нужен:
   ```bash
   git rev-parse HEAD
   git status --porcelain -- src/
   ```

   Сначала проверь `$TASK_DIR/align-with-rules-report.md` — это более свежий источник, если он есть и применял правки к коду. Если раздел "Сборка и тесты" в нём содержит реальный результат прогона (не "код не менялся..." и не "не применимо") — найди коммит, который добавил этот файл: `git log -1 --format=%H -- "$TASK_DIR/align-with-rules-report.md"`. Если этот коммит — предок текущего `HEAD` (`git merge-base --is-ancestor <коммит> HEAD`), `git diff --quiet <коммит> HEAD -- src/` пуст, и `git status --porcelain -- src/` пуст — код в `src/` не менялся с этого прогона. Возьми результат оттуда вместо повторного прогона.

   Иначе (файла `align-with-rules-report.md` нет, его раздел "Сборка и тесты" говорит, что код не менялся или что режим самостоятельный, или `src/` менялся после него) — проверь так же `$TASK_DIR/quality-gate-report.md`: если записанный в нём коммит — предок `HEAD`, `git diff --quiet <коммит> HEAD -- src/` пуст, и `git status --porcelain -- src/` пуст — код в `src/` не менялся с момента прогона `run-quality-gate` (точное совпадение коммитов не подходит: `run-quality-gate` коммитит свой отчёт сам, поэтому `HEAD` к моменту этого шага уже ушёл вперёд минимум на этот коммит). Возьми готовый результат из раздела "Сборка" `quality-gate-report.md`.

   В обоих случаях запомни, какой отчёт и коммит переиспользован — это пойдёт в промпт субагента на следующем шаге, чтобы он не гонял сборку повторно.

   Иначе — ни один из отчётов не подходит (например, `align-with-rules` внёс правки в код и не закоммитил их) — пересборка потребуется; передай это как отдельное указание субагенту в следующем шаге (сама пересборка выполняется там же, вместе с остальной тяжёлой частью, а не отдельно здесь).

4. Тяжёлую часть проверки — код по факту, ручной запуск приложения, поиск и подтверждение багов — выполни в изолированном subagent-контексте: полные тексты изменённых файлов и вывод ручного запуска объёмны и не должны оседать в основной сессии. Вызови `Agent`:
   - `subagent_type: general-purpose`. Вызов синхронный (без `isolation`) — результат нужен сразу для записи отчёта на следующем шаге.
   - Самодостаточный промпт (агент не видит эту беседу и не помнит контекст задачи), включающий:
     - Рабочая директория — корень репозитория проекта (передай абсолютный путь `$PROJECT_ROOT`).
     - Пути к `$TASK_DIR/intent.md`, `$TASK_DIR/plan.md`, `$TASK_DIR/execution-report.md` (агент читает их сам). Если по шагу 3 сборку можно переиспользовать — передай готовый результат и коммит, откуда он взят, с указанием не гонять `./mvnw` повторно; если нужна пересборка — явно попроси сначала прогнать `./mvnw clean package -DskipTests` и зафиксировать результат.
     - Для каждого изменённого/нового файла из раздела "Изменённые/созданные файлы" `execution-report.md` — прочитать его **целиком**, а не только hunks из `git diff` (контекст вокруг изменения часто скрывает баг, не видимый в самом диффе). Файлы вида `.run/*.xml` (локальные конфигурации IDE) в проверку не входят.
     - Проверить: соответствие критериям готовности из `intent.md` (каждый пункт отдельно — выполнен / не выполнен / не проверить без ручного запуска); соответствие шагам `plan.md` (что пропущено или сделано иначе); соответствие правилам `.claude/rules/` — по красным флагам из [`code-writer.md`](../../skills/code-writer.md) (`@Autowired` на поле, `@Data` на JPA-сущности, Javadoc не на том языке, что принято в проекте, правка существующей миграции БД вместо новой, обращение верхнего слоя к репозиторию в обход сервиса) как минимальному чек-листу, плюс любые другие нарушения; логические/функциональные баги (edge-case, потенциальный NPE, неверная бизнес-логика, гонки/побочные эффекты).
     - **Обязательно запустить приложение вручную** (`./mvnw spring-boot:run` или собранный jar) — автотестов на этом шаге пайплайна ещё нет, это единственный способ подтвердить те критерии готовности, которые не закрываются одним чтением кода (например, реальное поведение экрана `consoleui/`).
     - Разделить находки на **баги** (ведут к неверному поведению или падению) и **замечания** (стилистические/архитектурные отклонения, не ломающие поведение). Каждую находку подтвердить повторным чтением реального кода перед тем, как включить в ответ — не включать находку, в которой нет уверенности на 100% после перепроверки.
     - Вернуть структурированный ответ (не полный текст прочитанных файлов и не полный вывод ручного запуска), по разделам, зеркальным шаблону `verification-report.md` ниже: результат сборки; что подтвердил ручной запуск; статус каждого критерия готовности; отклонения от плана; нарушения правил проекта; список багов (`<файл>:<строка>`, критичность, как воспроизвести); список замечаний.

5. По ответу субагента запиши `$TASK_DIR/verification-report.md` по шаблону ниже. Строку `**Готово к finish-task:**` в разделе "Итоговый вердикт" выставь сразу: `да`, если раздел "Найденные баги" — "не найдено"; `нет — есть баги без статуса, дождаться ручной правки`, если баги есть.

   Спроси пользователя, завершён ли шаг (например: «Отчёт готов, коммитим `verification-report.md`?»). При отрицательном ответе — не коммитить. При положительном — обнови `$TASK_DIR/pipeline-state.md`: `verify-implementation` → `завершён`, `Текущий шаг` → `write-tests` (если «да») либо → `ручная правка багов (без отдельного шага пайплайна)` (если «нет»). Закоммить файл отчёта вместе с `pipeline-state.md` отдельным коммитом, по аналогии с `intent.md` ([`form-intent/SKILL.md`](../form-intent/SKILL.md), шаг 6):
   ```bash
   git add "$TASK_DIR/verification-report.md" "$TASK_DIR/pipeline-state.md"
   git commit -m "$(cat <<'EOF'
   Add verification report: <короткое имя задачи>

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```

6. Дай пользователю итоговый вердикт одной фразой (готово / нужны доработки). Если раздел "Найденные баги" пуст — скажи, что следующий шаг — `write-tests`; если баги есть — скажи, что они чинятся в диалоге, без отдельного шага пайплайна, и что как только все они исправлены и `verification-report.md` обновлён (строка «Готово к finish-task» — «да»), следующий шаг — `write-tests`.

## Шаблон `verification-report.md`

```markdown
# Отчёт о проверке: <короткое имя задачи>

- Ветка: <branch> / Версия: <version>
- Основано на: execution-report.md, plan.md, intent.md

## Сборка
- `./mvnw clean package -DskipTests`: <результат> <если переиспользовано из align-with-rules-report.md или quality-gate-report.md — указать, из какого отчёта и коммит>

## Ручной запуск приложения
<что проверено запуском (./mvnw spring-boot:run / jar), какие критерии готовности это подтвердило>

## Критерии готовности (из intent.md)
- [x]/[ ] <критерий> — <комментарий>

## Соответствие плану
<что сделано не так, как в plan.md, или пропущено>

## Соответствие правилам проекта
<нарушенные правила со ссылкой на конкретный файл в .claude/rules/, или "нарушений не найдено">

## Найденные баги
1. **[критичность: высокая/средняя/низкая]** <описание> — `<файл>:<строка>` — <как проявляется/воспроизвести>
2. ...
<если багов нет — "не найдено">

## Замечания (не баги)
- ...

## Итоговый вердикт
<готово к мержу / нужны доработки, коротко почему>
**Готово к finish-task:** да / нет — <причина>
```
