Не использовать для починки логических багов (в рамках пайплайна они чинятся вручную в диалоге, после `verify-implementation`) и не использовать для планирования новой фичи (`form-intent`/`form-plan`).

# Приведение кода в соответствие правилам (audit → fix)

Шестой этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → [`form-plan`](../form-plan/SKILL.md) → [`execute-plan`](../execute-plan/SKILL.md) → [`run-quality-gate`](../run-quality-gate/SKILL.md) → `align-with-rules` → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → [`finish-task`](../finish-task/SKILL.md).

В отличие от остальных шагов пайплайна, этот скилл не привязан жёстко к тому, что его вызвали "в рамках задачи" — он сам определяет, в каком режиме работать (шаг 1), и одинаково корректно ведёт себя, если его вызвали посреди пайплайна или отдельно, в любой момент, на любой ветке.

Цель — найти в коде места, которые нарушают правила из [`.claude/rules/`](../../rules/README.md), и поправить их, не меняя наблюдаемое поведение. Это приведение к уже согласованным конвенциям проекта, а не рефакторинг "как лучше" и не поиск логических багов.

Пункты, которые в файлах правил помечены заметкой-указателем на линтер («формализовано в `checkstyle.xml`/`pmd.xml`/`import-control.xml`/`spotless-format.xml`…»), вручную не сверяются — их уже проверил `run-quality-gate` (`mvn clean verify`). Этот скилл отвечает только за смысловую часть правил, которую линтер не ловит.

## Порядок действий

1. Определи режим и область проверки:
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```
   - Если пользователь явно назвал файлы/директорию/класс — работай только с ними, это отменяет автоопределение ниже.
   - Иначе, если существует `$TASK_DIR/execution-report.md` — **режим пайплайна**: текущая ветка соответствует задаче, для которой уже отработал `execute-plan`. К этому моменту `run-quality-gate` уже пройден (переход сюда заблокирован hook'ом, если это не так) — при желании свериться с `$TASK_DIR/quality-gate-report.md`, что именно проверялось, но повторно гонять сборку/тесты не нужно, это не задача этого шага. Область проверки — файлы из раздела "Изменённые/созданные файлы" `execution-report.md`, не весь проект.
   - Иначе — **самостоятельный режим**: область проверки по умолчанию — весь `src/main/java` и `src/test/java` (если он не пуст), плюс `pom.xml` и путь к миграциям БД проекта (например `src/main/resources/db/changelog/`, если такой есть), если по ходу находятся нарушения конвенций миграций/сборки.

2. Если область проверки из шага 1 — конкретные файлы, названные пользователем, или файлы из `execution-report.md` (режим пайплайна): читай [`.claude/rules/README.md`](../../rules/README.md) и файлы правил сам, инлайн — но только те, что касаются затронутых задачей слоёв (например, если задача не трогает слой сервисной реализации, правило про слои и зависимости в этой части не нужно) — область достаточно узкая, чтобы не перегружать контекст, — и переходи сразу к шагу 3.

   Если область — весь проект (самостоятельный режим без явного указания файлов): не читай `src/main/java`/`src/test/java` целиком в основной контекст — вынеси сканирование в изолированный subagent, по аналогии с [`run-quality-gate`](../run-quality-gate/SKILL.md), шаг 4. Вызови `Agent`:
   - `subagent_type: general-purpose`. Вызов синхронный (без `isolation`) — результат нужен сразу для шага 5 (показ пользователю).
   - Самодостаточный промпт (агент не видит эту беседу), включающий:
     - Рабочая директория — корень репозитория проекта (передай абсолютный путь `$PROJECT_ROOT`).
     - Прочитать [`.claude/rules/README.md`](../../rules/README.md) (индекс) и все файлы правил, на которые он ссылается — конкретные имена файлов и их число зависят от проекта, определяй по факту индекса, не по памяти о номерах из другого проекта. Часть правил может быть помечена самим файлом правила как "заготовка на будущее" (например: правило про REST-контроллеры, если в проекте пока нет REST-слоя; правило про отдельные Maven-модули, если проект однмодульный; правило про конкретный брокер сообщений, если интеграция ещё не подключена) — для таких проверить, появился ли уже в коде класс/модуль/зависимость, к которой правило применяется; если нет — пропустить правило.
     - Пройти по `src/main/java`, `src/test/java`, `pom.xml`, каталогу миграций БД (если есть) и сопоставить с каждым применимым правилом. Правила обычно группируются по темам — сопоставляй тему с конкретным файлом в `.claude/rules/` этого проекта по индексу, а не по номеру:

       | Тема | На что смотреть |
       |------|-----------------|
       | Слои и зависимости | `@Autowired` на поле вместо конструктора, обращение верхнего слоя (UI/controller) к репозиторию напрямую минуя сервис, сервис без пары интерфейс/`...Impl`, если так принято в проекте |
       | Lombok / сущности | `@Data`/`@EqualsAndHashCode` на JPA-сущности |
       | Именование | по конвенции проекта |
       | Javadoc / комментарии | отсутствующий, либо не на том языке, что принято в проекте |
       | Импорты | wildcard-импорты, неверный порядок |
       | Миграции БД | формат имени/changeset id, `--rollback`, не редактировать уже закоммиченные миграции |
       | Логирование и ошибки | `System.out.println`, фреймворковые исключения вместо кастомных, пустой `catch` |
       | Тесты | отсутствующий `@DisplayName` (если принято в проекте), моки не через принятый в проекте фреймворк |
       | Repository | по конвенции проекта |
       | Общие конвенции | магические числа/строки, лишняя вложенность |

     - Не выдумывать нарушения там, где правило неприменимо или неоднозначно — такие случаи помечать как "спорные", а не пропускать молча.
     - Вернуть структурированный список находок (не полный текст файлов): `<файл>:<строка>` — правило — в чём нарушение — как исправить — категория (однозначное/спорное). Ничего не исправлять — только диагностика.

   Дождись ответа субагента и используй его список находок как результат шага 3 — сам код в основной контекст не читай, если находка не потребует уточнения (тогда прочитай точечно только этот файл).

3. Если пропустил шаг 2 (узкая область) — пройди по коду сам и сопоставь с каждым применимым правилом, тем же критериям, что перечислены в промпте субагента выше.

4. Собери находки в список: `<файл>:<строка>` — какое правило нарушено — в чём именно нарушение — как должно быть по правилу.

   Перед тем как зафиксировать находку как нарушение — проверь, не задокументировано ли в самом файле правила (`.claude/rules/NN-....md`) осознанное отклонение репозитория для этого случая (например, раздел вида «Известные отклонения» в конце файла правила). Если такая пометка есть и проверяемый код следует тому же паттерну — это не находка, а известное отклонение проекта (см. категорию ниже), а не нарушение. Если правило само себе такого раздела не имеет — считай, что отклонений нет, и не выдумывай их.

5. Раздели находки на:
   - **Однозначные** — механическое исправление без риска изменить поведение (порядок импортов, `@Data` → `@Getter/@Setter`, `System.out` → `log`, англоязычный Javadoc → русский и т.п.).
   - **Спорные** — исправление требует структурного решения (перенос логики между слоями, вынос кода в отдельный пакет, разбиение класса) — здесь легче случайно сломать поведение или зацепить чужой незавершённый код.
   - **Известное отклонение** — задокументировано в самом файле правила (см. выше) как принятое для этого репозитория; не исправляется, только фиксируется в отчёте для прозрачности.

6. Покажи пользователю список находок по шаблону ниже (сначала спорные, они требуют больше внимания) и спроси, какие применить сейчас — можно не все. Не исправляй ничего до этого шага, даже однозначные находки.

7. Для каждой одобренной находки внеси правку, следуя тем же конвенциям, что и `execute-plan` (стиль похожих классов, буквальное соответствие правилу, а не "заодно" улучшение чего-то ещё). Если хотя бы одна находка была применена — прогони и запомни результат (он понадобится для отчёта на шаге 8):
   ```bash
   ./mvnw clean package -DskipTests
   ./mvnw test
   ```
   чтобы убедиться, что поведение не изменилось. Если ни одной находки не было одобрено — код не менялся, повторный прогон не нужен.

8. Запиши файл-отчёт — создаётся всегда, в обоих режимах: в режиме пайплайна — `$TASK_DIR/align-with-rules-report.md`; в самостоятельном режиме — `specification/align-with-rules-reports/<YYYY-MM-DD-HHMM>.md` (директория создаётся при необходимости; метка времени — чтобы не затирать отчёт при повторном прогоне в тот же день). Формат — по шаблону ниже.

   В режиме пайплайна заполни раздел "Сборка и тесты": если на шаге 7 был прогон — его результат; если правок не применялось — напиши "код не менялся, актуален результат `quality-gate-report.md`". Это даёт `verify-implementation` возможность переиспользовать уже свежий результат вместо третьего подряд прогона `./mvnw` на том же коде. В самостоятельном режиме (нет `verify-implementation`, который мог бы это переиспользовать) — напиши "не применимо (самостоятельный режим)".

   Спроси пользователя, завершён ли шаг (например: «Правки применены, коммитим отчёт и изменённый код?»). При отрицательном ответе — не коммитить. При положительном — в режиме пайплайна (есть `execution-report.md`) дополнительно обнови `$TASK_DIR/pipeline-state.md` (`align-with-rules` → `завершён`, `Текущий шаг` → `verify-implementation`) — в самостоятельном режиме `pipeline-state.md` не трогай, он не существует вне задачи пайплайна. Закоммить файл отчёта вместе со всеми применёнными в шаге 7 правками кода (и, в режиме пайплайна, `pipeline-state.md`):
   ```bash
   git add <файл1> <файл2> ... "<путь к align-with-rules-report.md>" ["$TASK_DIR/pipeline-state.md" — только в режиме пайплайна]
   git commit -m "$(cat <<'EOF'
   Align with rules: <короткое имя задачи или "самостоятельный прогон">

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```

   Дай пользователю сводку в чате: сколько находок было всего, сколько исправлено, сколько отклонено/отложено и почему. В режиме пайплайна дополнительно скажи, что следующий шаг — `verify-implementation`; в самостоятельном режиме — что шаг завершён (следующего шага пайплайна нет).

## Формат находки (в чате, перед применением)

```markdown
### <N>. <короткое описание нарушения>
- Где: `<файл>:<строка>`
- Правило: [`NN-....md`](../../rules/NN-....md)
- Нарушение: <что именно не так>
- Исправление: <что будет сделано>
- Категория: однозначное / спорное / известное отклонение
```

## Шаблон `align-with-rules-report.md`

```markdown
# Отчёт о приведении в соответствие правилам: <короткое имя задачи или "самостоятельный прогон">

- Дата: <YYYY-MM-DD>
- Режим: пайплайн (ветка <branch>) / самостоятельный
- Область проверки: <файлы из execution-report.md, либо весь проект>

## Находки
### <N>. <короткое описание нарушения>
- Где: `<файл>:<строка>`
- Правило: [`NN-....md`](../../rules/NN-....md)
- Категория: однозначное / спорное / известное отклонение
- Статус: исправлено / отклонено (причина) / отложено (причина) / зафиксировано как известное отклонение

## Сборка и тесты
<результат повторного прогона на шаге 7 (пайплайн) / "код не менялся, актуален результат quality-gate-report.md" / "не применимо (самостоятельный режим)">

## Итог
- Всего находок: <N>
- Исправлено: <N>
- Отклонено/отложено: <N>
```
