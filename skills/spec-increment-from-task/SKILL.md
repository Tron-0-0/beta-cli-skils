# /increment-from-task — Завести инкремент по описанию задачи

## Важно

- **Стек:** скилл рассчитан на Java/Spring Boot backend-проекты — слои и терминология плана
  (controller/service/repository/entity/dto/mapper, JPA, Liquibase, MapStruct, Maven/Gradle)
  предполагают именно этот стек.
- **Шаг 0.5 — gate-check с одним узким стоп-условием.** Отсутствие `intent.md` — штатный
  сценарий, он не блокирует: скилл работает от `$ARGUMENTS`. Блокирует только один случай —
  `intent.md` существует, но пуст; флагом `--skip-gate-checks` (только для отладки) можно
  пропустить и его.
- Не начинай реализацию, пока не закрыты уточняющие вопросы из шага 3, и не начинай её вообще —
  эта команда только заводит и дооформляет план
- Не трогай файлы **других** инкрементов — ни исторических (`Статус: Выполнено`), ни соседних
  "К выполнению". Единственное исключение — `specification/increment/index.md`: в него на шаге 4а
  добавляется ровно одна новая строка (в конец таблицы), существующие строки не трогаются
- Один вызов — один новый инкремент; не пытайся угадать, что пользователь имел в виду несколько
  задач сразу, если текст тикета описывает что-то одно связное
- Структура хранения инкрементов: `specification/increment/<release>/<ticket>/increment.md`.
  Папка `<release>` создаётся при первом инкременте этого релиза.
- Если есть `intent.md` в папке тикета (`specification/increment/{release}/{ticket}/intent.md`)
  — он становится **единственным** источником описания задачи (см. Шаг 1); `$ARGUMENTS` в этом
  случае используется только для именованных аргументов (`--release`/`--ticket`), не как текст
  описания
- **`intent.md` остаётся в бизнес-формате.** Не требуй и не делай его «техническим» — это
  документ аналитики. Перевод бизнес-языка в технические сигнатуры (имена модулей/файлов/
  миграций/контрактов) — задача **этого скилла** на шаге 2. Если в `intent.md` отсутствуют
  имена классов/методов/таблиц/URL — это нормально, не нужно их туда дописывать; восстанови
  их по коду и спецификации при подготовке плана.

Эта команда получает **сырой текст** — название и описание тикета — и сама создаёт новый файл
инкремента с нуля, а затем доводит его до полноценного плана (шаги 1-4 ниже), но
**останавливается перед реализацией кода**: реализация в pipeline-конвейере задач — отдельный
шаг с валидацией человеком между планом и кодом (см.
`specification/index.md` (раздел "Спецификация проекта" → навигация по разделам)).

**Использование:**
```
/increment-from-task --release=01.023.00 --ticket=AO-12 Кнопка экспорта отчёта в PDF на странице задачи. Нужно...
```

Также доступны именованные аргументы (могут быть вперемешку с текстом задачи в любом порядке):

| Аргумент | Обязательный | Описание |
|----------|-------------|----------|
| `--release=<номер релиза>` | Да (если не передан — запросить у пользователя) | Номер релиза, в рамках которого ведётся разработка |
| `--ticket=<номер тикета>` | Да (если не передан — вычислить из ветки) | Ключ задачи (например AO-8). Если не передан и не удаётся извлечь из ветки — запросить у пользователя |

## Шаг 0. Разобрать аргументы

1. Извлеки из `$ARGUMENTS` именованные аргументы:
    - `--release=<значение>` — номер релиза (например `01.023.00`, `01.024.00`)
    - `--ticket=<значение>` — ключ тикета (например `AO-12`)
2. Если не передан `--ticket`, но в `$ARGUMENTS` первым словом (до первого пробела) идёт строка
   вида `{БУКВЫ}-{ЦИФРЫ}` (например `AO-12`) — это ключ тикета.
    - В этом случае определи релиз: выполни `Glob specification/increment/*/{TASK_KEY}/`
      (поиск по всем папкам релизов).
        - **0 совпадений** — запроси у пользователя через `AskUserQuestion` или текстовым сообщением
          "Укажите номер релиза (например, 01.023.00):".
        - **1 совпадение** — возьми имя этой папки как `--release`.
        - **2+ совпадений** — спроси у пользователя через `AskUserQuestion`.
3. Если `--release` не передан — запроси у пользователя через `AskUserQuestion` или текстовым
   сообщением "Укажите номер релиза (например, 01.023.00):". Не продолжай без номера релиза.
4. Если `--ticket` не передан — определи ключ тикета `{TASK_KEY}`:
    - выполни `git branch --show-current` и отбрось префикс `feature/`/`bugfix/`
      (имя ветки задачи всегда `{тип}/{ключ}`)
    - Если ветка не соответствует шаблону — запроси ключ у пользователя.

> ⚠️ **Согласованность с object-pipeline:** эта логика дублирует «Шаг 0. Определить
> {release} и {ticket}» из `object-pipeline/SKILL.md`. При изменении логики обновления
> оба файла.

## Шаг 0.5. Проверить intent.md (опционален) и загрузить описание

> ⚠️ Правило блокировки — см. «Важно» выше: единственный стоп здесь — п. 5 (файл найден, но
> пуст). Остальные случаи — штатные сценарии, не путать с пропущенным Шагом 1
> (`spec-intent-generation`): его отсутствие тоже легитимно.

1. Определить `{release}` и `{ticket}` (из аргументов или имени ветки).
2. `Glob specification/increment/{release}/{ticket}/intent.md`
3. Если файл **не найден** → это штатный сценарий:
   скилл работает без `intent.md` — описание берётся из `$ARGUMENTS` как есть.
   Переходи к Шагу 0.6 (загрузка service-rules).
4. Если файл **найден и не пуст** (содержит разделы «Процесс и шаг процесса», «Описание»)
   → ✅ gate-check пройден. **Прочитай содержимое** `intent.md` по разделам и зафиксируй
   каждый раздел в контексте сессии (эта информация понадобится на шагах 1–4):

   | Раздел `intent.md` | Что фиксировать |
      |--------------------|-----------------|
   | `## Процесс и шаг процесса` | Бизнес-процесс + шаг процесса (якорь для «Контекста») |
   | `## Описание` | Текущее и целевое поведение (перевести в технические формулировки) |
   | `## Точки изменений` | Карта артефактов (REST, БД, события, НСИ, интеграции) → основа для «Изменений в коде» |
   | `## Открытые вопросы` | Первый источник вопросов на Шаге 3 |
   | `## Критерии приёмки` | Основа для разделов «Цель» и «Совместимость» (поведение для исторических записей) |
   | `## Границы` | «Явно входит» → «Изменения в коде»; «Явно НЕ входит» → «Совместимость» |
   | `## Допущения для шага реализации` | Перенести в одноимённый раздел плана |

   Полный и окончательный маппинг разделов `intent.md` → `increment.md` — в таблице
   «Что куда переносится из intent.md» (Шаг 4.1).

   → Переходи к Шагу 0.6.
5. Если файл **найден, но пуст**:
    - Если `$ARGUMENTS` содержит `--skip-gate-checks` → не останавливайся: выведи
      `⚠️ intent.md пуст, но флаг --skip-gate-checks пропускает проверку — использую $ARGUMENTS
      как источник описания.` и переходи к Шагу 0.6, как в п. 3.
    - Иначе → **стоп**:
      ```
      ⛔ intent.md существует, но пуст. Заполни описание задачи перед продолжением.
      ```

## Шаг 1. Определить номер, источник описания и создать файл инкремента

Номер инкремента = ключ тикета (задачи) `{TASK_KEY}` — из аргумента `--ticket` или из ветки.

**Источник описания задачи:**

1. **Если `intent.md` найден на Шаге 0.5** — используй уже загруженное содержимое по разделам
   (из Шага 0.5). Повторно файл не читай — используй то, что зафиксировано в контексте сессии.
2. **Если `intent.md` не найден** — описание задачи берётся из `$ARGUMENTS` как есть. Если при
   этом `$ARGUMENTS` пуст или не содержит осмысленного описания — **остановись здесь** и попроси
   пользователя уточнить, что нужно сделать, вместо того чтобы создавать пустой/бессмысленный
   инкремент. К п. 3 переходи только после того, как источник описания определён.
3. Создай структуру папок (если не существует) и файл:
   ```
   specification/increment/{release}/{ticket}/
   ```
   Файл инкремента:
   ```
   specification/increment/{release}/{ticket}/increment.md
   ```

   Содержимое файла на этом шаге — полное описание задачи (из `intent.md` или из `$ARGUMENTS`)
   без изменений (это черновик, как если бы его руками положил человек).
   Дальше с ним работают шаги 2–4 ниже.

Номер релиза `{release}` — из аргумента `--release`.

## Шаг 2. Прочитать контекст

1. `specification/increment/index.md` (таблица статусов всех инкрементов) — нет ли уже
   пересекающегося инкремента (открытого или готового); `specification/index.md` — общая навигация
   по разделам, помогает понять, к какому разделу проекта ближе всего относится задача
2. **Если есть `intent.md`** (см. шаг 1) — это **основной вход для плана**. Проанализируй уже
   зафиксированное на Шаге 0.5 содержимое с инженерной оптикой (файл с диска повторно не читай)
   и **определи какие именно модули/таблицы/сервисы затронуты**:
    - «Процесс и шаг процесса» → какой именно модуль/контроллер/сервис реализует этот шаг в коде.
    - «Точки изменений» (артефакт: «входящий REST-запрос», «запись в БД (атрибут)»,
      «исходящее событие», «справочник/НСИ», «интеграция с <внешняя система>»,
      «бизнес-правило / статус») → определи **конкретные** контроллеры, сервисы, репозитории/таблицы,
      мапперы, Feign/WebClient/RestTemplate-клиенты, REST-контракты, Kafka-контракты в коде.
      Имена таблиц и комментарии (COMMENT ON) берутся из `intent.md` (раздел «Точки изменений»)
      и фиксируются в `increment.md`, но **не генерируют Java-сигнатуры методов/аннотации** —
      это делает `spec-increment-plan`.
    - «Критерии приёмки» → проверяемые пункты в плане (что тестируем, какие сценарии
      автотестов, какие ручные проверки).
    - «Границы» (явно НЕ входит) → что **не трогаем** в «Совместимости».
    - «Допущения для шага реализации» → в одноимённый раздел плана как есть.
      На этом шаге **не редактируй `intent.md`** — он остаётся в бизнес-формате, в плане ты
      только ссылаешься на него.
3. Релевантный раздел `specification/absolut/` (структура и имена подразделов определяются по
   факту репозитория — навигация через `specification/absolut/index.md`) — актуальное состояние
   "как есть", с которым план должен состыковаться (как правило: index.md, business.md, api.md,
   db.md; при наличии дополнительных файлов раздела — читай и их).
4. Затронутый код Spring Boot backend-слоёв (controller → service → repository → entity → dto →
   mapper) — пойми реальные сигнатуры, а не предполагай их. Это **основной способ превратить
   «бизнес-точки» из intent.md в конкретные файлы изменений** в плане.

## Шаг 3. Задать уточняющие вопросы

Свободный текст тикета почти никогда не содержит всех деталей, нужных для реализации. Прежде чем
писать план, определи неоднозначности и задай уточняющие вопросы пользователю (через
`AskUserQuestion`, а если вопросов много и они не укладываются в закрытые варианты — обычным
текстом).

**Если есть `intent.md` (от скилла `spec-intent-generation`) — сначала проверь раздел
«Открытые вопросы»**. Если он непустой — это **первый источник вопросов** для пользователя:
он уже сформулирован аналитиком, его нужно только закрыть. Сведи каждый пункт в
конкретный вопрос; если по нему уже был задан вопрос на стадии intent — проверь, нет ли
ответа в `intent.md` или `$ARGUMENTS`.

Если `intent.md` нет или раздел «Открытые вопросы» пуст — определи неоднозначности
самостоятельно. Типичные зоны неопределённости:

- Границы изменений (что явно НЕ входит в объём)
- Роли/права доступа к новой функциональности
- Поведение при ошибках и граничных случаях
- Совместимость с уже существующими данными/поведением (нужна ли миграция, что с уже
  существующими записями)
- Если текст тикета — по сути просто SQL/конфиг без описания REST-контракта — нужен ли
  соответствующий Controller-эндпоинт, или изменение чисто в данных (миграция/справочник)

Не переходи к шагу 4, пока не получены ответы на все вопросы, без которых нельзя однозначно
написать «Изменения в коде» или «Цель» — то есть влияющие на объём работ, выбор технического
решения или список затронутых сущностей. Чисто стилистические уточнения ответа не требуют.

## Шаг 4. Переписать файл инкремента по правилам проекта

### 4.1. Формат инкремента

> ⚠️ **Используй загруженные на Шаге 0.6 service-rules при генерации раздела «Изменения в коде».**
> Для каждого загруженного правила примени соответствующие конвенции:

| Загруженный rule | Применяется к разделу | Какие конвенции |
|------------------|----------------------|-----------------|
| `01_coding.md` | Изменения в коде (общее) | DI через `@RequiredArgsConstructor`, MapStruct-мапперы с `uses = {...}` для вложенных объектов, `enum` вместо констант для типов/статусов (§1.7), форматы вызовов: ≤3 params → одна строка, 4 params → каждый с новой строки, ≥5 params → параметр-объект (record) |
| `03_migrations.md` | Изменения в коде (БД-миграция) | Liquibase/Flyway (один инструмент на проект); версионирование по релизу или монотонной дате; immutable применённые changeset'ы; `COMMENT ON` на новую таблицу/колонку + `--rollback`; breaking-изменения — через expand/contract |
| `08_database.md` | Изменения в коде (Entity, Repository) | `@Table(name=snake_case)`, суррогатный PK (`UUID`/`BIGINT` + `@GeneratedValue`), имена совпадают с миграцией 1:1; связи `LAZY` по умолчанию; списки — `Page`/`Slice`, не `List`; `@Version` на конкурентно изменяемых сущностях; аудит через `@CreatedDate`/`@LastModifiedDate` |
| `13_monetary.md` | Изменения в коде (DTO, Entity) | Денежные поля — `BigDecimal`, `double`/`float` запрещены; `NUMERIC(precision, scale)` в DDL; округление — явный `RoundingMode` |

## Шаг 4а. Добавить инкремент в индекс и застейджить

> ⚠️ **ВАЖНО:** Используй `{release}` **только** из аргумента `--release` или определённый на Шаге 0.
> **НЕ подтягивай** номер релиза из предыдущих инкрементов, из `increment/index.md`, или из контекста.

> `specification/increment/{release}/{ticket}/increment.md` — где `{release}` совпадает с тем,
> что используется в Шаге 4а для индексной таблицы.

1. Добавь новую строку в конец таблицы `specification/increment/index.md` (тот же формат, что и
   у существующих строк):
   `| [N]({release}/{ticket}/increment.md) | Название | К выполнению |` — `Название` бери
   из заголовка `# Инкремент N — Название`, который только что записал на шаге 4.

   Ссылка в квадратных скобках — на путь относительно `specification/increment/`:
   `{release}/{ticket}/increment.md`.

2. `git add` новый файл инкремента, `specification/increment/index.md` и всю структуру папки:
   ```bash
   git add specification/increment/{release}/{ticket}/increment.md specification/increment/index.md
   ```

`specification/increment/index.md` слит через git `merge=union` (`.gitattributes`), поэтому
параллельное добавление строк разными релизами/тикетами сливается автоматически без конфликта.
Если конфликт всё же возник (например, слияние выполняется стороной, не учитывающей
`.gitattributes`) — разрешать его, оставляя строки **обеих** сторон, не выбирая одну.
