# Системный анализ (бизнес-intent → system-intent)

Второй этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → `form-system-intent` → [`form-plan`](../form-plan/SKILL.md) → [`execute-plan`](../execute-plan/SKILL.md) → [`run-quality-gate`](../run-quality-gate/SKILL.md) → [`align-with-rules`](../align-with-rules/SKILL.md) → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → [`finish-task`](../finish-task/SKILL.md).

`form-intent` уже зафиксировал ценность, скоуп и критерии готовности на уровне бизнеса, но сознательно не касался того, как идея встраивается в систему. Этот шаг закрывает именно это: как идея будет работать как процесс — последовательность шагов, откуда и куда идут данные, какие правила принятия решений — и как это соотносится с уже описанной архитектурой, взаимодействиями компонентов и моделью данных проекта.

Этот скилл работает на уровне системы: процесс/алгоритм, поток данных, интеграция с уже существующей системной логикой проекта — описанной в `specification/absolut/architecture.md`, `interactions.md`, `data-model.md`. Он **не занимается бизнес-стороной** (это уже сделал `form-intent`: цель/ценность, скоуп, критерии готовности — не переспрашивай и не переписывай их здесь, только ссылайся). И он **не проектирует код**: не называет конкретные классы, пакеты, слои проекта (какие именно слои есть в проекте — определяет `form-plan` по факту архитектуры) и не привязывается к файлам — это задача [`form-plan`](../form-plan/SKILL.md), следующего шага. Если в процессе уточнения разговор уводит в детали реализации ("в каком классе это писать", "как назвать метод") — не отвечай на это здесь, зафиксируй как есть в процессе и отложи до `form-plan`.

## Порядок действий

1. Определи директорию задачи (та же логика, что в `form-intent`):
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```

2. Прочитай `$TASK_DIR/intent.md`. Если файла нет — прежде чем считать, что `form-intent` не выполнялся, проверь, не осталась ли задача в другой ветке: поищи `intent.md` в `specification/increment/$VERSION/*/`. Если нашёлся в другой ветке — скажи пользователю, что задача велась в ветке `<найденная>`, и предложи переключиться (`git checkout <найденная>`) вместо продолжения в текущей. Если нигде не нашёлся — скажи пользователю, что сначала нужно прогнать `form-intent`, и спроси, хочет ли он это сделать сейчас.

3. Если в `$TASK_DIR/system-intent.md` уже есть файл — покажи пользователю его текущее содержимое и спроси, обновляем ли мы существующий анализ (например, потому что `intent.md` менялся) или это нужно переделать с нуля.

4. Прочитай сначала [`specification/README.md`](../../../specification/README.md), затем из документов, относящихся к системному уровню, читай те, что реально касаются идеи из `intent.md`:
   - [`architecture.md`](../../../specification/absolut/architecture.md) — общая картина устройства системы (на уровне "что за чем идёт и почему", не на уровне классов).
   - [`interactions.md`](../../../specification/absolut/interactions.md) — существующие процессы/пайплайны и то, как компоненты взаимодействуют во времени — нужно, чтобы понять, куда встраивается новый процесс.
   - [`data-model.md`](../../../specification/absolut/data-model.md) — если идея касается данных/сущностей и связей между ними на концептуальном уровне.

   При сомнении, относится документ к идее или нет — лучше прочитать и убедиться, чем пропустить и упустить противоречие с уже принятым системным решением.

   Если для содержательных уточняющих вопросов информации в `specification/` не хватает (спека устарела, не описывает нужную область) — только тогда обратись к коду (grep/чтение классов), чтобы восполнить пробел, и лишь после этого формулируй вопросы пользователю.

5. Уточни у пользователя (не додумывай сам, если неочевидно из `intent.md`). Вопросы — на уровне системы, не на уровне кода:
   - Процесс/алгоритм на высоком уровне: последовательность шагов, откуда берутся и куда идут данные, какие правила принятия решений — описание логики, а не кода (не нужно называть классы/методы/пакеты).
   - Как идея соотносится с уже описанной системной логикой из `specification/` (`architecture.md`, `interactions.md`, `data-model.md`): расширяет существующий процесс, вводит новый, конфликтует или пересекается с уже принятым архитектурным решением.
   - Известные пользователю системные ограничения/edge-cases (объёмы данных, конкурентный доступ, порядок операций, обработка ошибок на уровне процесса), которые обязательно учесть.

   **Триггер рассинхрона:** если процесс, который описывает пользователь, прямо противоречит текущей архитектуре или взаимодействиям, уже описанным в `architecture.md`/`interactions.md` — не выбирай молча одну из версий и не додумывай, какая верна. Это обязательный вопрос пользователю до того, как процесс зафиксирован в `system-intent.md`.

   Не задавай вопросы, ответ на которые уже очевиден из `intent.md`, из `specification/` или из кода. И не задавай вопросы уровня "в каком слое/классе это реализовать" — это забота `form-plan`, не этого шага.

6. Запиши системный анализ в `$TASK_DIR/system-intent.md` строго по шаблону ниже.

7. Спроси пользователя, завершён ли шаг (например: «Системный анализ готов, коммитим `system-intent.md`?»). При отрицательном ответе — не коммитить, продолжить правки и спросить повторно. При положительном — обнови `$TASK_DIR/pipeline-state.md` (`form-system-intent` → `завершён`, `Текущий шаг` → `form-plan`) и закоммить его вместе с `system-intent.md` на текущей (задачной) ветке, отдельным коммитом:
   ```bash
   git add "$TASK_DIR/system-intent.md" "$TASK_DIR/pipeline-state.md"
   git commit -m "$(cat <<'EOF'
   Add system intent: <короткое имя задачи>

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```
   Имя модели в `Co-Authored-By` не указывается: модель проекта может меняться, и зашитое имя быстро начинает врать.

   Это относится и к первому созданию анализа на этой ветке, и к каждому последующему обновлению `system-intent.md` в рамках той же задачи — каждая версия фиксируется своим коммитом.

8. Скажи пользователю путь к файлу и что следующий шаг — вызвать `form-plan`.

## Шаблон `system-intent.md`

```markdown
# Системный анализ: <короткое имя задачи>

- Дата: <YYYY-MM-DD>
- Ветка: <branch>
- Версия: <version>
- Основано на: intent.md

## Процесс / алгоритм (высокий уровень)
<пошаговое описание логики: последовательность действий, откуда и куда идут данные, правила принятия решений — без привязки к классам/файлам/слоям>

## Связь с текущей системной логикой
<как соотносится с specification/absolut/architecture.md, interactions.md, data-model.md — что расширяет, что меняет, с каким уже принятым архитектурным решением связано; ссылки на конкретные разделы этих документов>

## Системные ограничения и edge-cases
- ...

## Открытые вопросы и допущения
- ...
```

Если пользователь не смог ответить на какой-то пункт — не блокируй работу, зафиксируй его как открытый вопрос/допущение и двигайся дальше.

Этот файл не должен содержать названий Java-классов, пакетов или конкретных файлов кода (кроме случаев, когда пользователь сам их называет) — их определит `form-plan`. И не должен дублировать разделы `intent.md` (цель/ценность, скоуп, критерии готовности) — только ссылаться на них при необходимости.
