# /spec-increment-plan — Детальный технический план реализации

Превращает **бизнес-требования** (`intent.md`) + **системный план** (`increment.md`) 
в **детальный технический план** (`implementation-plan.md`).

Анализирует **реальный код проекта**, собирает карту классов и методов, 
определяет **цепочки вызовов** от входа до выхода.

**ЗАДАЁТ уточняющие вопросы** пользователю при неопределённости (бизнес-логика, алгоритмы, цепочки, интеграции, паттерны).

**НЕ пишет код** — только план реализации.

**Использование:**
```
/spec-increment-plan 01.023.00 AO-12
/spec-increment-plan AO-12
/spec-increment-plan specification/increment/01.023.00/AO-12/increment.md
```

## Важно

- **Gate-check обязателен:** не выполняй шаги 1-3, если не пройден Шаг 0.5. Пропуск шагов pipeline запрещён, кроме `--skip-gate-checks` (только для отладки).
- **Не пиши код** — только анализ и генерация плана. Реализация - зона `spec-increment-implement`.
- **Не запускай `mvn`** — только план, без проверки компиляции.
- **Интерактивность:** задавай вопросы пользователю при неопределённости. Утверждай каждый алгоритм, паттерн, цепочку вызовов перед фиксацией в плане.
- **Service-rules обязательны:** загружаются на Шаге 1.5, применяются при генерации плана.
- **Читай реальный код** — не предполагай сигнатуры, читай через `Glob` и `Read`.
- **Универсальность:** скилл работает с любым проектом - не используй хардкод имён пакетов, классов, путей. Определяй структуру по реальному коду.

## Входы и выходы

| Вход | Описание |
|------|----------|
| `intent.md` | Бизнес-требования: процесс, шаг процесса, точки изменений, контракты |
| `increment.md` | Системный план: цели, контекст, допущения, точки изменений |
| Код проекта | Реальные сигнатуры, пакеты, зависимости, связи |

| Выход | Описание |
|-------|----------|
| `implementation-plan.md` | Карта вызовов, обзор методов, алгоритмы, интеграции, паттерны, чек-лист |

# Поиск файлов и шаги

## Шаг 0. Найти файлы инкремента

Инкременты хранятся по пути `specification/increment/<release>/<ticket>/`.

> ⚠️ **Флаг `--skip-gate-checks`:** действует и здесь, и на Шаге 0.5. Если он есть в `$ARGUMENTS` — при
> любом **стоп** ниже вместо остановки выведи `⚠️ Gate-check пропущен флагом --skip-gate-checks:
> {текст, который был бы в стопе}` и продолжай.

Разбери `$ARGUMENTS`:
- Если это существующий путь, заканчивающийся на `increment.md` - используй его напрямую.
- Если это два токена - через пробел или через слэш (например `01.023.00 AO-12` или
  `01.023.00/AO-12`) - первый токен это `{release}`, второй - `{ticket}`. Ищи через
  `Glob specification/increment/{release}/{ticket}/intent.md` и `increment.md`.
- Если это один токен без слэша (например `AO-12`) - это только `{ticket}`, `{release}` неизвестен:
  ищи через `Glob specification/increment/*/{ticket}/intent.md` и `increment.md`.

**Оба файла должны существовать.** Если один из них не найден - **стоп** с сообщением:
```
⛔ Файл {intent.md|increment.md} не найден для тикета {ticket}.
Убедитесь в правильности release и ticket.
```

Несколько кандидатов или ни одного - покажи список и уточни у пользователя.

Если `Статус` найденного файла `increment.md` уже `Выполнено` - сообщи об этом и остановись.

## Шаг 0.5. Gate-check: проверить содержание файлов

> ⛔ **НЕ выполняй шаги 1-3, если gate-check не пройден.**
> ⚠️ **Флаг `--skip-gate-checks`:** если он есть в `$ARGUMENTS` — при любом **стоп** ниже вместо
> остановки выведи `⚠️ Gate-check пропущен флагом --skip-gate-checks: {текст, который был бы в
> стопе}` и продолжай (к следующему пункту проверки или сразу к Шагу 1, если пункт последний).

`{release}`, `{ticket}` и оба файла (`intent.md`, `increment.md`) уже найдены на Шаге 0 - здесь
проверяется их содержание по существу.

1. Проверить содержание:
   - `intent.md`: раздел "Процесс и шаг" не пуст - продолжить
   - `increment.md`: раздел "Цель" и "Изменения в коде" не пуст - продолжить
   - Если пуст - остановиться с сообщением
2. **Дополнительная валидация:**
   - Проверить наличие обязательных разделов в обоих файлах
   - Если разделы содержат только шаблонный текст - **стоп**
   - Проверить формат `{release}` (`X.Y.Z`, например `01.023.00`) и `{ticket}`
     (`{ЗАГЛАВНЫЕ_БУКВЫ}-{ЦИФРЫ}`, например `AO-12`)
   - Если формат неверный - **стоп**
   - Если размер файла > 5000 символов - **warning**
3. Если gate-check пройден - продолжить к шагу 1.

## Шаг 1. Прочитать бизнес-требования

1. `Read` - `intent.md` - извлечь:
   - Процесс и шаг процесса
   - Текущее и целевое поведение
   - Точки изменений (REST/БД/события/интеграции)
   - Контракты сервисов
   - Наблюдаемые критерии приёмки

2. `Read` - `increment.md` - извлечь:
   - Цель инкремента
   - Контекст (какие классы/таблицы уже есть)
   - Обозначенные точки изменений
   - Допущения и технические ориентиры
   - Совместимость с историческими данными

3. Связать бизнес-требования из `intent.md` с системным планом из `increment.md`.
4. Сформировать предварительный список: какие части проекта затронет реализация.

## Шаг 1.5. Загрузить service-rules

> ⚠️ **Этот шаг ОБЯЗАТЕЛЕН перед Шагом 2.** Загрузи конвенции до анализа кода.

1. Прочитай `.gigacode/service-rules/00_index.md` - определи релевантные правила по ключевым
   словам из **уже загруженного** содержимого `intent.md` + `increment.md` (из Шага 1).
2. Используй таблицу релевантности для определения:

   | Ключевые слова из intent.md/increment.md | Какие rules загрузить |
   |----------------------------------------|-----------------------|
   | БД, таблица, колонка, Liquibase, SQL, миграция | `03_migrations.md`, `08_database.md` |
   | Controller, endpoint, REST, Swagger, API, запрос, ответ, header | `01_coding.md`, `07_api_contract.md` |
   | Entity, JPA, репозиторий, @Table | `01_coding.md`, `08_database.md` |
   | маппер, MapStruct, DTO, преобразование | `01_coding.md` |
   | сервис, бизнес-логика, валидация, @Service | `01_coding.md`, `16_refactoring.md` |
   | денежное поле, сумма, стоимость, BigDecimal, руб | `13_monetary.md` |
   | enum, статус, перечисление, код | `17_enums_over_constants.md` |
   | тест, unit, Mockito, AssertJ | `06_unit_tests_with_spring_context.md` |
   | логирование, MDC, @Slf4j, log.error | `09_logging.md` |
   | метрик, health, probe, actuator | `02_monitors.md` |

3. Прочитай **ТОЛЬКО релевантные** rules через `Read - .gigacode/service-rules/{filename}.md`.
4. Зафиксируй список загруженных rules в контексте сессии - этот список понадобится при генерации
   `implementation-plan.md` (вставь конвенции из правил в секции плана по соответствующим слоям).

**Если rules не загружались** (вызов вне pipeline, файл `00_index.md` отсутствует):
> Сервис-правила не применятся - используй общепринятые конвенции Java/Spring Boot и примеры
> из существующего кода проекта.

## Шаг 2. Проанализировать код проекта

**Критически важно:** не предполагай сигнатуры - **читай реальный код**.

### 2.1. Собрать карту классов проекта

```
1. Glob **/*Controller*.java - все контроллеры и endpoints
2. Glob **/*Service*.java - интерфейсы сервисов
3. Glob **/*ServiceImpl*.java - реализации сервисов
4. Glob **/*Repository*.java - репозитории
5. Glob **/*Entity*.java - сущности
6. Glob **/*DTO*.java, **/*Request*.java, **/*Response*.java - DTO
7. Glob **/*Mapper*.java - мапперы
8. Glob **/*Enum*.java, **/*Constant*.java - перечисления
```

### 2.2. Определить входные точки

```
1. Для каждого Controller: прочитать @RequestMapping, @PostMapping, @GetMapping
2. Определить public-методы с @PostMapping/@GetMapping/@PutMapping/@DeleteMapping
3. Составить список всех entry-points (REST, Scheduled, Event listeners)
```

### 2.3. Проследить цепочки вызовов

```
1. Для каждой entry-point: прочитать тело метода - определить вызов Service
2. Для каждого Service-метода: прочитать тело - определить вызовы Repository, других сервисов, внешних API
3. Для каждого Repository: прочитать методы - определить запросы к БД
4. Построить полный call-chain: Controller - Service - Repository/External - Return
```

### 2.4. Определить интеграции

```
1. Glob **/*Feign*.java, **/*Client*.java - внешние HTTP-клиенты
2. Glob **/*Kafka*.java, **/*Event*.java, **@EventListener - события
3. Определить, какие внешние сервисы вызываются в цепочке
```

### 2.5. Определить паттерны и архитектуры

```
1. Посмотреть на структуру проекта: как организован по слоям
2. Определить используемые паттерны: Strategy, Factory, Observer, Builder, и т.д.
3. Посмотреть мапперы: MapStruct, ручной mapping
4. Определить обработку ошибок: глобальный handler, exceptions
```

## Шаг 2.5. Уточняющие вопросы у пользователя

> Этот шаг **интерактивный**. На каждом подпункте задавай вопросы, если есть неопределённость.
> Утверждай каждый алгоритм, паттерн, цепочку вызовов перед фиксацией в плане.

### 2.5.1. Уточнение цепочек вызовов
- Все ли методы в цепочке охвачены?
- Есть ли побочные ветки (try-catch, условия, ветвления)?
- Какие методы вызываются последовательно, какие параллельно?

### 2.5.2. Уточнение алгоритмов
- Какие расчёты выполняются в каждом методе?
- Какие условия и ветвления?
- Как обрабатываются ошибки?

### 2.5.3. Уточнение интеграций
- Какие внешние API вызываются?
- Какие форматы данных передаются/получаются?
- Нужна ли обработка retry, timeout, fallback?

### 2.5.4. Уточнение методов
- Что принимает метод (параметры, источники данных)?
- Что делает внутри (пошагово)?
- Что возвращает (тип, содержание)?

**После утверждения каждого подпункта - переходить к следующему.**
Если пользователь подтверждает, что этап разобран полностью - двигаться дальше.
