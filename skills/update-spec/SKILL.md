# Актуализация спецификации проекта

Девятый, предпоследний этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → [`form-plan`](../form-plan/SKILL.md) → [`execute-plan`](../execute-plan/SKILL.md) → [`run-quality-gate`](../run-quality-gate/SKILL.md) → [`align-with-rules`](../align-with-rules/SKILL.md) → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → `update-spec` → [`finish-task`](../finish-task/SKILL.md).

Спецификация протухает сама по себе: код меняется в рамках пайплайна, а `specification/` — это отдельный, руками (скиллом) синхронизируемый снимок. Задача этого скилла — найти расхождения между кодом и документами и обновить именно расхождения, не переписывая всё заново вслепую.

Как и [`align-with-rules`](../align-with-rules/SKILL.md), этот скилл не привязан жёстко к тому, что его вызвали "в рамках задачи" — он сам определяет, в каком режиме работать (шаг 1), и одинаково корректно ведёт себя, если его вызвали как обязательный шаг пайплайна или отдельно, в любой момент, на любой ветке.

## Когда НЕ использовать

Если `specification/` не существует в корне проекта — это не актуализация, а первичное создание. Предложи [`init-spec`](../init-spec/SKILL.md) вместо этого скилла.

## Порядок действий

1. Определи режим:
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```
   Проверь, что `specification/` существует в корне проекта — если нет, см. раздел выше.
   - Если существует `$TASK_DIR/write-tests-report.md` и ещё нет `$TASK_DIR/update-spec-report.md` — **режим пайплайна**: текущая ветка соответствует задаче, для которой уже отработал `write-tests`. Область актуализации — только изменения этой задачи.
   - Иначе — **самостоятельный режим**: область актуализации — все расхождения, накопившиеся с момента последней актуализации, по всему проекту.

2. Собери источники изменений — по-разному в зависимости от режима:
   - **Режим пайплайна**: прочитай `$TASK_DIR/intent.md` (бизнес-мотивация задачи), `$TASK_DIR/execution-report.md` (раздел "Изменённые/созданные файлы" — что реально изменилось в коде), `$TASK_DIR/write-tests-report.md` (какие классы получили тестовое покрытие — само по себе тоже часть того, что могло повлиять на спецификацию, например переход сервиса из статуса "заготовка" в рабочий) и, если есть, `$TASK_DIR/align-with-rules-report.md` (правки поверх execute-plan). Этого достаточно, чтобы понять расхождения, вносимые именно этой задачей — открывать код напрямую нужно только точечно, если отчётов недостаточно для конкретного файла спецификации.
   - **Самостоятельный режим**: собери источники в этом порядке — каждый следующий только для того, что не покрыто предыдущим:
     - Прочитай `> Актуально на: <дата>, ветка <branch>` в шапке каждого файла `specification/absolut/*.md` — это точка отсчёта.
     - Просмотри `git log --oneline --since=<дата>` (в рамках репозитория проекта), чтобы получить список файлов/путей, которые менялись.
     - Просмотри `specification/increment/r*/*/` — папки задач по всем версиям и веткам, у которых есть `execution-report.md` и/или `verification-report.md`: это основной источник "что сделано и зачем" (из `intent.md` — бизнес-мотивация, из `execution-report.md` — что реально изменилось в коде). Задачи, ещё не мигрировавшие под `increment/` (начатые до реструктуризации `specification/` по доменам, до своего завершения), по-прежнему лежат по старому плоскому пути `specification/r*/*/` — просматривай и его, самостоятельный режим не обязан игнорировать историю до реструктуризации. Это дешевле и надёжнее, чем вычитывать весь код заново — используй именно эти отчёты для обновления `specification/absolut/*.md`, не открывая сам код там, где отчёт уже даёт достаточно деталей.
     - Сопоставь список путей из `git log` (шаг выше) со списками "Изменённые/созданные файлы" из найденных `execution-report.md`: пути, которые встречаются в `git log`, но не покрыты ни одним `execution-report.md` — это правки мимо пайплайна (не через `form-intent`). Только для этих конкретных путей — точечно, не всей директорией — прочитай текущий код (сущности/точки входа/сервисы/миграции/`pom.xml`, смотря что затронуто), чтобы поймать, что изменилось. Полный обход всего дерева кода, как в `init-spec`, здесь не нужен — он оправдан только при первичной инициализации, когда истории задач ещё нет.

3. Раздели файлы спецификации по способу обновления — они отличаются по надёжности вывода из кода:
   - **Выводятся из кода почти однозначно** (`absolut/structure.md`, `absolut/api.md`, `absolut/data-model.md`, `absolut/architecture.md`) — обнови напрямую там, где нашёл расхождение: новая сущность/команда/слой — добавь, удалённая — убери, изменившееся поведение (например, сервис обзавёлся методами и перестал быть заготовкой) — перепиши как факт, а не как TODO.
   - **Формулируются людьми, код только подсказывает** (`absolut/business.md`, `ideas.md`) — не перезаписывай эти файлы по факту кода. Если из кода/задач видно что-то, что похоже на новое бизнес-правило или реализованную идею из `ideas.md` — предложи пользователю формулировку и спроси подтверждение, прежде чем менять файл.

4. Для каждого изменённого файла выведи пользователю короткий список правок в формате "было → стало" перед тем, как писать на диск, если правок много или они существенны (новая сущность/новый слой архитектуры). Для мелких правок (опечатка в описании существующей команды) можно просто исправить и упомянуть в итоговом резюме.

5. Обнови шапку `> Актуально на: <дата>, ветка <branch>` в каждом изменённом файле и запись в `specification/README.md`.

5a. Оцени, не пора ли скорректировать структуру `specification/absolut/`, по двум триггерам:
   - **По зоне применения**: в коде появилась функциональность, не относящаяся ни к одному существующему домену/файлу `absolut/` — предложи пользователю новый домен/файл.
   - **По размеру**: файл(ы) домена в `absolut/` превысили ориентир ~150–200 строк (по аналогии с бюджетом `CLAUDE.md`) — предложи разбивку внутри домена или самого домена на несколько файлов.

   В обоих случаях только предложи и спроси подтверждение пользователя (как уже делаешь для правок `business.md`/`ideas.md` на шаге 3) — не переструктурируй `absolut/` самостоятельно. Разбивка семи перенесённых файлов `absolut/` по доменам не входит в эту оценку сама по себе — это только обязанность для будущих запусков `update-spec`, когда для неё созреют основания по одному из двух триггеров.

6. Запиши файл-отчёт — только в режиме пайплайна, `$TASK_DIR/update-spec-report.md`, по шаблону ниже (в самостоятельном режиме отдельный файл-отчёт не нужен — сами изменённые файлы `specification/*.md` со свежей шапкой уже фиксируют результат).

   Спроси пользователя, завершён ли шаг (например: «Спецификация актуализирована, коммитим?»). При отрицательном ответе — не коммитить. При положительном:
   - **Режим пайплайна**: обнови `$TASK_DIR/pipeline-state.md` (`update-spec` → `завершён`, `Текущий шаг` → `finish-task`) и закоммить его вместе с остальными файлами:
     ```bash
     git add <изменённые файлы specification/*.md> "$TASK_DIR/update-spec-report.md" "$TASK_DIR/pipeline-state.md"
     git commit -m "$(cat <<'EOF'
     Update spec: <короткое имя задачи>

     Co-Authored-By: Claude <noreply@anthropic.com>
     EOF
     )"
     ```
   - **Самостоятельный режим**:
     ```bash
     git add <изменённые файлы specification/*.md>
     git commit -m "$(cat <<'EOF'
     Update spec: самостоятельная актуализация

     Co-Authored-By: Claude <noreply@anthropic.com>
     EOF
     )"
     ```

7. В конце дай пользователю сводку: какие файлы изменены и в двух словах что именно, какие файлы проверены и расхождений не найдено. В режиме пайплайна дополнительно скажи, что следующий шаг — `finish-task` (вызывается вручную); в самостоятельном режиме — что шаг завершён (следующего шага пайплайна нет).

## Что не трогать

- Не удаляй из `ideas.md` пункты только потому, что они ещё не реализованы — это бэклог, а не текущее состояние.
- Не переписывай `business.md` на основе догадок по коду — бизнес-обязанности подтверждает пользователь.
- Не трогай `specification/increment/r*/` (папки задач конкретных версий/веток) — это архив артефактов пайплайна конкретных задач, а не часть актуализируемой документации проекта. То же касается `specification/r*/` — старого плоского пути, ещё встречающегося у задач, начатых до реструктуризации.
- Не трогай `specification/roadmap/` — это очередь задач и их статусы, она ведётся вручную по ходу пайплайна, а не выводится из кода.

## Шаблон `update-spec-report.md` (только режим пайплайна)

```markdown
# Отчёт об актуализации спецификации: <короткое имя задачи>

- Дата: <YYYY-MM-DD>
- Ветка: <branch>
- Источники: intent.md, execution-report.md, write-tests-report.md[, align-with-rules-report.md]

## Изменённые файлы specification/
- `<файл>` — <что изменилось, было → стало кратко>

## Проверено, расхождений не найдено
- `<файл>`

## Итог
Спецификация актуализирована по изменениям задачи <короткое имя>. Готово к finish-task.
```
