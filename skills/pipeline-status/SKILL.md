# Статус и следующий шаг пайплайна (state machine по `pipeline-state.md`)

Вспомогательный скилл поверх пайплайна из [`CLAUDE.md`](../../../CLAUDE.md#пайплайн-разработки-скиллы): [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → [`form-plan`](../form-plan/SKILL.md) → [`execute-plan`](../execute-plan/SKILL.md) → [`run-quality-gate`](../run-quality-gate/SKILL.md) → [`align-with-rules`](../align-with-rules/SKILL.md) → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → [`finish-task`](../finish-task/SKILL.md).

Он не выполняет ни один шаг сам — только определяет, какой шаг следующий, и по этому запускает нужный скилл. Источник истины — `pipeline-state.md`, файл в директории задачи, который каждый шаговый скилл обновляет сам вместе со своим коммитом (см. «Формат `pipeline-state.md`» ниже), а не память о том, что "вроде уже сделали", и не пересканирование остальных артефактов при каждом вызове.

## Важно

- **State machine по файлу состояния**, не по памяти о ходе разговора: если сессия прервалась и продолжилась заново, результат не должен зависеть от того, помнит ли модель предыдущие шаги.
- **Без auto-transition**: за один вызов запускается не больше одного шагового скилла. После его завершения — остановка, а не переход к следующему. Каждый шаговый скилл и так спрашивает пользователя перед своим коммитом (см. соответствующий `SKILL.md`) — этот скилл не сокращает и не обходит эти вопросы.
- **`finish-task` никогда не запускается автоматически** этим скиллом, даже когда он определён как следующий шаг — по [`CLAUDE.md`](../../../CLAUDE.md) он вызывается пользователем вручную. В этом случае скилл только сообщает, что задача готова к `finish-task`, и ждёт явной команды.
- Директория `specification/roadmap/` не читается автоматически (см. `CLAUDE.md`) — этот скилл её не трогает и не обновляет; чекбоксы в `progress.md`/`done.md` — забота `finish-task` по явному запросу пользователя.

## Флаги

- Без флага (по умолчанию) — определить текущий шаг, показать прогресс, запустить ровно один следующий шаговый скилл (кроме `finish-task`, см. выше).
- `--status` — только показать прогресс, ничего не запускать.
- `--step <имя-скилла>` — принудительно запустить конкретный шаговый скилл, игнорируя автоопределение (например, повторно прогнать `align-with-rules` после доработки, не проходя по цепочке заново).

## Шаг 0. Определить директорию задачи

```bash
PROJECT_ROOT=$(git rev-parse --show-toplevel)
cd "$PROJECT_ROOT"
RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
VERSION="r${RAW_VERSION%-SNAPSHOT}"
[ -z "$RAW_VERSION" ] && VERSION="r0"
BRANCH=$(git branch --show-current)
TASK_DIR="specification/increment/$VERSION/$BRANCH"
```

Если `$TASK_DIR` не существует и `intent.md` не найден нигде в `specification/increment/$VERSION/*/` — задача на этой ветке ещё не начата: сообщи об этом и предложи `form-intent` (шаг 1), дальше не продолжай.

Если `$TASK_DIR` не найден, но `intent.md`/другие артефакты этой же задачи обнаружились в `specification/increment/$VERSION/<другая-ветка>/` — скажи пользователю, что задача велась в ветке `<найденная>`, и предложи переключиться (`git checkout <найденная>`), вместо того чтобы предполагать новую задачу на текущей ветке.

## Формат `pipeline-state.md`

Путь: `$TASK_DIR/pipeline-state.md`. Markdown, как и остальные артефакты задачи:

```markdown
# Состояние пайплайна: <короткое имя задачи>

- Ветка: <branch>
- Версия: <version>
- Последнее обновление: <YYYY-MM-DD> — шагом `<имя скилла или "pipeline-status (миграция)">`

## Шаги
1. form-intent — <статус>
2. form-system-intent — <статус>
3. form-plan — <статус>
4. execute-plan — <статус>
5. run-quality-gate — <статус>
6. align-with-rules — <статус>
7. verify-implementation — <статус>
8. write-tests — <статус>
9. update-spec — <статус>
10. finish-task — <статус>

## Текущий шаг
<имя одного из 10 шагов выше, либо `ручная правка багов (без отдельного шага пайплайна)`>
```

Статус шага — одно из: `не начат` / `в процессе` / `завершён`. `в процессе` используется, когда шаг начат, но ещё не прошёл (например, `run-quality-gate` после `FAIL`) — `Текущий шаг` в этом случае остаётся тем же шагом, не продвигается.

Владелец обновления файла — каждый шаговый скилл, вместе со своим коммитом (одним коммитом с основным артефактом шага), кроме двух исключений:
- Первичное создание файла — `form-intent`, в момент создания `TASK_DIR` (до первого коммита; закоммичен будет вместе с первым коммитом `intent.md`).
- Разовая миграция для задач, начатых до появления этой возможности (нет `pipeline-state.md`, но есть другие артефакты) — выполняет этот скилл при первом вызове для такой задачи (шаг 1, вторая ветка ниже), с отдельным коммитом по подтверждению пользователя.

## Шаг 1. Определить текущий шаг

**Ветка А — `pipeline-state.md` уже существует.** Прочитай его и возьми «Текущий шаг» как источник истины — никакого сканирования остальных артефактов в этой ветке.

- Если «Текущий шаг» — `ручная правка багов (без отдельного шага пайплайна)`: точечно прочитай (не сканируя остальные артефакты) строку `**Готово к finish-task:**` в `$TASK_DIR/verification-report.md`. «да» → следующий шаг для запуска — `write-tests`. «нет» → сообщи пользователю, что сначала нужно закрыть баги из `verification-report.md`, и не запускай ничего.
- Если «Текущий шаг» — `run-quality-gate`, а статус этого шага в списке «Шаги» — `в процессе` (не `не начат`) — это повторный прогон после `FAIL`; явно отметь это в статусе прогресса на шаге 2.
- Иначе — следующий шаг для запуска — это и есть «Текущий шаг» из файла.

**Ветка Б — `pipeline-state.md` нет, но есть `intent.md` (или другие артефакты задачи).** Это задача, начатая до появления файла состояния — выполни разовую миграцию сканированием артефактов:

Проверить наличие файлов в `$TASK_DIR`, по порядку:

| # | Артефакт | Скилл, который его создаёт |
|---|----------|------------------------------|
| 1 | `intent.md` | `form-intent` |
| 2 | `system-intent.md` | `form-system-intent` |
| 3 | `plan.md` | `form-plan` |
| 4 | `execution-report.md` | `execute-plan` |
| 5 | `quality-gate-report.md` | `run-quality-gate` |
| 6 | `align-with-rules-report.md` | `align-with-rules` |
| 7 | `verification-report.md` | `verify-implementation` |
| 8 | *(файла нет — статус внутри `verification-report.md`)* | *(ручная правка багов, без отдельного шага)* |
| 9 | `write-tests-report.md` | `write-tests` |
| 10 | `update-spec-report.md` | `update-spec` |
| 11 | *(ручной вызов)* | `finish-task` |

**Задачи старше `form-system-intent`:** если `plan.md` (или любой более поздний артефакт) уже существует, а `system-intent.md` нет — это не пропущенный шаг, а задача, начатая до появления `form-system-intent` в пайплайне (по аналогии с тем, как `done.md` размечает задачи, стартовавшие до `run-quality-gate`/`align-with-rules`). В этом случае шаг 2 считается пройденным (`[-]`, не блокирует) и определение текущего шага продолжается так, как будто `system-intent.md` не требовался.

Определить текущий (первый невыполненный) шаг тем же порядком, что и раньше, с новым ветвлением на шаге 8:

1. Нет `intent.md` → шаг 1, скилл `form-intent`.
2. Есть `intent.md`, нет `system-intent.md` и нет `plan.md` → шаг 2, `form-system-intent`.
3. Есть `intent.md`, нет `plan.md`, но `system-intent.md` есть (или пропуск из-за «задачи старше `form-system-intent`» — см. выше) → шаг 3, `form-plan`.
4. Есть `plan.md`, нет `execution-report.md` → шаг 4, `execute-plan`.
5. Есть `execution-report.md`, нет `quality-gate-report.md` → шаг 5, `run-quality-gate`.
6. Есть `quality-gate-report.md`:
   - Если раздел "Итог" в нём — `FAIL` → шаг ещё не пройден: следующий шаг всё ещё `run-quality-gate`.
   - Если `PASS`, но нет `align-with-rules-report.md` → шаг 6, `align-with-rules`.
7. Есть `align-with-rules-report.md`, нет `verification-report.md` → шаг 7, `verify-implementation`.
8. Есть `verification-report.md` → прочитать строку `**Готово к finish-task:**` в разделе "Итоговый вердикт":
   - `нет` → следующий шаг — ручная правка багов (без отдельного шага пайплайна); сообщи об этом пользователю и не запускай ничего.
   - `да`, нет `write-tests-report.md` → шаг 8, `write-tests`.
   - `да`, есть `write-tests-report.md`, нет `update-spec-report.md` → шаг 9, `update-spec`.
   - `да`, есть `write-tests-report.md` и `update-spec-report.md` → все шаги 1–9 пройдены, следующий — шаг 10, `finish-task` (не запускать автоматически, см. "Важно").

По результату сканирования создай `$TASK_DIR/pipeline-state.md`, инициализированный найденным состоянием (статусы `завершён` для пройденных шагов, `не начат` для остальных, «Текущий шаг» — найденный выше; если найденный шаг — ручная правка багов, статус `verify-implementation` — `завершён`, а «Текущий шаг» — маркер ручной правки). Покажи пользователю получившийся файл и спроси, коммитим ли (тот же паттерн вопроса, что у шаговых скиллов). При да — закоммить отдельным коммитом:
```bash
git add "$TASK_DIR/pipeline-state.md"
git commit -m "$(cat <<'EOF'
Add pipeline state (миграция): <короткое имя задачи>

Co-Authored-By: Claude <noreply@anthropic.com>
EOF
)"
```
Это выполняется один раз — при следующем вызове файл уже есть, и используется ветка А.

**Ветка В — нет ни `pipeline-state.md`, ни `intent.md`.** Как и раньше, задача не начата, предложить `form-intent`.

## Шаг 2. Показать прогресс

Рендерится из `pipeline-state.md` (или из результата разового скана при миграции по ветке Б) — тот же визуальный формат чек-листа с ✅/❌/⏸:

```markdown
## Статус пайплайна: <короткое имя задачи> (ветка <branch>)

[x] form-intent            ✅
[x] form-system-intent     ✅
[x] form-plan               ✅
[x] execute-plan            ✅
[x] run-quality-gate        ✅ PASS
[ ] align-with-rules        ❌ — следующий шаг
[ ] verify-implementation   ⏸
[ ] (ручная правка багов)   ⏸ (без отдельного шага — статус внутри verification-report.md)
[ ] write-tests              ⏸
[ ] update-spec              ⏸
[ ] finish-task               ⏸ (только вручную)

Текущий шаг: align-with-rules
```

Если следующий шаг — повторный `run-quality-gate` после `FAIL` (см. ветку А выше), явно добавь это в статус: `[~] run-quality-gate ⚠ FAIL — требуется повторный прогон`.

## Шаг 3. Запустить нужный скилл (если не `--status`)

1. Если передан `--step <имя-скилла>` — использовать его вместо автоопределения из шага 1.
2. Если определённый шаг — `finish-task`: не запускать, только сообщить пользователю, что задача готова, и дальше нужен явный запрос ("заверши задачу" и т.п.).
3. Если определённый шаг — ручная правка багов (без отдельного шага пайплайна) и «Готово к finish-task» — «нет»: не запускать ничего, только сообщить пользователю, что нужно закрыть баги из `verification-report.md`.
4. Иначе — запустить найденный скилл через инструмент `Skill` (`skill: "<имя-скилла>"`), передав тот же контекст задачи, что уже определён (ветка, `$TASK_DIR`). Шаговый скилл сам задаст пользователю все нужные уточняющие вопросы и сам спросит перед своим коммитом — не предвосхищать и не дублировать это здесь.
5. После завершения запущенного скилла — остановиться. Не проверять `pipeline-state.md` заново и не запускать следующий шаг в этом же вызове.

## Пример

```
Пользователь: что дальше по этой задаче?

→ Шаг 0: TASK_DIR = specification/increment/r0.1.0/some-task
→ Шаг 1: pipeline-state.md существует (ветка А) — «Текущий шаг»: align-with-rules
→ Шаг 2: показан прогресс, текущий шаг — align-with-rules
→ Шаг 3: запускаю align-with-rules
```
