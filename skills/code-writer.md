# Skill: написание кода в проекте

Плейбук для любой задачи по написанию или изменению кода в текущем проекте. Стек определяй по факту `pom.xml` и `.claude/rules/` (обычно Spring Boot, JPA/Hibernate, Liquibase/Flyway, Lombok — но не предполагай заранее, сверяйся с реальными зависимостями проекта).

## Когда применять

Любая задача вида «добавь команду», «создай сущность», «напиши сервис», «поправь баг», «добавь миграцию» в рамках этого проекта.

## Порядок действий

1. Прочитать [`.claude/rules/README.md`](../rules/README.md) (индекс) и файлы правил, релевантные конкретной задаче (не обязательно все — например, для задачи без изменения схемы БД правило про миграции не нужно). Конкретные имена файлов правил — по факту индекса этого проекта, не по памяти о другом проекте. Правила подгружаются автоматически по `paths` только при чтении файла из их зоны — перед написанием кода их всё равно нужно прочитать явно (новый файл, созданный без чтения соседних, правило не подтянет).
2. Прочитать `CLAUDE.md` в корне проекта (если есть) — архитектурный контекст: слои, доменная модель, что уже реализовано, а что заготовка.
3. Найти в проекте 1-2 похожих существующих класса того же слоя/назначения и повторить их структуру: пакет, аннотации, Javadoc, стиль импортов.
4. Писать код, соблюдая правила из `.claude/rules/` буквально — не по памяти/по умолчанию из общих знаний о Spring.
5. Если меняется схема БД — добавить новый changeset/миграцию по конвенции проекта (путь и формат — см. правило проекта о миграциях в `.claude/rules/`), не редактировать существующие файлы.
6. Если добавляется бизнес-логика в сервисный слой (`service.impl` или аналог по факту проекта) — unit-тест на неё обязателен, по правилу проекта о тестах.

## Красные флаги (стоп, перепроверить)

- Поле с `@Autowired` вместо конструктора — неправильно (импорт `@Autowired` ловит Checkstyle, `IllegalImport`, но лучше не доводить до падения сборки).
- `@Data` на JPA-сущности — неправильно.
- Комментарии/Javadoc не на том языке, что принято в проекте (сверься с `.claude/rules/`).
- Редактирование существующей миграции БД вместо добавления новой.
- Обращение из верхнего слоя (UI/controller) напрямую к репозиторию, минуя сервис.
