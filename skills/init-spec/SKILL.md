# Инициализация спецификации проекта

Создаёт единый источник правды о проекте: не про то, как писать код (это `.claude/rules/`), а про то, что проект делает, зачем, из чего состоит и как устроен. Спецификация — не пересказ кода, а его осмысление: там, где `.claude/rules/` описывает "как", `specification/` описывает "что и зачем".

## Когда НЕ использовать

Если `specification/` уже существует и в файлах есть содержательный текст — это не инициализация, а актуализация. Сообщи об этом пользователю и предложи [`update-spec`](../update-spec/SKILL.md) вместо перезаписи с нуля.

## Порядок действий

1. Проверь, нет ли уже `specification/` с непустыми файлами в корне проекта. Если есть — см. раздел выше.

2. Собери факты о проекте, читая реальный код и конфигурацию, а не додумывая:
   - `CLAUDE.md` в корне проекта (если есть) — уже готовое резюме архитектуры, слоёв, доменной модели, незавершённых частей.
   - `.claude/rules/` — архитектурные ограничения (слои, паттерны).
   - Точки входа приложения — определи по факту стека: REST-контроллеры (`@RestController`), CLI/Shell-команды (например `@ShellMethod` для Spring Shell), обработчики сообщений, и т.п. — что из этого реально есть в проекте, то и является текущим "API".
   - JPA-сущности и связи между ними (путь — по факту структуры `src/main/java`, обычно пакет вида `entity`/`model`).
   - Слой сервисов и их реализаций — какая бизнес-логика реально есть, а какая — пустая заготовка.
   - Миграции БД (`src/main/resources/db/changelog/` для Liquibase, либо аналог для Flyway/другого инструмента) — фактическая структура таблиц.
   - `pom.xml` — реальные зависимости/интеграции (что подключено, а что только упомянуто в правилах `.claude/rules/` как "заготовка на будущее").

3. Спроси пользователя про то, что не выводится из кода:
   - Бизнес-обязанности: для кого проект, какую проблему решает, кто пользователь.
   - Идеи проекта: бэклог/куда планируется развитие (если пользователь не назовёт — оставь раздел с пометкой "не заполнено", не выдумывай).

4. Создай структуру:
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   mkdir -p specification/absolut
   ```
   Директории задач (`specification/increment/r<версия>/<ветка>/`) создаются позже отдельными задачами через `form-intent` — здесь их предварительно создавать не нужно.

5. Заполни файлы по шаблонам ниже. Не переписывай в спецификацию код целиком — только осмысленное резюме (как это уже сделано в `CLAUDE.md`, если он есть, но более подробно и по темам). Явно помечай нереализованное/заготовки (например, класс сервиса без методов, задел под будущий процесс) — это так же важно, как и то, что уже работает: спецификация, которая выдаёт желаемое за действительное, вреднее отсутствия спецификации.

6. Создай `specification/README.md` — индекс с датой создания и ссылками на все файлы.

7. Скажи пользователю, где лежит папка, и что для поддержания её в актуальном состоянии по мере развития проекта есть [`update-spec`](../update-spec/SKILL.md).

## Файлы и их назначение

- **`README.md`** (верхний уровень `specification/`) — индекс: список файлов с одной строкой описания каждого, дата последней актуализации.
- **`ideas.md`** (верхний уровень `specification/`) — идеи и направления развития, которые не являются текущим скоупом (бэклог). Заполняется со слов пользователя.
- **`absolut/business.md`** — для кого проект, какую проблему решает, ключевые бизнес-правила и сущности в бизнес-терминах (без привязки к именам классов).
- **`absolut/architecture.md`** — слои проекта (по факту структуры `src/main/java`, например `controller`/`web` → `service` → `repository` → `entity`, либо иная схема, если проект устроен по-другому), ключевые паттерны, технологический стек, что реализовано / что заготовка.
- **`absolut/structure.md`** — карта пакетов проекта: что лежит в каждом пакете и по какому принципу — состав пакетов определи по факту `src/main/java`, не предполагай заранее.
- **`absolut/api.md`** — точки входа приложения (по факту — см. шаг 2: REST-эндпоинты, CLI/Shell-команды, обработчики сообщений и т.п.) — перечислить каждую с назначением. Явно отметить, какие из типовых точек входа (REST, брокер сообщений и т.п.) в проекте пока не подключены, если это видно из `.claude/rules/` или `pom.xml`, и как они будут структурироваться, когда появятся.
- **`absolut/data-model.md`** — сущности и связи между ними (по факту JPA-аннотаций/связей в коде), с указанием, откуда это следует (миграции БД / JPA-аннотации).
- **`absolut/interactions.md`** — как компоненты взаимодействуют между собой во времени: например, пайплайн обработки входных данных через цепочку классов, поток обработки команды/запроса от точки входа до ответа — конкретные имена классов бери из реального кода проекта, не из шаблона.

Каждый файл начинается с одной строки: `> Актуально на: <дата>, ветка <branch>` — это то, что обновляет `update-spec`.
