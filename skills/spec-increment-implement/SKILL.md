# /spec-increment-implement — Реализовать код по готовому инкременту

Выполняет **только реализацию** кода по уже готовому плану — план уже написан и провалидирован
человеком (pipeline-статус "Ревью инкремента"), уточняющие вопросы уже закрыты. **Не трогает**
`specification/absolut/`,
`specification/index.md`, `specification/increment/index.md` и не меняет `Статус` файла
инкремента — актуализация документации и финальный статус `Выполнено` относятся к отдельному,
более позднему этапу конвейера ("Запустить актуализацию абсолютной документации").

**Использование:**
```
/spec-increment-implement specification/increment/01.023.00/AO-12/increment.md
/spec-increment-implement AO-12
/spec-increment-implement 01.023.00/AO-12
```

## Важно

### Gate-check (обязателен перед Шагом 1)

> ⚠️ **Флаг `--skip-gate-checks`:** если он есть в `$ARGUMENTS` — при любом **стоп** ниже вместо
> остановки выведи `⚠️ Gate-check пропущен флагом --skip-gate-checks: {текст, который был бы в
> стопе}` и продолжай к следующему пункту/Шагу 1.

1. Определить `{release}` и `{ticket}` (из аргументов или имени ветки).
2. Найти `implementation-plan.md` по пути `specification/increment/{release}/{ticket}/implementation-plan.md`.
    - **Если найден** → использовать как приоритетный источник деталей реализации (классы, сигнатуры, пакеты, миграции).
    - **Если не найден** → **стоп**:
      ```
      ⛔ Пропущен(ы) шаг(и) pipeline-конвейера.
 
      Не выполнен Шаг 3 конвейера (spec-increment-plan v2.0+): файл implementation-plan.md не найден.
      Требует выполнения: /spec-increment-plan {release} {ticket}
 
      Выполните пропущенный шаг, затем повторите запуск.
      ```
3. Проверить статус инкремента:
    - **Статус ≠ "Выполнено"** и **раздел "Изменения в коде" не пуст** → продолжить.
    - Если статус = "Выполнено" или раздел пуст → остановиться:
      ```
      ⛔ Нечего реализовывать: инкремент уже выполнен или раздел "Изменения в коде" пуст.
      ```

### Общие правила

- **Gate-check:** не выполняй Шаг 1, если не выполнен pipeline-шаг spec-increment-plan v2.0+ (Шаг 3 конвейера).
- **Пропуск шагов pipeline запрещён**, кроме `--skip-gate-checks` (только для отладки).
- Не задавай вопросов о том, ЧТО делать — план уже провалидирован. Уточняй только при прямом противоречии между планом и реальным кодом.
- Не трогай `specification/absolut/`, `specification/index.md`, `specification/increment/index.md`.
- Не меняй `Статус` файла инкремента на `Выполнено`.
- Не трогай файлы **других** инкрементов.
- Тесты правятся **только для восстановления компиляции** (сигнатуры, импорты, удалённые методы). Писать новые тесты или переписывать тестовую логику — зона ответственности `spec-increment-test`.
- Раздел "Обоснование решений по результатам разработки" — только для реальных причин, не для пересказа сделанного; нет значимого решения — нет и раздела.

## Шаг 0. Найти файл инкремента

Инкременты хранятся по пути `specification/increment/<release>/<ticket>/increment.md`.

Если `$ARGUMENTS` — существующий путь (заканчивающийся на `increment.md`), используй его
напрямую. Иначе воспринимай аргумент как:
- **номер тикета** (например `AO-12`) — ищи через `Glob specification/increment/*/{ticket}/increment.md`
- **релиз/тикет** (например `01.023.00/AO-12`) — ищи через `Glob specification/increment/{release}/{ticket}/increment.md`

Несколько кандидатов или ни одного — покажи список и уточни у пользователя.

Проверка `Статус = Выполнено` уже сделана в Gate-check выше (п.3) — здесь повторно её не делай.

## Шаг 2. Реализовать по новому формату плана

**Важно:** реализация ПИШЕТСЯ на основе service-rules, загруженных на **Шаге 1.5**.

**Приоритет источников реализации:**
1. **`implementation-plan.md`** v2.0+ — читать и использовать как основной источник: цепочки вызовов, алгоритмы методов, интеграции, данные, паттерны.
2. **`increment.md`** (раздел "## Изменения в коде") — если `implementation-plan.md` нет.

> ⚠️ Если implementation-plan.md не найден → вывести в чат:
> ```
> ⚠️ implementation-plan.md не найден. Использую системный план из increment.md.
> Рекомендуется: запустите /spec-increment-plan v2.0+ {release} {ticket} для детального технического плана.
> ```

Реализация строго по разделам `implementation-plan.md` v2.0+:

### 2.1. Прочитать «Цепочка вызовов»

- Определить порядок реализации: от входной точки (REST-эндпоинт, событие, scheduler) до выхода (БД, внешний API)
- Проследить полный путь: Controller → Service → Repository/External → Return
- Связать каждый метод в цепочке с конкретным файлом реализации

### 2.2. Реализовать «Обзор методов»

Для **каждого метода** в цепочке из `implementation-plan.md`:

- **Класс:** реализовать класс согласно `full.package.Name`
- **Метод:** сигнатура метода определяется по `methodName({params})`
- **Вход:** входные параметры → типы и источники данных
- **Алгоритм:** тело метода — пошаговая реализация согласно описанию:
  1. Шаг 1 → код шага 1
  2. Шаг 2 → код шага 2
  3. ...
- **Выход:** тип возврата, что возвращает
- **Зависимости:** внедрить зависимости через `@RequiredArgsConstructor` + `private final`

### 2.3. Реализовать «Интеграции»

- **Внешние API** → Feign-клиенты или HTTP-вызовы
- **Контракты** → DTO, request/response модели для передачи данных
- **Error handling** → retry, timeout, fallback согласно плану
- **События/Kafka** → @EventListener, producer/consumer

### 2.4. Реализовать «Данные»

- **Сущности** → JPA Entity классы в `model/entity/`
- **БД** → Liquibase миграции с `COMMENT ON` для каждой таблицы/колонки
- **Репозитории** → Spring Data JPA интерфейсы в `repository/`
- **Трансформации** → MapStruct мапперы (`DTO ↔ Entity ↔ Request/Response`)
- **Расчёты** → алгоритмы в методах сервисов

### 2.5. Реализовать «Паттерны и архитектура»

- **Паттерны** → реализовать указанные паттерны (Strategy, Factory, Observer, Builder и т.д.)
- **Архитектурные решения** → следовать решениям из плана
- **Service-rules** → применить загруженные конвенции (использовать правила, полученные на Шаге 1.5)

## Шаг 4. Зафиксировать обоснования решений (если есть)

По ходу реализации могли приниматься решения, которых нет в исходном плане и которые не очевидны
из самого кода: выбор между альтернативами, компромисс из-за ограничения, обнаруженного только на
практике, осознанное отступление от плана, обход неочевидного поведения зависимости/фреймворка.
Если такое было — допиши это в конец файла инкремента отдельным разделом:

```markdown
## Обоснование решений по результатам разработки

- {что решено не так, как в плане, или не описано планом} — {почему именно так}
```

- Пиши только то, что реально несёт причину ("почему"), а не пересказ того, что уже и так видно из
  раздела "Изменения в коде" или из самого диффа. "Реализовал метод X" — не обоснование, это
  пересказ; "Метод X не использует Y, потому что Z" — обоснование.
- Если за всю реализацию не было ни одного решения, которое стоит объяснять отдельно от кода — не
  создавай этот раздел вообще. Пустой или формальный раздел ("всё сделано по плану", "особых
  решений не было") хуже, чем его отсутствие: отсутствие раздела однозначно читается как "нечего
  добавить", а не как забытый шаг.
- Раздел — последний в файле, после всех существующих секций плана.

### 5.2. Сбор данных для отчёта

1. **Посчитай файлы** через `git status --short | wc -l` или `git diff --name-only HEAD`:
   - Entity: `git diff --name-only HEAD | grep "model/entity/"`
   - Repository: `git diff --name-only HEAD | grep "repository/"`
   - Service: `git diff --name-only HEAD | grep "service/"`
   - Controller: `git diff --name-only HEAD | grep "controller/"`
   - MapStruct: `git diff --name-only HEAD | grep "configuration/mapper/"`
   - DTO: `git diff --name-only HEAD | grep "<модуль-с-DTO-контрактами>"` (имя модуля — по факту структуры проекта)
   - Liquibase: `git diff --name-only HEAD | grep "db/changelog/"`

2. **Прочти increment.md** — извлеки разделы:
   - `## Цель` — для Summary
   - `## Изменения в коде` — для категорий файлов
   - `## Обоснование решений по результатам разработки` (раздел из Шага 6, необязательный) — для «Архитектурные решения»

3. **Прочти implementation-plan.md** — извлеки:
   - `## Цепочка вызовов` — для Controller/Service описаний
   - `## Данные` — для Entity/Repository/DTO описаний
   - `## Паттерны и архитектура` — для «Архитектурные решения»

### 5.3. Правила генерации

- **Summary** — 2-3 предложения, что реализовано, без деталей
- **Entity/Repository/Service** — перечислить ВСЕ классы, не только ключевые
- **MapStruct** — разделить на Request и Response мапперы
- **DTO** — разделить на Request и Response, указать модуль (по факту структуры проекта)
- **Liquibase** — перечислить все таблицы с количеством колонок
- **Архитектурные решения** — только реальные решения, не пересказ плана
- **Затронутые файлы** — ТОЛЬКО сводная таблица по категориям, полный список в `increment.md`
- **Что НЕ реализовано** — всегда указывать `specification/absolut/` и тесты
