---
name: finish-task
description: Десятый, последний шаг пайплайна разработки — вызывается пользователем вручную ("заверши задачу", "сведи ветку", "закрой задачу") после verify-implementation/write-tests/update-spec, не запускается автоматически. Выполняет squash ещё не опубликованных коммитов ветки задачи в один, обновляет статус задачи в specification/roadmap/progress.md, переносит её в specification/increment/r<версия>/done.md после слияния в интеграционную ветку (создавая файл текущей релизной версии, если его ещё нет, иначе дополняя), коммитит это обновление (и любые случайно оставшиеся незакоммиченными файлы) и переключается на неё. Не выполняет само слияние — это остаётся ручным действием пользователя.
---

# Завершение задачи (roadmap → коммит → интеграционная ветка)

Десятый, последний этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → [`form-plan`](../form-plan/SKILL.md) → [`execute-plan`](../execute-plan/SKILL.md) → [`run-quality-gate`](../run-quality-gate/SKILL.md) → [`align-with-rules`](../align-with-rules/SKILL.md) → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → `finish-task`.

В отличие от остальных девяти шагов, этот не запускается автоматически — раз каждый шаг пайплайна уже коммитит сам себя по ходу работы, роль этого шага не в том, чтобы "подмести" за ними (коммитить обычно уже нечего, кроме его собственной правки `roadmap/progress.md`), а в том, чтобы явно закрыть задачу: обновить статус в `specification/roadmap/progress.md` и вернуться на интеграционную ветку проекта. Перед переключением на интеграционную ветку скилл сжимает ещё не опубликованные коммиты задачи в один, чтобы история `develop` не засорялась техническими коммитами шагов пайплайна. Слияние ветки в неё этот скилл не выполняет — это отдельное ручное действие пользователя.

Статус по каждому шагу пайплайна (`form-intent` → ... → `finish-task`) чек-листами в `progress.md`/`done.md` не хранится — единственный источник истины по шагам конкретной задачи — её `pipeline-state.md` (см. [`pipeline-status`](../pipeline-status/SKILL.md)). `progress.md`/`done.md` хранят только сводную таблицу (с общим статусом задачи из словаря в [`roadmap/index.md`](../../../specification/roadmap/index.md)) и короткое описательное упоминание задачи под заголовком.

`done.md`, в отличие от `progress.md`, живёт не в `specification/roadmap/`, а в `specification/increment/r<версия>/done.md` — один файл на релизную версию, рядом с папками задач этой версии (см. `roadmap/index.md`).

## Порядок действий

1. Определи директорию задачи:
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```
   Определи интеграционную ветку проекта (`INTEGRATION_BRANCH`) — обычно `develop`, если её нет локально — `main`/`master` (первая существующая); если неочевидно — спроси пользователя один раз.

2. Прочитай `$TASK_DIR/verification-report.md`. Если файла нет — спроси пользователя, был ли `verify-implementation` осознанно пропущен для этой задачи (симметрично escape hatch у `run-quality-gate`/`align-with-rules`). Если да — попроси короткую причину; если в `pipeline-state.md` для этого шага такой причины ещё нет (шаг был пропущен, не дойдя до самостоятельной отметки) — допиши её там на шаге 7. Пропусти шаг 3 и перейди к шагу 3b. Если пропуска не было или пользователь не уверен — скажи, что `verify-implementation` не пройден, и не продолжай.

3. Если `verification-report.md` есть — проверь готовность по строке `**Готово к finish-task:**` в разделе "Итоговый вердикт": `да` → продолжай; `нет` → сообщи пользователю причину из этой строки (обычно «есть баги без статуса, дождаться ручной правки») и не продолжай. Если такой строки в файле нет (отчёт старого формата) — откатись на прежнюю эвристику: раздел "Найденные баги" либо "не найдено", либо у каждого бага есть `→ Статус: ...`.

3a. Проверь `$TASK_DIR/write-tests-report.md`. Если файла нет — спроси пользователя, был ли `write-tests` осознанно пропущен для этой задачи (тот же escape hatch, что и в шаге 2 для `verify-implementation`). Если да — попроси короткую причину и, при необходимости, допиши её в `pipeline-state.md` на шаге 7 (как в шаге 2). Если пропуска не было или пользователь не уверен — скажи, что `write-tests` не пройден, и не продолжай.

3b. Проверь `$TASK_DIR/update-spec-report.md`. Если файла нет — спроси пользователя, был ли `update-spec` осознанно пропущен для этой задачи (тот же escape hatch, что и в шаге 2 для `verify-implementation`). Если да — попроси короткую причину и, при необходимости, допиши её в `pipeline-state.md` на шаге 7 (как в шаге 2). Если пропуска не было или пользователь не уверен — скажи, что `update-spec` обязателен и не пройден, и не продолжай.

4. Проверь, что текущая ветка (`git branch --show-current`) совпадает с веткой из `TASK_DIR` — не коммить и не переключай ветку, если это не так.

5. Обнови `specification/roadmap/progress.md`: найди строку задачи в сводной таблице по имени ветки (задача должна быть уже перенесена сюда из `queue.md` — если её там нет, либо она ещё не бралась в работу, либо уже перенесена в `done.md` вручную, и этот шаг для неё не актуален) и смени значение колонки «Статус» на `завершение · не влито в \`$INTEGRATION_BRANCH\`` (пайплайн пройден, ветка ждёт слияния — по образцу уже использовавшейся формулировки, см. `git log -p -- specification/roadmap/progress.md`; словарь статусов — в [`roadmap/index.md`](../../../specification/roadmap/index.md)). Описательный абзац под заголовком секции трогай, только если он устарел по существу (не в связи с этим шагом). Статус по шагам пайплайна здесь не отмечается чек-листами — это по-прежнему только `pipeline-state.md` (см. примечание выше).

6. `git status --porcelain` — покажи пользователю список изменённых/новых файлов (обновлённый `roadmap/progress.md` плюс всё, что могло остаться незакоммиченным другими шагами) и спроси, коммитим ли (тот же паттерн вопроса-подтверждения, что и в остальных 9 шагах). Если пусто — коммитить нечего, сразу к шагу 8.

7. При положительном ответе — обнови `$TASK_DIR/pipeline-state.md` (`finish-task` → `завершён`; заодно допиши причины, собранные на шагах 2/3a/3b, для тех шагов, у которых их там ещё нет) и собери сообщение коммита на основе `intent.md` (короткое имя задачи) вида `Finish task: <короткое имя задачи>`; `git add` именно изменённых файлов (не `-A`), включая `$TASK_DIR/pipeline-state.md`; если среди изменений встретился файл, явно не относящийся к `TASK_DIR` или к путям, изменённым по ходу задачи (судя по `execution-report.md`/`align-with-rules-report.md`) — остановись и спроси пользователя, а не коммить его молча. Закоммить:
   ```bash
   git add <файл1> <файл2> ... "$TASK_DIR/pipeline-state.md"
   git commit -m "$(cat <<'EOF'
   Finish task: <короткое имя задачи>

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```

7a. **Squash ещё не опубликованных коммитов ветки в один**, перед переключением на `$INTEGRATION_BRANCH`.

    Определить границу — самую свежую (ближайшую к `HEAD`) точку среди всех "опубликованных" ориентиров, чтобы squash не задел ни одного коммита, уже присутствующего в `$INTEGRATION_BRANCH` или на remote:

    ```bash
    git status --porcelain   # страховка: рабочее дерево должно быть чистым на этом шаге
    CURRENT_HEAD=$(git rev-parse HEAD)
    DEVELOP_BASE=$(git merge-base HEAD "$INTEGRATION_BRANCH" 2>/dev/null)

    UPSTREAM_TIP=""
    if git rev-parse --abbrev-ref --symbolic-full-name '@{u}' >/dev/null 2>&1; then
      UPSTREAM_TIP=$(git rev-parse '@{u}')
    fi

    REMOTE_TIP=""
    REMOTE_NAME=$(git remote | head -1)
    if [ -n "$REMOTE_NAME" ]; then
      REMOTE_LINE=$(git ls-remote --heads "$REMOTE_NAME" "$BRANCH" 2>/dev/null)
      [ -n "$REMOTE_LINE" ] && REMOTE_TIP=$(echo "$REMOTE_LINE" | awk '{print $1}')
    fi

    BOUNDARY="$DEVELOP_BASE"
    for CAND in "$UPSTREAM_TIP" "$REMOTE_TIP"; do
      [ -z "$CAND" ] && continue
      # кандидат учитывается, только если он реально предок HEAD — иначе он не «граница», а расхождение,
      # которое reset --soft мог бы молча похоронить; в этом случае кандидат пропускается с предупреждением
      if ! git merge-base --is-ancestor "$CAND" "$CURRENT_HEAD"; then
        echo "Предупреждение: $CAND (upstream/remote) не является предком HEAD — пропускаю как кандидата границы"
        continue
      fi
      CAND_COUNT=$(git rev-list --count "$CAND..$CURRENT_HEAD")
      BOUNDARY_COUNT=$(git rev-list --count "$BOUNDARY..$CURRENT_HEAD")
      [ "$CAND_COUNT" -lt "$BOUNDARY_COUNT" ] && BOUNDARY="$CAND"
    done
    ```

    Если `$DEVELOP_BASE` пуст (нет общего предка с `$INTEGRATION_BRANCH`) — не выполнять squash, сообщить пользователю о проблеме и остановиться (это указывает на более серьёзную проблему с веткой, не относящуюся к squash).

    Если `git status --porcelain` не пуст — не выполнять squash (сигнал, что предыдущие шаги не закоммитили что-то), сообщить пользователю и остановиться.

    Если `$BOUNDARY` == `$CURRENT_HEAD` — squash нечего делать (все коммиты ветки уже опубликованы и/или уже есть в `$INTEGRATION_BRANCH`): пропустить этот шаг без ошибки, перейти к шагу 8 как раньше.

    Иначе — собрать сообщение итогового коммита:
    - Заголовок — короткое имя задачи из заголовка `$TASK_DIR/intent.md` (строка `# Намерение: <короткое имя задачи>`, без префикса «Намерение: »), тот же принцип, что уже используют сообщения промежуточных коммитов пайплайна (`Add plan: <короткое имя задачи>` и т.п.), но без префикса `Add ...:` — это финальный коммит задачи, а не коммит одного из её артефактов.
    - Тело — 3–8 содержательных пунктов, кратко пересказывающих, что реализовано: составляются по разделу `## Выполненные шаги` (и, если нужно, `## Изменённые/созданные файлы`) из `$TASK_DIR/execution-report.md`, если файл есть, дополненные при необходимости целью/ценностью из `## Цель / ценность` в `intent.md`. Не копировать пункты `execution-report.md` дословно построчно — они технические (по шагам плана), пересказ должен читаться как описание того, что получил пользователь, а не как чек-лист выполнения плана. Если `execution-report.md` недоступен (шаг был пропущен и это отражено в `pipeline-state.md`) — тело строится только на основе `intent.md` (раздел «Идея»/«Цель / ценность»).
    - Футер — `Co-Authored-By: Claude <noreply@anthropic.com>` (тот же формат, что и в остальных коммитах, создаваемых шаговыми скиллами этого пайплайна).

    Показать пользователю: диапазон коммитов, которые будут squash'нуты (`git log --oneline "$BOUNDARY..$CURRENT_HEAD"`), и собранное сообщение — спросить подтверждение (тот же паттерн вопроса-подтверждения, что и в остальных шагах пайплайна перед коммитом; `git reset --soft` — операция, переписывающая историю, пусть и только ещё не опубликованных коммитов, поэтому подтверждение обязательно, не пропускается даже при «да» на шаге 6). При отрицательном ответе — не выполнять squash, оставить ветку как есть, перейти к шагу 8, сообщить пользователю в финальном резюме (шаг 10), что squash был пропущен по его решению.

    При положительном ответе:
    ```bash
    git reset --soft "$BOUNDARY"
    git commit -m "$(cat <<EOF
    <заголовок>

    <тело>

    Co-Authored-By: Claude <noreply@anthropic.com>
    EOF
    )"
    ```
    `pipeline-state.md` не трогается этим шагом (задача на этом этапе завершена, дальнейших шагов на этой ветке не будет).

8. `git checkout "$INTEGRATION_BRANCH"`.

9. Спроси пользователя, слита ли ветка `<BRANCH>` в `$INTEGRATION_BRANCH` уже сейчас (или сливается прямо сейчас, в рамках этого же разговора). Если нет или пользователь не уверен — ничего не делай: задача остаётся в `progress.md` до отдельного запроса пользователя обновить роадмап после слияния (сам факт вливания отдельным чекбоксом нигде не отмечается — он проявляется тем, что задача переехала в `done.md` текущей релизной версии, см. ниже). Если да:
   a. `DONE_FILE="specification/increment/$VERSION/done.md"`. Перенеси задачу из `progress.md` в `$DONE_FILE` (уже на ветке `$INTEGRATION_BRANCH`; если файла для этой релизной версии ещё нет — создай его с шапкой по образцу уже существующих `done.md` других версий — заголовок `# Выполненные задачи`, таблица `| Задача | Ветка | Завершена |`, ссылка-примечание на `roadmap/index.md`; если уже есть — просто дополни): убери задачу из таблицы и раздела в `progress.md` (перенумеровав оставшиеся задачи и поправив колонку «Зависит от», если она ссылалась на номер этой задачи), добавь строку в таблицу `$DONE_FILE` (задача / ветка / сегодняшняя дата, в начало — список отсортирован от новых к старым) и короткий раздел `### <название>` под ней — одна строка вида `` `<ветка>` · <версия> · [intent.md](<ветка>/intent.md) · ... `` со ссылками на все файлы, которые реально есть в `TASK_DIR` (пути — относительно `$DONE_FILE`, т.е. просто `<ветка>/<файл>`, задачи этой версии лежат рядом). Без чек-листа шагов (он был бы дублированием `pipeline-state.md`) и без краткого описания задачи — оно уже есть в `intent.md`, дублировать не нужно.
   b. `git add specification/roadmap/progress.md "$DONE_FILE"`, закоммить сообщением вида `Update roadmap: <короткое имя задачи> завершена и влита в интеграционную ветку` (тот же паттерн, что уже использовался для похожих коммитов — см. `git log --grep="Update roadmap"`).

10. Сообщи пользователю: ветка `<имя>` готова, изменения закоммичены (включая обновление роадмапа) или уже были чистыми, текущая ветка — `$INTEGRATION_BRANCH`; если шаг 9 не сработал (слияния ещё не было) — напомни, что после ручного слияния нужно отдельно попросить обновить роадмап. Если squash на шаге 7a был выполнен — упомяни, что коммиты ветки сжаты в один; если он был пропущен пользователем или не требовался (граница совпала с `HEAD`) — отдельно не упоминать.

Без шаблона выходного файла в `specification/` — этот шаг не создаёт новых файлов задачи, только правит `specification/roadmap/progress.md` (и, при слиянии, `specification/increment/r<версия>/done.md` — создавая его при необходимости), коммитит и переключает ветку.
