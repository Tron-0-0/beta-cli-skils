# Реализация плана (plan → код + отчёт)

Четвёртый этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → [`form-plan`](../form-plan/SKILL.md) → `execute-plan` → [`run-quality-gate`](../run-quality-gate/SKILL.md) → [`align-with-rules`](../align-with-rules/SKILL.md) → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → [`finish-task`](../finish-task/SKILL.md).

Это единственный шаг пайплайна, который пишет код. Всё, что нужно было решить и согласовать, уже решено в `intent.md`/`plan.md` — здесь не нужно заново продумывать архитектуру, нужно реализовать план и честно задокументировать, что получилось. Этот шаг пишет только код по плану — тесты на новую бизнес-логику пишутся и прогоняются отдельно, на шаге [`write-tests`](../write-tests/SKILL.md), уже после `verify-implementation`.

## Порядок действий

1. Определи директорию задачи:
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```

2. Прочитай `$TASK_DIR/plan.md`. Если файла нет — сначала проверь, не осталась ли задача в другой ветке: поищи `plan.md` в `specification/increment/$VERSION/*/`. Если нашёлся в другой ветке — скажи пользователю, что задача велась в ветке `<найденная>`, и предложи переключиться (`git checkout <найденная>`) вместо продолжения в текущей. Если нигде не нашёлся — скажи пользователю, что нужен план (`form-plan`), не начинай писать код по собственной интерпретации задачи.

3. Прочитай `.claude/skills/code-writer.md` и — из `.claude/rules/` (по индексу `README.md`) — только файлы правил, релевантные конкретным шагам `plan.md`, не все подряд (например, если план не меняет схему БД, правило про миграции не нужно). Конвенции, которые в зависимости от плана могут понадобиться: слои, DI, Lombok, именование, Javadoc, импорты, миграции БД, логирование, тесты. Следуй прочитанным правилам буквально, а не по памяти о Spring "по умолчанию".

4. Иди по шагам `plan.md` по порядку. Для каждого шага:
   - Найди в проекте похожий существующий класс и повторь его структуру (пакет, аннотации, стиль импортов/Javadoc), как требует общее правило проекта об оформлении кода из `.claude/rules/`.
   - Если шаг оказался невыполним как описан в плане (например, обнаружилась несовместимость) — не молчи и не переписывай план задним числом: реализуй разумную альтернативу, но чётко зафиксируй это как отклонение в отчёте (шаг 6).
   - Тесты на этом шаге не пишутся — unit-тесты для новой/изменённой бизнес-логики пишет отдельно [`write-tests`](../write-tests/SKILL.md), после `verify-implementation`.

5. После того как шаги реализованы, прогони:
   ```bash
   ./mvnw clean package -DskipTests
   ```
   Зафиксируй результат (успех/ошибки) в отчёте — только сборку/компиляцию, тесты на этом шаге не прогоняются.

6. Запиши `$TASK_DIR/execution-report.md` по шаблону ниже.

7. Если сборка из шага 5 зелёная — спроси пользователя, завершён ли шаг (например: «Реализация готова, коммитим?»). При отрицательном ответе — не коммитить, продолжить правки и спросить повторно, когда пользователь скажет, что готово. При положительном — обнови `$TASK_DIR/pipeline-state.md` (`execute-plan` → `завершён`, `Текущий шаг` → `run-quality-gate`) и закоммить изменённые/созданные файлы задачи плюс `execution-report.md` и `pipeline-state.md` (по образцу коммита `intent.md` в [`form-intent/SKILL.md`](../form-intent/SKILL.md), шаг 6 там): `git add` только по списку конкретных файлов (не `-A`), сообщение:
   ```bash
   git add <файл1> <файл2> ... "$TASK_DIR/execution-report.md" "$TASK_DIR/pipeline-state.md"
   git commit -m "$(cat <<'EOF'
   Implement: <короткое имя задачи>

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```
   Если сборка не зелёная и это зафиксировано как отклонение в отчёте — коммит **не делается**, рабочее дерево остаётся некоммиченным: `run-quality-gate`/hook в таком состоянии корректно посчитают код неготовым.

8. Скажи пользователю, что реализация готова, кратко перечисли отклонения от плана (если были), и что следующий шаг — `run-quality-gate`.

## Шаблон `execution-report.md`

```markdown
# Отчёт о реализации: <короткое имя задачи>

- Ветка: <branch> / Версия: <version>
- Основано на: plan.md

## Выполненные шаги
- [x] <шаг из плана> — <кратко, что сделано>
- [ ] <шаг из плана> — не выполнен, потому что <причина>

## Изменённые/созданные файлы
- <путь> — <новый/изменён> — <суть изменения>

## Отклонения от плана
<чего в плане не было, но пришлось сделать иначе — и почему; если отклонений нет, написать "нет">

## Сборка
- `./mvnw clean package -DskipTests`: <результат> (тесты — на шаге `write-tests`, здесь не прогоняются)

## Незакрытые вопросы
- ...
```
