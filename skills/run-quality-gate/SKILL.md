Тесты на этом шаге не прогоняются — их пишет и запускает отдельный шаг `write-tests`, после `verify-implementation`. Тяжёлую часть (сборка, статанализ, разбор вывода) выполняет в изолированном subagent-контексте через инструмент Agent и пишет краткий вердикт в `quality-gate-report.md`. Использовать сразу после `execute-plan`, до `align-with-rules` — переход к нему заблокирован hook'ом `pre-align-with-rules-gate.sh`, если этот гейт не пройден. Не использовать для проверки стиля/конвенций кода (это `align-with-rules`) и не использовать для поиска логических багов (это `verify-implementation`).

# Проверка качества (build/static-analysis gate)

Пятый этап пайплайна: [`form-intent`](../form-intent/SKILL.md) → [`form-system-intent`](../form-system-intent/SKILL.md) → [`form-plan`](../form-plan/SKILL.md) → [`execute-plan`](../execute-plan/SKILL.md) → `run-quality-gate` → [`align-with-rules`](../align-with-rules/SKILL.md) → [`verify-implementation`](../verify-implementation/SKILL.md) → *(ручная правка багов, без отдельного шага)* → [`write-tests`](../write-tests/SKILL.md) → [`update-spec`](../update-spec/SKILL.md) → [`finish-task`](../finish-task/SKILL.md).

Обнаружение здесь остаётся детерминированным: что считается находкой — решают PMD/Checkstyle, не модель. Но, в отличие от чистого гейта, этот шаг умеет сам устранять найденные механические нарушения по подтверждению пользователя и перезапускать проверку, вместо того чтобы просто останавливаться на `FAIL`. Тесты сюда не входят — они появляются в пайплайне позже, на шаге `write-tests`, чтобы не гонять один и тот же прогон трижды на коде, который может ещё измениться после `verify-implementation`. Переход к `align-with-rules` (смысловое ревью на соответствие правилам) заблокирован hook'ом, пока этот гейт не пройден на актуальном коммите.

## Порядок действий

1. Определи директорию задачи:
   ```bash
   PROJECT_ROOT=$(git rev-parse --show-toplevel)
   cd "$PROJECT_ROOT"
   RAW_VERSION=$(awk '/<\/parent>/{f=1} f && /<version>/{gsub(/<\/?version>/,""); print; exit}' pom.xml 2>/dev/null | xargs)
   VERSION="r${RAW_VERSION%-SNAPSHOT}"
   [ -z "$RAW_VERSION" ] && VERSION="r0"
   BRANCH=$(git branch --show-current)
   TASK_DIR="specification/increment/$VERSION/$BRANCH"
   ```

2. Прочитай `$TASK_DIR/execution-report.md`. Если файла нет — прежде чем считать, что `execute-plan` не выполнялся, поищи его в `specification/increment/$VERSION/*/`. Если нашёлся в другой ветке — скажи пользователю, что задача велась в ветке `<найденная>`, и предложи переключиться (`git checkout <найденная>`) вместо продолжения в текущей. Если нигде не нашёлся — скажи пользователю, что сначала нужен `execute-plan`, не продолжай.

3. Проверь свежесть уже существующего гейта — дёшево, инлайн, без субагента:
   ```bash
   git rev-parse HEAD
   git status --porcelain -- '**/*.java' .claude/
   ```
   Свежесть проверяется только по `*.java`-файлам и `.claude/` (правила/скиллы пайплайна) — правки ресурсов (`application.properties`, YAML и т.п.) не требуют пересборки/перезапуска тестов сами по себе и не считаются основанием для повторного гейта. Это тот же критерий, что использует hook `pre-align-with-rules-gate.sh`.

   Если `$TASK_DIR/quality-gate-report.md` уже существует, коммит, записанный в нём, совпадает с текущим `git rev-parse HEAD`, и вывод команды выше пуст — гейт уже пройден на актуальном коде. Покажи пользователю уже записанный итог и не перезапускай сборку/тесты — сразу переходи к шагу 7.

4. Иначе запусти проверку в изолированном subagent-контексте — вывод `./mvnw` может быть большим и не должен занимать контекст основной сессии. Вызови `Agent`:
   - `subagent_type: general-purpose`. Вызов синхронный (без `isolation`) — результат нужен сразу, следующий шаг этого скилла зависит от него.
   - Самодостаточный промпт (агент не видит эту беседу и не помнит контекст задачи), который должен явно включать:
     - Рабочая директория — корень репозитория проекта (передай абсолютный путь `$PROJECT_ROOT`).
     - Перед прогоном — `git status --porcelain -- '**/*.java'` (baseline, ожидается пустым после свежести из шага 3).
     - Прогнать единой командой `./mvnw clean verify -DskipTests` (без предварительного grep по `pom.xml` на предмет PMD/checkstyle — оба плагина, как и Spotless, уже привязаны к соответствующим фазам сборки в `pom.xml`, отдельно проверять их подключение не нужно).
     - После прогона — `git status --porcelain -- '**/*.java'` и `git diff --stat -- '**/*.java'` — список файлов, переформатированных Spotless в процессе сборки (если пусто — «не переформатировал»).
     - Если сборка упала на компиляции — зафиксировать факт и детали (файл/класс); находки статического анализа в этом случае не парсить (`verify` до фазы PMD/Checkstyle не дойдёт).
     - Если сборка/компиляция прошли — найти находки PMD/Checkstyle из структурированного вывода (`target/checkstyle-result.xml`, `target/pmd.xml`), не из текстового лога Maven — так надёжнее для последующего парсинга. Если ни один из файлов не появился — вернуть «не настроено в проекте». Каждую находку вернуть в виде `<файл>:<строка> — правило — сообщение`.
     - Вернуть структурированный ответ, не полный лог Maven: статус сборки (OK/FAIL + детали при FAIL), список переформатированных Spotless файлов (или «нет»), список находок PMD/Checkstyle (или «нет»/«не настроено в проекте»).

5. По статусу сборки и находкам из шага 4 — цикл самоустранения:
   - **Сборка упала (ошибка компиляции)** → сразу `FAIL`, без цикла — зафиксировать в отчёте, эскалация в обычный диалог (правки в коде, не в этом скилле).
   - **Сборка ОК, находок PMD/Checkstyle нет** → `PASS`, перейти к шагу 6.
   - **Сборка ОК, есть находки** → показать их пользователю в чате, по одной, в формате как у `align-with-rules` (см. [«Формат находки»](../align-with-rules/SKILL.md#формат-находки-в-чате-перед-применением)):
     ```markdown
     ### <N>. <короткое описание нарушения>
     - Где: `<файл>:<строка>`
     - Правило: <PMD/Checkstyle-правило, не файл из .claude/rules/>
     - Нарушение: <что именно не так>
     - Исправление: <что будет сделано>
     ```
     Спросить подтверждение на исправление. Без подтверждения правки не вносятся ни на одной находке — даже если она выглядит тривиальной.
   - При подтверждении — внести правки в основном контексте (не через субагента: находки PMD/Checkstyle обычно механические — неиспользуемый импорт, длина строки/метода, магические числа и т.п.), следуя стилю уже написанного кода. Затем повторить шаг 4 (новый единый прогон субагентом) на исправленном коде.
   - Если повторный прогон вскрывает новые находки (в том числе вызванные предыдущей правкой или переформатированием Spotless) — тот же цикл: показ → подтверждение → правка → повторный прогон. Число итераций не ограничено.
   - Если пользователь на любой итерации отказывается вносить правки — остановить цикл: `FAIL`, отклонённые находки фиксируются в отчёте как есть, переход к `align-with-rules` остаётся заблокирован hook'ом до устранения (как и раньше).
   - Находки, не устранимые простой механической правкой (требуют структурного решения) — зафиксировать как есть, эскалация в обычный диалог вне цикла; этот скилл их не автоматизирует.

6. Запиши/перезапиши `$TASK_DIR/quality-gate-report.md` по шаблону ниже:
   - Если за цикл шага 5 были применены правки к `*.java` — сначала закоммить их **отдельным коммитом, до** записи отчёта:
     ```bash
     git add <изменённые .java файлы>
     git commit -m "$(cat <<'EOF'
     Fix quality gate findings: <короткое имя задачи>

     Co-Authored-By: Claude <noreply@anthropic.com>
     EOF
     )"
     ```
     Взять `git rev-parse HEAD` после этого коммита — это и есть SHA для поля «Коммит» отчёта. Так отчёт может сослаться на код, который он проверял, не ссылаясь сам на себя (без `--amend`, который в пайплайне нигде не используется). Если правок не было — SHA как и раньше, текущий `HEAD`, этим шагом не меняется.

     Это единственный шаг пайплайна, где за один шаг может получиться два коммита вместо одного — оба создаются сразу после одного и того же подтверждения пользователя ниже, вопрос задаётся один раз, не два. Хук `pre-align-with-rules-gate.sh` от этого порядка не страдает: его инвариант (SHA отчёта — предок текущего `HEAD`, и между ними нет диффа по `**/*.java`/`.claude/`) остаётся верным.
   - Итог `PASS` — если сборка зелёная **и** (статический анализ либо не настроен в проекте, либо все найденные нарушения устранены за цикл шага 5). Итог `FAIL` — если сборка упала, либо остались отклонённые пользователем находки.
   - Обнови `$TASK_DIR/pipeline-state.md`: при `PASS` — `run-quality-gate` → `завершён`, `Текущий шаг` → `align-with-rules`; при `FAIL` — статус остаётся `в процессе`, `Текущий шаг` остаётся `run-quality-gate` (повторный прогон после исправления).

   Спроси пользователя, завершён ли шаг (например: «Гейт записан, коммитим `quality-gate-report.md`?»). При отрицательном ответе — не коммитить. При положительном — закоммить файл отчёта вместе с `pipeline-state.md` (второй коммит шага, если правки из цикла уже закоммичены выше; единственный коммит, если правок не было):
   ```bash
   git add "$TASK_DIR/quality-gate-report.md" "$TASK_DIR/pipeline-state.md"
   git commit -m "$(cat <<'EOF'
   Add quality gate report: <короткое имя задачи>

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```
   Это относится и к `PASS`, и к `FAIL` — отчёт коммитится в любом случае, чтобы зафиксировать факт проверки.

7. Сообщи пользователю итог:
   - При `PASS` — гейт пройден (с учётом того, сколько находок было устранено за цикл, если он был), следующий шаг — `align-with-rules`.
   - При `FAIL` — что именно не так (упавшая сборка или отклонённые находки статического анализа), и что это нужно исправить на текущей задаче (не переносить дальше по пайплайну), прежде чем гейт можно перезапустить.

## Шаблон `quality-gate-report.md`

```markdown
# Отчёт о проверке качества: <короткое имя задачи>

- Ветка / Версия / Коммит: <branch> / <version> / <SHA>
- Дата проверки: <YYYY-MM-DD>
- Команда: `./mvnw clean verify -DskipTests`

## Сборка
OK / FAIL — <детали при FAIL>

## Spotless (автоформатирование)
Переформатировал файлы: да (<список>) / нет

## Статический анализ (PMD/Checkstyle)
OK (находок нет) / находки устранены / FAIL (находки отклонены пользователем) / не настроено в проекте

## Цикл самоустранения
- Итераций прогона: <N>
- Устранено находок: <N> — <файл:строка — правило> (кратко, по одной строке на находку)
- Отклонено пользователем: <N> — <файл:строка — правило — причина отказа> (или «нет»)

## Итог
PASS / FAIL
```
